Stop paying a fresh TCP handshake for every request — and the cross-task bug that hid inside the fix

Levels 1–6 close the backend connection after every exchange. Correct, but slow: at any real concurrency, every request pays ~1 RTT to the backend before byte one, purely to build a socket that gets thrown away one response later. Level 7 closes that gap with a per-Server bounded LIFO idle-connection pool — a Mutex<Vec<PooledConn>> with lazy idle-timeout eviction, no sweeper task. It also fills two timeout holes (a hung backend that blocked forever; an idle bound on pooled sockets), and pools the whole Conn<TcpStream> so buffer reuse comes for free. The real story of this level is a TOCTOU bug that every per-task review passed — a pooled connection that died between check and write left the client with no response at all, caught only by a whole-branch review, fixed by serializing the head once and retrying only the write.

Executive Summary

Reuse the socket you already dialed — and prove the reuse never leaks a byte or drops a request.

Levels 1–6 send the backend Connection: close after every exchange, so each proxied request first pays a full TCP handshake — about one round-trip — before a single byte of the request even leaves. Level 7 removes that tax with a connection pool: after a clean, reusable exchange, the backend socket goes into an idle stack instead of being closed, and the next request to that backend takes it back out and skips the connect entirely.

The pool lives on Server in balancer.rs — the struct that already owns the per-backend inflight, ewma_us, and breaker. It is one new field, idle: Mutex<Vec<PooledConn>>: a bounded LIFO stack guarded by a plain std::sync::Mutex (the critical section is a Vec::pop/push with no .await in it). Eviction is lazy — there is no background sweeper; take_conn discards anything past POOL_IDLE_TIMEOUT as it pops, and return_conn caps the stack at POOL_MAX_IDLE by dropping the newest connection on overflow. LIFO is deliberate: it keeps the warmest connection in play and lets the coldest age out.

What gets pooled is the whole Conn<TcpStream>, not the bare socket — so its already-allocated read buffer comes back with it and buffer reuse is free, no separate buffer-pool abstraction required. A connection is only returned if it passes a five-condition is_poolable predicate: framing was not read-until-close, the backend did not say Connection: close, the backend spoke HTTP/1.1, no I/O error occurred, and the read buffer is fully drained. Two of those conditions (backend_sent_close, backend_is_http11) are captured immediately after the response head is parsed, because the client-leg rewrite later clobbers the same fields.

Level 7 also fills two timeout holes. BACKEND_RESPONSE_TIMEOUT wraps the response-head read: a hung backend that accepts the connection and never answers used to block that task forever with no client error and no breaker signal — now it produces a 504 and mark_failure(), making a hang ejectable exactly like a refused connect. And the pool's POOL_IDLE_TIMEOUT is the keep-alive bound that stops a pooled socket outliving the backend's own patience.

The level's real lesson is a bug in the fix. A pooled connection can die between the idle-check and the first write — a genuine TOCTOU race. The first draft broke out of the retry loop on a pool hit, so a first-write failure hit a bare ? and the client got no HTTP response at all. Every per-task review passed; only a whole-branch review caught it. The fix: run the non-idempotent XFF rewrite once above the loop, serialize head_bytes once, and extend the acquire loop so a head-write failure retries like a connect failure — scoped strictly to the head, never the body.

The Big Picture

Level 7 does not add a stage to the request pipeline — it changes where the backend socket comes from and adds one deadline in the middle. The route match, the balancer pick, the header rewrites, the body streaming: all unchanged. What changes is a fork right before the dial: try the pool first (0-RTT hit), and only connect on a miss. At the far end, after the response is relayed, a fork decides whether the socket is clean enough to go back into the pool or must be closed.

The ordering is what makes it correct. The non-idempotent request rewrite runs once, above the acquire loop, producing a single serialized head_bytes. The acquire loop then picks a server, takes-or-dials a connection, and writes that same head — and a failure at any of those steps (pick, dial, or head-write) retries identically. Only once the head is safely on the wire does the exchange leave the loop and begin streaming the body, past which nothing may be retried.

Analogy: A taxi rank outside a hotel, one rank per destination (per Server). Instead of phoning for a brand-new cab on every trip (a fresh handshake), a returning cab that is still in good shape pulls to the front of the rank — LIFO — so the next passenger takes the warmest, most-recently-driven cab. Cabs that have sat too long (idle timeout) are waved off when someone finally looks; the rank only holds so many (max idle), and an extra returning cab past the cap is simply sent home rather than bumping one already parked. Crucially, a passenger who climbs into a cab whose engine has secretly died (the TOCTOU race) doesn't get stranded — the dispatcher just flags that cab dead and calls the next one, because no luggage was loaded yet.

The Per-Server LIFO Pool

One new field on an existing struct, chosen to sit exactly where the balancer already shards its state.

The pool is a field on Server (balancer.rs), the struct that already owns inflight, ewma_us, and breaker. The whole addition is:

pub struct Server {
    addr: String,
    inflight: AtomicUsize,
    ewma_us: AtomicU64,
    breaker: Breaker,
    idle: Mutex<Vec<PooledConn>>,   // NEW
}

struct PooledConn {
    conn: crate::proxy::Conn<TcpStream>,  // socket + its read buffer, together
    idle_since: Instant,
}

Why Server, not Upstream or a global pool

A pool per Server means the per-server breaker/EWMA data and the new idle pool live and die together: when a server leaves the config, its idle connections go with it — no separate cleanup pass. It also makes the lock-contention story trivial. Server is already the unit of concurrency the balancer fans requests across, so sharding the pool by server means a busy backend's pool traffic never serializes behind an unrelated backend's pool traffic: they are different mutexes entirely. A single global Mutex<HashMap<Addr, Vec<Idle>>> would force every checkout and return across every backend through one lock — the classic contention bottleneck this level uses as its worked example (see Theory).

Why std::sync::Mutex, not tokio::sync::Mutex

The critical section is a Vec::pop or Vec::push with no .await inside it. An async mutex only earns its keep when the lock is held across an await point (so the task can yield while holding it); here the lock is taken, the vector is poked, and the lock is released, all synchronously. Using tokio::sync::Mutex would buy a scheduler hop and a heavier lock for nothing. This is the same reasoning Level 6's rate limiter used for its shard locks.

LIFO, and why "warmest first" matters

The stack is last-in, first-out: return_conn pushes onto the back, take_conn pops from the back. So the connection handed out next is the one returned most recently — the warmest, least likely to have been closed by the backend's own idle timer in the meantime. The connections that sit unused drift to the bottom and are the ones the lazy idle-timeout eviction reaps. A FIFO queue would do the opposite: hand out the coldest connection first, maximizing the chance of drawing one the backend already killed. LIFO minimizes the TOCTOU window that the story below is about.

Verified: constants in balancer.rs — POOL_MAX_IDLE = 4, POOL_IDLE_TIMEOUT = Duration::from_secs(60). The runtime values are threaded through a PoolConfig { max_idle, idle_timeout } whose Default reads exactly those two constants, so the CLI flags override the same numbers the tests assert against.

Checkout & Return on the Lease

Pooling becomes two more methods on an RAII type that already exists, not a second parallel guard with its own lifecycle.

One RAII object already exists per exchange: Lease, which holds an in-flight count on the chosen server and feeds the breaker/EWMA on Drop (Level 3). Level 7 adds two methods to it — take_conn and return_conn — rather than inventing a second guard type with a parallel lifecycle to reason about. The Lease already borrows the Server for its whole lifetime, so it is the natural handle for that server's pool.

take_conn: pop the warmest live connection, discard the stale

Checkout pops from the back (LIFO) and skips anything older than the idle timeout, looping until it finds a live connection or the stack empties:

fn take_conn(&self) -> Option<Conn<TcpStream>> {
    let mut guard = self.idle.lock().unwrap();
    let now = Instant::now();
    while let Some(pc) = guard.pop() {
        if now.saturating_duration_since(pc.idle_since) < self.pool.idle_timeout {
            return Some(pc.conn);
        }
        // else: stale, `pc` drops here (closes the socket), loop continues.
    }
    None
}

A stale entry costs nothing until something actually looks — the same "nobody pays until somebody looks" principle as Level 6's lazy token-bucket refill. Note saturating_duration_since rather than elapsed(): it is monotonic-clock-safe and cannot panic on a backwards clock reading.

return_conn: bounded at return, drop the newest on overflow

fn return_conn(&self, conn: Conn<TcpStream>) {
    let mut guard = self.idle.lock().unwrap();
    if guard.len() < self.pool.max_idle {
        guard.push(PooledConn { conn, idle_since: Instant::now() });
    }
    // else: `conn` is dropped here (closes the socket) — pool stays capped.
}

The cap is enforced at return, not at checkout, and on overflow it drops the new connection rather than evicting an existing one. Why prefer the residents? There is no reason to favor a fresh-idle connection over ones already parked — they are equally valid, and evicting a resident would mean closing a socket you were about to keep only to keep one you were about to close. Dropping the newcomer is strictly less work and keeps the pool's contents stable.

These methods are private on Server; the public Lease::take_conn/Lease::return_conn forward to them. That keeps the pool's internals encapsulated behind the lease the caller already holds.

The Five-Condition is_poolable Predicate

Derived from state serve_one already computes for the client-leg keep-alive decision — plus one condition the client leg never needs.

A connection is eligible to go back into the pool if and only if all five hold. It is a pure, synchronous function in proxy.rs taking plain values, so it is trivially unit-tested (six tests: each condition independently forces false, all-true forces true):

fn is_poolable(
    resp_framing: BodyFraming,
    backend_sent_close: bool,
    backend_is_http11: bool,
    exchange_errored: bool,
    buffer_empty: bool,
) -> bool {
    if resp_framing == BodyFraming::UntilClose { return false; }  // 1
    if backend_sent_close                       { return false; }  // 2
    if !backend_is_http11                       { return false; }  // 3
    if exchange_errored                         { return false; }  // 4
    buffer_empty                                                    // 5
}
#ConditionWhy it disqualifies
1framing is not UntilCloseUntilClose means "read until the backend closes the socket" — the backend itself told us the connection is single-use.
2backend did not send Connection: closeAn explicit refusal to persist. We asked for keep-alive; the backend is free to decline.
3backend spoke HTTP/1.1An HTTP/1.0 backend doesn't support persistent connections at all by default.
4no I/O error in the exchangeAn errored socket is in an unknown state; reusing it courts a desync.
5read buffer is fully drainedThe genuinely new one — see below.

Conditions 1–4 mirror the client-leg keep-alive check applied symmetrically to the backend leg. There is no new state to track for them — resp_framing, the response headers, and resp.version are all in hand when the response is relayed, and error-freedom is structural (see the error model): only the one success path that reaches the poolability decision with no error ever calls return_conn.

Condition 5: the buffer must be empty, and why only the backend leg needs it

Condition 5 — Conn::buffer_is_empty(), a one-line read of the private filled == 0 — has no client-leg analogue. On the client leg, extra buffered bytes after a message correctly mean the next pipelined request and must be preserved (Level 1's preserves_pipelined_bytes_after_head). On the backend leg there is no pipelining: this proxy sends one request per checkout and waits for its response before sending another. So any bytes still sitting in the buffer after the body was fully consumed are not a next message — they are either backend misbehavior or a framing-accounting bug, and pooling them forward would hand the next checkout's read_head a mix of stale and fresh bytes: the exact connection-desync failure mode Level 1 closed for the client leg, now on the backend leg.

The ordering trap: capture two fields before the client-leg rewrite

This is the subtle part, and the whole reason is_poolable takes plain bools instead of the response head. Later in serve_one, resp.headers passes through strip_hop_by_hop (which strips Connection) and the client-leg framing block pushes a new Connection header describing what we tell the client; resp.version gets force-set to Http11 for the client leg regardless of what the backend actually spoke. By the time the pooling decision happens, both fields describe the client leg, not the backend's original response. So they are captured the instant the head is parsed:

let resp_framing = http::response_body_framing(&method, &resp)?;
// captured NOW, before any client-leg rewrite clobbers resp.headers / resp.version:
let backend_sent_close = http::header(&resp.headers, "connection")
    .map(|v| v.split(',').any(|t| t.trim().eq_ignore_ascii_case("close")))
    .unwrap_or(false);
let backend_is_http11 = resp.version == Version::Http11;

Making is_poolable take bools rather than &Response is defensive by design: it makes it impossible to read these fields late from inside the function — the caller is forced to capture the right values at the right time, at the call site. Every implementer and reviewer in this level's build re-verified this ordering by tracing the actual code, not trusting the comment.

Watch out: the backend leg now asks for Connection: keep-alive (the head-rewrite pushes it) instead of close — pooling can never find a live connection if every request tells the backend to hang up. But that invitation alone does not decide poolability: condition 2 still independently checks the backend's own response Connection header, because a backend is free to ignore the invitation and close anyway.

The Backend Response Timeout

The one genuinely new behavior of the level: a hung backend becomes ejectable, not eternal.

Before Level 7, a backend that accepted the TCP connection and then never responded was a black hole: backend.read_head() awaited forever, blocking that connection task with no client-visible error and no signal to the circuit breaker. The backend looked healthy to the balancer (it accepted the connect!) while silently swallowing requests. BACKEND_RESPONSE_TIMEOUT closes that gap, following the exact tokio::time::timeout(DURATION, future) pattern HEAD_READ_TIMEOUT and BACKEND_CONNECT_TIMEOUT already use:

let resp_bytes = match tokio::time::timeout(backend_timeout, backend.read_head()).await {
    Err(_) => {
        // Hung backend: connect succeeded and the request was sent, so this
        // is as real a failure as a refused connect — indict the server.
        lease.mark_failure();
        crate::warn!("[{peer}] backend {} response timed out", lease.addr());
        respond_error(client, 504, "Gateway Timeout").await?;
        metrics.record_request(m_id, 504, t_start.elapsed());
        return Ok(false);
    }
    // ... Ok(Ok(None)) => backend closed before responding; Ok(Ok(Some)) => head in hand
};

On expiry the client gets a 504 Gateway Timeout and the lease fires mark_failure(), which feeds the passive breaker exactly like a refused connect. So a backend that "hangs" now becomes ejectable the same way a backend that "refuses" already was — to the breaker, a backend that never answers looks like a backend that never connects.

The default is 30s (DEFAULT_BACKEND_RESPONSE_TIMEOUT = Duration::from_secs(30)), tunable via --backend-timeout. It bounds only time-to-first-byte — the response head read — not total body-transfer time. That is deliberate: total transfer time is size- and route-dependent and stays unbounded, matching the KB's framing of this timeout as protecting against hung application code up to first byte, not against slow-but-alive transfers. A separate body-streaming deadline would penalize a legitimately large download.

Measured: against a backend that accepts and never answers, with --backend-timeout 2s, a 504 came back in ~2.08s, and the breaker ejected the backend on the very next request — a repeat returned an immediate 502 in 0.04s instead of hanging again. That confirms mark_failure() on timeout genuinely feeds the same passive breaker feed a refused connect already used.

Serialize Once, Retry Only the Write

Pooling introduces no new failure category — a pooled connection is just an alternate source of a TcpStream, fed into the same retry machinery. But making that true required restructuring the loop.

The request-head rewrite (route.rules.apply_request — appends X-Forwarded-For, sets the host, adds Connection: keep-alive, etc.) is non-idempotent: run it twice and you double-append XFF. So it must run once. The connect, by contrast, must be retryable — a refused backend should fall to another server. Level 7 resolves the tension by splitting the two: the rewrite and serialization happen once, above the loop; the loop then re-uses the identical bytes on every attempt.

// ONCE, above the loop — the non-idempotent rewrite:
req.headers.push(("Connection".to_string(), "keep-alive".to_string()));
// ... other apply_request rewrites (X-Forwarded-For, host, ...) ...
let head_bytes = http::write_request_head(&req);   // the single serialization

let (mut lease, mut backend, from_pool) = loop {
    let mut lease = upstream.pick(peer.ip()) /* or 502 if no healthy server */;
    // acquire: pooled first (0-RTT), else dial fresh
    let (mut conn, from_pool) = if let Some(conn) = lease.take_conn() {
        (conn, true)                                   // POOL HIT: skip connect
    } else {
        match timeout(BACKEND_CONNECT_TIMEOUT, TcpStream::connect(&addr)).await {
            Ok(Ok(s))          => { s.set_nodelay(true); (Conn::new(s), false) }
            Ok(Err(_)) | Err(_) => { lease.mark_failure(); /* retry, or 502/504 */ }
        }
    };
    // write the SAME pre-serialized head; a failure here is treated
    // EXACTLY like a failed connect:
    match conn.write_all(&head_bytes).await {
        Ok(())  => break (lease, conn, from_pool),
        Err(e)  => { lease.mark_failure(); /* retry if idempotent, else 502 */ }
    }
};

Retry is gated on three conditions, all required: attempts remain (MAX_RETRIES = 2, one shared budget — no separate pooled-retry category), the method is idempotent (safe to replay), and no request-body byte has left yet. That last point is the hard boundary: the moment the loop exits and copy_body_limited starts streaming, a failure is no longer replayable — part of a possibly non-idempotent request is already committed to a backend and can never be safely replayed. Failures past that point feed the breaker and surface to the client.

Error-freedom is structural, not checked

This structure is what makes is_poolable's condition 4 (no I/O error) true by construction. Only the one success path that reaches the poolability decision with no error ever calls return_conn. Every fallible step between acquire and that decision returns early via ? or an explicit error branch — a timed-out or errored connection is never even a candidate for pooling. "A timed-out backend connection must be dropped, not pooled" becomes true because there is no code path that pools one, not because a separate check rejects it.

The TOCTOU Bug That Hid Behind Every Passing Review

This is the story of the level. Every per-task review passed. The bug was invisible to all of them because it lived in the interaction between two tasks, not inside either one.

A pool hit hands back a socket that looked alive at checkout — it passed the idle-age check. But the backend can close it in the window between that check and our first write. This is a genuine time-of-check to time-of-use race, inherent to any connection pool: the socket is fine when you inspect it and dead when you use it. A fresh-connect miss can never hit this; only a pool hit can.

What the first draft did wrong

The original code structured the retry loop around TcpStream::connect only. A pool hit broke out of that loop immediately — it had a connection, why loop? The first write then happened after the loop, and its failure hit a bare ?. That ? propagated the io::Error straight past the already-exited retry logic to handle_client's generic handler — which just logs and drops the connection. The result for a dead-pooled-connection write failure was no HTTP response at all: not a 502, not a 504, nothing. For a case that should have retried on another server exactly like a failed connect already did.

Why every per-task review passed: each of the six tasks was reviewed on its own diff, and each was correct in isolation. The pool code (Task 1) was right. The wiring (Task 5) was right. The retry loop (pre-existing) was right. The bug only existed in the seam: pool-hit-breaks-loop composed with first-write-hits-bare-? composed with the generic handler dropping silently. A reviewer who only ever sees one task's diff at a time is structurally blind to it. It took a whole-branch review — the most capable model reading all six task-diffs as one composed feature — to see it, and the finding was confirmed by re-reading the actual source before dispatching a fix, not by trusting the reviewer's report.

The fix, and its exact scope

The fix is the serialize-once structure above: extend the acquire loop so the head-write lives inside it, and a write failure on either a pooled or a freshly-dialed connection is handled identically to a connect failure — mark_failure, log, retry-or-502. The scope is surgical: retry covers only the head-write, never body-streaming or flush, because a body byte reaching a backend commits a possibly non-idempotent side effect that can never be replayed. The non-idempotent rewrite was moved above the loop precisely so the identical head_bytes could be re-written on retry without double-appending X-Forwarded-For.

Live-verified with a poisoned socket: a pooled connection was deliberately killed with a TCP RST (via SO_LINGER). An idempotent GET drawing that dead connection produced a write failed log line and a transparent retry to a healthy backend — the client saw 200. A non-idempotent POST in the same situation correctly got 502 with no replay. The review also swept up four stale "dead until Task 5" comments left behind when Task 5 removed the #[allow(dead_code)] attributes they were justifying. Scoped re-review verdict: ADDRESSED, no new findings.

The lesson, recorded in PROGRESS.md as the explicit reason a whole-branch review is worth its cost: cross-task composition bugs are structurally invisible to a reviewer who only ever sees one task's diff at a time.

Theory, Documented Not Built

Four of Build.md's Level 7 items are the kind the KB frames as explanation, not code — handled the same way Levels 5/6 handled their explain-only sections.

Explained

Async worker model

Level 1 already built task-per-connection on Tokio. Level 7 documents why it sidesteps C10K — no per-connection thread, no per-connection stack-sized memory cost — versus Nginx's process+epoll model, and why Rust+Tokio gives event-driven behavior with task-shaped ergonomics instead of raw callback/epoll code. No model change.

Explained

Zero-copy (splice/sendfile)

Explained with the KB's own caveat: an L7 proxy mostly can't use it for headers (it must inspect them), and it needs measurement first. No unsafe syscalls added — there is no benchmark yet showing Conn::copy_body_to is the bottleneck, and building for an unmeasured problem is the "measure, don't guess" mistake.

Worked example

Lock contention

Explained using this level's own pool as the example rather than an abstract discussion: sharding per-Server versus one global Mutex<HashMap<Addr, Vec<Idle>>> is exactly the "shard the state" lesson — a busy backend's pool traffic never serializes behind an unrelated backend's, because they're different mutexes.

Verified, not built

Request pipelining

Conn::read_head's buffering already carries bytes past one request's boundary into the next (Level 1's preserves_pipelined_bytes_after_head). Level 7 re-verified this holds with pooling active — a pooled connection's buffer must not leak a prior exchange's bytes (condition 5). No backend-leg pipelining exists and none was added.

Buffer reuse is likewise a consequence of the design, not separate work: because PooledConn holds a whole Conn<TcpStream> — the struct that already owns the read buffer — reusing the connection reuses the buffer automatically. The per-connection memory model shifts from requests × buffers under sustained keep-alive load toward min(pool occupancy, historical concurrency) × buffers: fewer allocations per request, not a smaller peak (the pool is still bounded per server by POOL_MAX_IDLE, so worst-case memory is unchanged). A standalone buffer-pool abstraction would have had to reimplement exactly this life-cycle by hand.

How the Industry Does It

Backend connection reuse is table stakes for every production proxy; the interesting part is which trade-offs each took. Ferrum is a teaching build — a per-Server Vec with a single mutex is deliberately crude next to a decade-hardened keep-alive subsystem. As of the mid-2020s:

The honest contrasts:

  • Ours is a single Vec behind one mutex per server. HAProxy's http-reuse has four graded modes and tracks per-server pool health with far more nuance; Envoy's cluster connection pools integrate with its circuit breakers and support HTTP/2 multiplexing, where one connection carries many concurrent streams. Ferrum sends exactly one request per checkout and waits — no multiplexing at all.
  • Lazy eviction is a genuine simplification, not just a shortcut. The incumbents run active idle sweeps; Ferrum pays nothing until a take_conn walks past a stale entry. For a teaching build with modest pools that is the right trade — but at very large idle-pool sizes an active sweep reclaims sockets sooner, which matters for the backend's own connection budget.
  • The dead-connection-on-reuse handling is the one place Ferrum is genuinely careful. HAProxy's http-reuse safe makes the same distinction Ferrum landed on the hard way: only idempotent requests may be transparently retried on a connection that turns out dead. Ferrum arrived there via a whole-branch review of a real silent-failure bug — the incumbents encoded it as a config knob years ago.
  • HTTP/1.1-only is the ceiling. Every incumbent multiplexes over HTTP/2 (or /3) to backends, amortizing far more setup than keep-alive alone. Ferrum's pool is the HTTP/1.1 answer — the right first lesson, and explicitly not the last word.

Glossary

Connection pool — a cache of live backend sockets kept open between requests so the next request skips the TCP handshake. Here: a bounded LIFO Vec per Server.

LIFO (last-in, first-out) — the pool hands out the most-recently-returned connection first, keeping the warmest socket in play and letting cold ones age out; minimizes the reuse-a-dead-socket window.

Lazy eviction — no background sweeper; a stale connection is discarded only when take_conn walks past it. "Nobody pays until somebody looks."

Poolability — the five-condition predicate deciding whether a finished exchange's connection may be reused: not UntilClose, no backend close, HTTP/1.1, no error, drained buffer.

Keep-alive — HTTP/1.1's persistent-connection mechanism; the backend leg now asks for it (Connection: keep-alive) so a socket becomes a pooling candidate.

Idempotent method — a request safe to replay (GET, HEAD, PUT, DELETE…); only these may be retried after a connect or head-write failure. POST is not.

TOCTOU — time-of-check to time-of-use; the race where a pooled socket passes the idle-age check and then turns out dead on the first write. The level's central bug.

Time-to-first-byte — the interval from sending the request to receiving the first byte of the response head; the only thing BACKEND_RESPONSE_TIMEOUT bounds.

Conn<S> — the connection wrapper owning a stream and its read buffer; pooling the whole Conn (not the raw socket) is what gives buffer reuse for free.

RAII / Lease — tie resource release to scope end; Lease already fed inflight/breaker on Drop, and now carries the two pool methods.

Whole-branch review — reviewing all task diffs together as one composed feature; the only review that could catch this level's cross-task composition bug.
