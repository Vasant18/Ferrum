Executive Summary

Level 10 makes Ferrum observable: it can now tell you not just what happened to one request, but what is happening to all of them, right now, versus an hour ago — the difference between an event stream and an aggregate.

Three pillars, proxy edition. Logs — one structured JSON line per request on stdout (observe.rs), plus a leveled human-readable error log on stderr (logging.rs); two streams because they have two audiences and must be redirectable independently. Metrics — a hand-rolled registry (metrics.rs) of AtomicU64 counters, AtomicI64 gauges, and fixed-bucket histograms, exposed in Prometheus text format. Traces — per-stage timings (route, connect, TTFB) stamped into ReqCtx and carried by the request ID Level 6 already propagates. Ferrum is a single hop, so W3C traceparent propagation was deliberately left out: the stage deltas answer the 3 a.m. question without a second instrumented service to trace into.

The design's first decision was zero new dependencies. The metrics and tracing crates would turn every lesson of this level into invisible config, and unlike Level 8's crypto nothing here is dangerous to hand-roll — a wrong histogram bucket is a wrong number on a graph, not a security hole. The registry follows the Level 7 hot-path rule applied to our own instrumentation: no mutex, no allocation at record time. Counters are labeled by status class (code="2xx") and pre-resolved UpstreamId, never by path — a path label is an attacker-controlled cardinality bomb. Histograms store each observation in exactly one of nine buckets and defer the cumulative le arithmetic to scrape time, because scrapes are rare and requests are not. The duration clock starts after read_head returns so keep-alive idle time never pollutes the metric, and requests_total is recorded on every exit path. /metrics and /health live on a separate admin listener that is off by default — /metrics leaks reconnaissance gold, so exposing it must be a deliberate act. 230 unit tests (214 from Level 8 kept green, +16) and a full live verification back it.

The Big Picture

Observability is not a stage in the pipeline — it is a cross-cutting concern that taps every stage. Timings are stamped along the request path; the access log fires at the very end; metrics are recorded at every exit; and a wholly separate socket serves the aggregates.

The clock for a request starts after the head is read (so a keep-alive client's think-time is excluded) and stamps land at route-matched, backend-in-hand, and response-head-parsed. When the exchange completes — after the last body byte flushes — serve_one records the counter and histogram, and the outermost middleware writes the JSON line. Meanwhile a second Tokio task owns the admin listener, reading the same shared Arc<Metrics> to render /metrics on demand.

Analogy: the access log is a security camera — one frame per person who walks through the door, timestamped, forever queryable ("who came in at 3:04?"). Metrics are the turnstile counter on the wall — it can't tell you who, but it tells you "we're at 900/min, up from 200 an hour ago" without replaying the tape. You need both: you can't reconstruct a percentile from footage fast enough at 3 a.m., and you can't identify a suspect from a turnstile.
Why "the three pillars". Logs, metrics, and traces are the industry's standard decomposition of observability. Logs are discrete events (high detail, expensive to keep). Metrics are numeric aggregates over time (cheap, low detail). Traces follow one request across its stages (or across services). Ferrum implements all three, but scoped to a single hop — the trace is per-stage timing on one machine, not a distributed span tree.

Metrics: atomics & fixed buckets

metrics.rs

Instrumentation runs on every request, on the hot path, concurrently on all worker threads. So the same discipline as the Level 7 connection pool: no mutex, no allocation at record time. Every instrument is an atomic, and every label set is resolved to a pre-built slot at startup.

The registry is a single Metrics struct built once in main and shared as Arc<Metrics> — the exact same lifetime and sharing story as Arc<RouteTable>. Like the route table, it is read-shaped after startup: the structure never mutates, only the atomic values inside it move.

Three instrument types, and why there is no fourth

Counter

AtomicU64, only goes up

What it is: a monotonically increasing count. requests_total is the canonical one. Resets to zero on restart, which Prometheus detects by seeing the value drop.

Why: rates are derived at query time (rate(requests_total[5m])), never recorded — baking a window size into the recorded value would fix it forever.

Gauge

AtomicI64, moves both ways

What it is: a value that can rise and fall. active_connections is ours. The only instrument allowed to decrease.

Why: some quantities are levels, not totals — how many connections are open right now, not how many were ever opened.

Histogram

9 atomics, pre-declared buckets

What it is: counts of observations falling into fixed latency buckets. Percentiles are computed at query time from bucket counts.

Why: the alternative — storing raw samples — costs memory per request; buckets cost a fixed 9 atomics per series total. That trade is the whole reason Prometheus histograms look the way they do.

Relaxed ordering, and why an increment is never lost

Every increment uses Ordering::Relaxed. That decision is worth defending, because the instinct under concurrency is to reach for SeqCst. Relaxed is correct here for two separate reasons:

  • No lost increments. fetch_add is a read-modify-write atomic. The hardware guarantees the read, the add, and the write happen as one indivisible operation — two threads bumping the same counter cannot interleave and clobber each other, regardless of memory ordering. Ordering governs how other memory operations are seen relative to this one; it does not govern the atomicity of the RMW itself. This is the load-bearing claim for every counter in the file, so it is tested the same way Level 6 tested the sharded rate limiter: 8 threads × 10,000 increments, assert the total is exactly 80,000.
  • Nothing to order. A metric increment has no happens-before relationship to protect. Nobody's read of one counter is supposed to establish anything about another. The stronger orderings buy synchronization guarantees that would only cost cache-line traffic for a benefit no reader here wants.
What Relaxed does NOT give you, and why that's fine. A scrape can observe counter A's increment from a request before counter B's increment from the same request — the two writes are not ordered relative to each other. Prometheus tolerates that skew by design: every scrape is already a torn snapshot of a moving system. You are never promised that two counters are consistent at an instant; you are promised each one is individually correct. For metrics, that is exactly enough.

Pre-resolved UpstreamId: the string compare happens once

A naive registry would take an upstream name at every record call and look it up. Ferrum instead resolves the name to an index once per request, right after routing picks the upstream, and records through that index from then on:

// A resolved upstream label: an index, not a string.
#[derive(Clone, Copy)]
pub struct UpstreamId(Option<usize>);

// Called ONCE per request in serve_one, after routing.
pub fn upstream_id(&self, name: &str) -> UpstreamId {
    UpstreamId(self.upstreams.iter().position(|s| s.name == name))
}

The lookup is a linear scan, not a HashMap, on purpose: a deployment has a handful of upstreams, so a hash buys nothing but a hash computation per lookup, and the lookup already happens only once. None is the upstream="-" slot for requests that never routed (431/413/400 pre-route, 404s, rejections). Kept separate from the upstream Vec so a config with an upstream literally named "-" can't collide — the type doesn't depend on the router's manners.

Analogy: UpstreamId is a coat-check ticket. You hand over your name once at the door (the string compare), get a numbered stub, and every later interaction quotes the number. The cloakroom never re-reads your name; it just goes to slot 4.

The Cardinality Bomb

the load-bearing rule

The single most important rule in the metrics file: labels come from our config, never from the request. Break it and you have handed an attacker a memory-exhaustion primitive dressed up as a dashboard.

Every distinct label combination is its own series — its own atomics in our registry, its own time series in Prometheus, its own row in the collector's index. Labels multiply. This is why requests_total is labeled by status class (code="2xx", five possible values) times upstream (declared on the CLI, few) — bounded and useful. The cardinality is 5 per upstream, honest to Prometheus practice.

What goes wrong if you label by path

Suppose you labeled by raw path instead. The path is attacker-controlled. A trivial loop —

while true; do curl http://ferrum/$(uuidgen); done

— makes every request a brand-new label value, so every request allocates a brand-new series that never goes away. Mechanically:

  • In our memory: the registry would have to allocate a new set of atomics per unique path, so a `Vec`/map growing without bound — a slow-motion OOM that the attacker controls the rate of.
  • In Prometheus: the collector ingests every series and keeps it in its head index and on disk. Cardinality explosion is the number-one way people take down their own Prometheus; a proxy that feeds it unbounded path labels is a loaded gun pointed at the monitoring system.
Danger: raw status code (dozens of values) is already a mild version of this; raw path (unbounded) is the full bomb. The fix is not "sanitize the path" — it is a category rule: a label's value set must be fixed at config time. Status class has 5 values. Upstream names are declared. Rejector names are a compile-time array. Nothing in a label ever comes from bytes the client sent. Paths belong in the log, where each is one line that ages out, not one series that lives forever.

The same reasoning fixes the rejector labels. rejected_total{by="..."} uses a static five-element array — ["ratelimit", "auth", "authz", "request-id", "other"] — and a future middleware whose author forgets to extend the list lands in other rather than inventing a new series. Visible in the metrics, not silently dropped, and still bounded.

Histograms: bucket at record, cumulate at scrape

metrics.rs · Histogram

A histogram here is 9 AtomicU64s per series. Each observation increments exactly one of them. The cumulative buckets Prometheus requires are computed later, at scrape time — because scrapes happen every ~15 s and observations happen thousands of times a second, so you do the O(buckets) work on the rare path.

The buckets are the schema

BUCKET_BOUNDS = [0.001, 0.005, 0.01, 0.05, 0.1, 0.5, 1.0, 5.0] seconds  (+ implicit +Inf)

Eight finite upper bounds plus an implicit +Inf, chosen to bracket what a local reverse proxy actually sees: sub-millisecond pool hits up through multi-second backend hangs. Level 7's backend response timeout is 10 s, so anything past 5 s lands in +Inf and is de facto "timed out or nearly." The bounds are a const array fixed at compile time — they are part of the schema, and changing them mid-flight would make cumulative counts incomparable across scrapes.

Record: one bucket, a linear scan

pub fn observe(&self, d: Duration) {
    let secs = d.as_secs_f64();
    match BUCKET_BOUNDS.iter().position(|&b| secs <= b) {
        Some(i) => self.buckets[i].fetch_add(1, Ordering::Relaxed),
        None    => self.inf.fetch_add(1, Ordering::Relaxed),
    };
    self.sum_micros.fetch_add(d.as_micros() as u64, Ordering::Relaxed);
    self.count.fetch_add(1, Ordering::Relaxed);
}

A linear scan over 8 comparisons and 3 atomic adds. A binary search over 8 elements would be slower than the scan it replaces (branch misprediction and setup cost dwarf 8 compares). Note secs <= b: the buckets use the le ("less than or equal") convention, so a value exactly on a boundary lands in that bucket. There is a test for it (a 1 ms observation lands in the 0.001 bucket, a 1001 µs observation in the next).

Why sum is integer micros. The running sum is stored as an AtomicU64 of microseconds, not a float of seconds, because there is no atomic f64 add on the platforms Ferrum targets — you would need a compare-and-swap loop. Integer micros sidestep that entirely, and a proxy that needs sub-microsecond precision in its metrics has mistaken itself for a benchmark. At scrape time the micros are divided by 1e6 back into the seconds the format wants.

Scrape: the cumulative walk

Prometheus histogram buckets are cumulative: the le="0.05" bucket must report everything ≤ 0.05, i.e. the sum of all lower buckets too. But storing them cumulatively would mean every observation increments several atomics (all buckets ≥ the one it fell in) — turning a 1-atomic write into an N-atomic write on the hot path. So storage is non-cumulative (one bucket per observation) and the cumulation happens in snapshot(), called only by the renderer:

fn snapshot(&self) -> ([u64; 9], f64, u64) {
    let mut cumulative = [0u64; 9];
    let mut running = 0u64;
    for (i, b) in self.buckets.iter().enumerate() {
        running += b.load(Ordering::Relaxed);   // add THIS bucket's count
        cumulative[i] = running;                // record the running total
    }
    cumulative[8] = running + self.inf.load(Ordering::Relaxed);
    // ... sum / 1e6, count
}

The rendered le="+Inf" line equals _count by construction — both come from the same bucket walk — which is exactly the invariant Prometheus requires. Never-touched series are elided from render() rather than emitted as rows of zeros: a scrape full of zeros for 5 classes × N upstreams is noise, and Prometheus treats an absent series and a zero series identically for rate().

Watch out — why an average lies. Suppose 99 requests take 1 ms and one takes 4 seconds. The average is ~40 ms, a number that describes not a single real request. The histogram tells the truth: 99 observations in the 0.001 bucket, one in +Inf (past the 5.0 bound). A p99 latency query reads that immediately — "your slow tail is multi-second," the thing the average smeared into a comfortable-looking middle. Percentiles need the distribution; a counter and a sum can only give you the mean.

Leveled Logging: check before you format

logging.rs

Two output streams, two audiences. The JSON access log (stdout) is for machines; the error log (stderr) is for humans mid-incident. They must be redirectable independently — 2>errors.log — which is the entire reason the split exists.

Before this level, Ferrum's request path printed unconditionally: every request cost several println!s of routing, rewrite, and pick diagnostics. Those lines were priceless while building Levels 2–8 and are pure noise in operation — the classic reason log levels exist. They are now debug!, silent by default, and one --log-level debug brings them all back.

The macro checks the level BEFORE evaluating its arguments

This is the whole performance story of a log level, and it is easy to get wrong. A suppressed debug! must cost one atomic load and a compare — not a format! allocation that is immediately thrown away. The macro achieves this by gating on enabled() before touching format_args!:

macro_rules! debug {
    ($($arg:tt)*) => {
        if $crate::logging::enabled($crate::logging::Level::Debug) {
            $crate::logging::emit(
                $crate::logging::Level::Debug,
                format_args!($($arg)*),   // only evaluated if enabled() passed
            );
        }
    };
}

Because the format_args! expansion sits inside the if, the compiler never evaluates the arguments when the level is off. Move the check inside emit instead and it is too late: the caller has already formatted its arguments to pass them in. The gate must be textual, at the call site — which is exactly why it is a macro and not a function. enabled() itself is one relaxed atomic load:

pub fn enabled(l: Level) -> bool {
    (l as u8) <= LEVEL.load(Ordering::Relaxed)
}

The level lives in a global AtomicU8, set once in main before any traffic. A global — not a threaded &Logger — because a log call's entire value is that it can appear anywhere: inside a Drop impl, in the balancer's breaker transitions, three layers deep in a parser. Threading a logger through every one of those signatures would tax every function in the program for the benefit of none. Relaxed is safe because the level is write-once-at-boot; no reader orders anything against it. This "do the work only on the rare path" principle is the same one the histogram uses for cumulation.

Hand-rolled RFC 3339 timestamps

Both logs stamp wall-clock time as RFC 3339 UTC with millisecond precision (2026-08-25T09:14:02.417Z). Rather than pull in chrono, Ferrum hand-rolls the calendar math — about 15 lines — using Howard Hinnant's civil_from_days, the same days-to-civil-date algorithm inside every date library:

fn civil_from_days(z: i64) -> (i64, u32, u32) {
    let z = z + 719_468;
    let era = z.div_euclid(146_097);
    let doe = z.rem_euclid(146_097);                 // day of 400-year era
    let yoe = (doe - doe/1460 + doe/36_524 - doe/146_096) / 365;
    let y = yoe + era * 400;
    let doy = doe - (365*yoe + yoe/4 - yoe/100);
    let mp = (5*doy + 2) / 153;                       // shifted-era month ramp
    let d = (doy - (153*mp + 2)/5 + 1) as u32;
    let m = if mp < 10 { mp + 3 } else { mp - 9 } as u32;
    (if m <= 2 { y + 1 } else { y }, m, d)
}

The trick is the "shifted era": move the year's start to March so the leap day lands at the end of the counting year, which makes the month-length pattern a clean linear ramp (153m + 2) / 5 instead of a lookup table with a February special case. It is UTC-only — no timezone table, no DST — which is precisely why logs are written in UTC in the first place. Verified against Python at four fixed points including the epoch, a leap-year day (2024-02-29), and a century non-leap boundary (2100-03-01) that only the era arithmetic gets right.

JSON Access Log & Stage Timings

observe.rs · proxy.rs

One JSON object per line, emitted by the same outermost-middleware on_response that used to write a key=value line. The format change buys machine queryability — and opens a new attack surface that a hand-rolled escaper closes.

The line

{"ts":"2026-08-24T10:15:42.123Z","id":"a1b2-42","peer":"127.0.0.1:55123",
 "method":"GET","target":"/api/users","status":200,"dur_ms":12.4,
 "route_ms":0.0,"connect_ms":1.2,"ttfb_ms":10.8,"upstream":"api",
 "backend":"127.0.0.1:9001","user":"-","pooled":true,"cache":"HIT",
 "waf_score":null,"rejected_by":null}

What structure buys you: jq 'select(.status>=500)' replaces regex archaeology; select(.status==401), group-by-upstream, percentile-of-dur_ms — all trivial. The prose version made every one of those a fragile field-position hack. --log-plain keeps the old human-readable line for eyeball debugging.

Log injection, upgraded: now it forges FIELDS

The request target is attacker-controlled, and Level 6 already taught that an unescaped CR/LF forges a whole log line. The format change raises the stakes: in a JSON log an unescaped " doesn't just forge a line — it breaks out of the string and forges fields. Picture a target of:

/x","status":200,"forged":"y

A naive logger that string-interpolates that into "target":"..." produces a JSON object with an attacker-chosen status:200 and a forged field — poisoning every downstream query that trusts the log. Worse, a raw control byte makes the whole line unparseable, which silently drops it from every jq query — an attacker's favorite outcome, because the evidence of the attack disappears. The RFC 8259 escaper runs on every dynamic value (keys are static, so only values pass through it):

pub fn json_escape(s: &str) -> String {
    // " → \"   \ → \\   \n \r \t → escapes   c < 0x20 → \u00XX
    // UTF-8 passes through untouched (JSON strings are Unicode).
}

The hostile target above escapes to /x\",\"status\":200,\"forged\":\"y — one harmless string value, fields intact. There is a direct test for exactly this field-forging payload.

Stage timings: route / connect / TTFB, and null-vs-0.0

Deltas from the exchange clock tell you where slowness lives. proxy.rs stamps Instants into ReqCtx at the points it already logs: t_route (parse + route cost), t_connect (backend dialed or pool hit), t_first_byte (backend response head in hand — the honest, observable TTFB from where we sit, since the read returns whole heads not bytes). The access log renders each as milliseconds via opt_ms:

fn opt_ms(d: Option<Duration>) -> String {
    match d {
        Some(d) => format!("{:.1}", d.as_secs_f64() * 1000.0),
        None    => "null".to_string(),   // never reached this stage
    }
}
Watch out — null is not 0.0, and neither is -1. A request rejected by auth never routes, so its ttfb_ms is null — "this stage did not happen." But 0.0 is a legitimate measurement: a pooled connection really can connect in ~0 ms. Collapsing "didn't happen" into 0 would tell your dashboard that auth-rejected requests have a blazing-fast backend connect. And a sentinel like -1 is worse — it is a number, so it silently poisons any average, sum, or percentile that forgot to filter it. null is the only value that aggregations correctly ignore. This is the load-bearing distinction, not pedantry.

The clock starts after read_head — keep-alive idle must not pollute

The exchange clock (t_start) is stamped after read_head returns, not at the top of serve_one:

// read_head above spends most of its life idle on a keep-alive
// connection, waiting for the client to DECIDE to send another request.
let t_start = std::time::Instant::now();
let mut req = http::parse_request_head(&head_bytes)?;

On a keep-alive connection, read_head blocks waiting for the client to decide to send its next request — that think-time can be seconds and is not Ferrum's latency. Folding it into dur_ms would make every keep-alive connection look pathologically slow and mask real regressions. The gap the placement deliberately excludes (the time for one head's bytes to trickle in once the client has started sending) is bounded by HEAD_READ_TIMEOUT and belongs to the client. Durations are monotonic (Instant); ts is wall-clock (SystemTime). Never mix the two clocks' jobs — wall time for cross-system correlation, monotonic for arithmetic.

The recording discipline: count every exit

record_request is called at every exit path, so requests_total means "the client got an answer": 431/413/400 pre-route (as upstream="-"), 404, middleware rejections, 502/504 connect failures, and the one success-path record placed after client.flush() — the last body byte on the wire.

Why after the flush? A duration that stopped at the response head would hide the transfer time of a slow client or a huge body — the request would look fast while the client waited seconds for bytes. Recording after the final flush captures the honest end-to-end latency. And rejections are double-counted deliberately — into both requests_total and rejected_total{by=...} — because "how many 429s did clients see?" and "which layer is rejecting?" are two different questions; folding them into one series would answer neither cleanly. Requests that die mid-exchange via ? (a broken socket) are NOT in requests_total — that series means "the client got an answer," and the error log plus the breaker carry the deaths.

The Admin Plane: a different socket

admin.rs

/metrics and /health live on their own listener (--admin ADDR, no default; the docs recommend 127.0.0.1:9100). Enabling it is an explicit operator choice — because /metrics is reconnaissance gold.

Three reasons it's a separate socket, not reserved paths on :8080

  1. It leaks recon. /metrics exposes route names, backend addresses, and error rates. The main listener faces the internet; binding the admin plane to its own address (localhost by default) makes exposure a deliberate act, not an accident of routing.
  2. No shadowing. A backend that legitimately serves its own /metrics is never intercepted or hidden by the proxy — the main listener's routing is completely untouched.
  3. It's what production does. This is Envoy's admin port and HAProxy's stats socket. "The admin plane is a different socket" is the production lesson, not an implementation detail.

Deliberately tiny

The admin server reuses the battle-tested Level 1 parser (read_head / parse_request_head) — a second hand-written parser is just a second bug surface — and nothing else from the proxy machinery. No routing, no middleware, no keep-alive, no pooling. One request per connection, Connection: close, done. A scraper hits it every ~15 s, so everything keep-alive would buy is rounding error, and everything it costs (drain-before-reuse discipline, poolability analysis) is complexity this endpoint exists to observe, not participate in.

It is not exempt from slowloris thinking, though: a 5-second whole-exchange deadline (ADMIN_TIMEOUT) covers read plus write. A full ConnLimiter would be overkill for a localhost-default socket, but an unbounded read deadline would be the same mistake Level 8 spent a whole level killing. Unknown path → 404 with a fixed body (no path echo, no reflection surface); non-GET → 405. The bind happens in main before the banner, so a bad or taken --admin address fails startup with exit 1 — the same guardrail posture as Level 8's TLS config checks.

/health: degraded but 200

/health reports the proxy's own liveness with an upstream summary:

{"status":"ok","upstreams":{"api":{"healthy":2,"total":3}},"active_connections":7}

It degrades to "status":"degraded" when any upstream has zero healthy backends — but stays HTTP 200.

Why 200 and not 503? This endpoint answers "is the proxy alive?" — and it is; it just answered. Backend health is a different question, and Level 4's breaker already owns it. If /health returned 503 on a dead backend, a supervisor (systemd, Kubernetes) would restart Ferrum — throwing away every healthy upstream's connections and warm pools to punish the proxy for a failure it neither caused nor can fix. That makes the outage strictly worse. The 200-with-degraded-payload is the correct signal: the proxy is up, and here is the diagnostic detail for a human or a smarter alert to act on.
Level 12 note baked in. The admin task resolves the upstream list per request through the shared route handle, not by capturing a Vec at boot. Capturing at boot would make /health report a retired config forever after a hot reload — and worse, keep the old pools alive by holding a strong reference. The seam for Level 12's reload is recorded here rather than discovered later.

How Industry Does It

Every production proxy solved observability; the interesting part is how, and where Ferrum's teaching build lands honestly against them.

nginx

Log templates + stub_status

Mechanism: a configurable log_format with a rich set of built-in variables ($request_time, $upstream_response_time, $status). Native metrics are minimal — stub_status gives a handful of connection counters; real Prometheus metrics need a third-party module (nginx-vts) or the commercial nginx Plus.

vs ours: our JSON line is nginx's log_format idea with the escaping done for you and the format fixed; our first-class histogram is something open-source nginx lacks natively.

HAProxy

Stats socket + timers

Mechanism: famously detailed timing breakdown per request (Tq/Tw/Tc/Tr/Tt — queue, wait, connect, response, total) in its log, and a runtime stats socket plus a built-in Prometheus exporter serving hundreds of counters/gauges.

vs ours: HAProxy's separate stats socket is exactly the pattern we copied for the admin plane. Its timer decomposition is richer than our four stamps; ours teaches the idea of stage timing at a fraction of the surface.

Envoy

Admin port + stats sinks

Mechanism: a dedicated admin listener (/stats, /stats/prometheus, /clusters, /config_dump) plus pluggable stats sinks and native distributed tracing (Zipkin, Jaeger, OTLP) with full traceparent propagation. Thousands of metrics out of the box.

vs ours: Envoy's admin listener is the model for admin.rs, down to it being a separate socket. The gulf is tracing: Envoy does distributed spans across services; Ferrum does per-stage timing on one hop, by design — we are a single hop with no downstream to trace into.

Apache httpd

mod_log_config + mod_status

Mechanism: LogFormat directives with %-variables (the origin of nginx's model), and mod_status for a human HTML scoreboard of worker state. Prometheus needs a third-party exporter.

vs ours: similar shape to nginx — flexible text logs, weak native metrics. Our structured-by-default JSON and built-in histogram are closer to the modern (Envoy-era) expectation.

Honest scope. Ferrum is a teaching build. The registry has a handful of series; Envoy has thousands and a config-driven stat prefix system. We have no distributed tracing, no stats sinks beyond the text endpoint, no log rotation (stdout/stderr is the supervisor's job — the twelve-factor position), and no dynamic label registration (labels are fixed at startup, the seam Level 12's hot reload will have to revisit). What Ferrum does have is the mechanism visible: you can read all of metrics.rs in one sitting and understand why every production proxy's histogram works the way it does. That legibility is the entire point.

Glossary

Cardinality

The number of distinct label combinations — hence distinct time series. High cardinality (unbounded label values) exhausts memory. The reason labels come from config, never from requests.

Histogram bucket (le)

A count of observations "less than or equal to" a fixed upper bound. Prometheus buckets are cumulative; ours store one-per-observation and cumulate at scrape time.

Counter vs gauge

A counter only rises (rates derived at query time); a gauge moves both ways (a level, like open connections). Different math, different instruments.

RAII / ConnGauge

Resource Acquisition Is Initialization: the gauge increments on construction and decrements in Drop, so no exit path — clean, error, panic — can leak it. Same pattern as L8's limiter and L3's lease.

TTFB

Time To First Byte. Here, honestly, "time until the backend's response head is fully read" — the observable version from where the proxy sits, since reads return whole heads.

Relaxed ordering

The weakest atomic memory order. Guarantees the RMW's own atomicity (no lost increment) but no ordering against other memory. Correct for metrics because there is nothing to order.

RFC 3339 / civil_from_days

The timestamp format (...T...Z, UTC, millis) and the ~15-line days-to-date algorithm that produces it without a chrono dependency.

Exposition format

Prometheus's text protocol: # HELP/# TYPE headers, one name{labels} value line per series. Ferrum builds it into a String at scrape time.
