Executive Summary

Level 13 gives Ferrum a Web Application Firewall — but not as a new subsystem bolted on the side. A WAF is a reverse proxy that grew an immune system, and because Level 6 already built the middleware chain, the WAF is just middleware with opinions: impl Middleware for Waf in waf.rs, slotted into the fixed chain.

The lesson, per the KB, is that normalization is 80% of WAF quality. Evasion is mostly encoding games, so normalize() percent-decodes up to twice (a second pass that changes anything is double-encoding — flagged and scored, because legitimate clients single-encode), targeted-entity-decodes the handful of forms attackers use to smuggle angle brackets and quotes, lowercases, and collapses whitespace runs so one union select pattern matches every spacing. Broken escapes stay literal — a WAF must never 500 on hostile input. canonicalize_path() resolves ./.. and flags any attempt to climb above root, even when the resolved path lands innocently: we cannot know how the backend resolves paths, so the attempt is the conviction-worthy fact.

On top sits detection: ~16 rules in a const array — data, not code — scanned linearly over four normalized surfaces (canonicalized path, query string, User-Agent, Referer). Following the ModSecurity CRS model, each hit adds points and conviction happens only at a threshold (default 10). A lone quote is 2 points (O'Brien buys coffee too); union+select co-occurring is 10, because that conjunction has no benign URL reading. Benign lookalikes are first-class tests. A reputation layer turns convictions into strikes and repeat offenders into temporary bans with doubling backoff — the Level 4 breaker's philosophy pointed inward at clients. Every WAF ships watching first: ;waf=detect logs and forwards; ;waf=block returns a generic 403. Rule names are log-only in both modes — a response that names the rule that fired is a payload-tuning oracle. 280 unit tests (261 kept green, +19), live verification all green.

The Big Picture

Where the WAF sits: after request-id, before ratelimit and auth. Hostility is refused before it can consume a rate token or trigger a credential comparison.

Chain order is fixed in code — never config — inside MiddlewareConfig::build, the invariant Level 6 established. The WAF is deliberately early: after request-id (so a blocked request still carries an id and an access-log line on the way out — the onion unwinds correctly) but before ratelimit and auth (a detected attack should never spend a rate token or reach a password comparison, and rejected_by:"waf" must attribute correctly). The ban check runs first of all, before any inspection: a banned IP is refused for roughly one hash and one short lock — no normalization, no rule scan. Cheap refusal of known offenders is most of what reputation buys.

Analogy: the WAF is a bouncer at the door who has read the guest list of known troublemakers (reputation) and also watches how you talk as you walk up. Someone already banned is turned away at a glance — no pat-down needed. Everyone else gets listened to: one muttered curse word is nothing, but "I'm going to union the vault and select the cash" trips the meter. He writes down exactly what you said in his logbook (the error log) but tells you only "not tonight" (a generic 403) — never which words gave you away, because that would just teach you to rephrase.

Normalization: 80% of WAF Quality

Attackers do not send you <script>; they send %3Cscript%3E, or %253Cscript, or &lt;script&gt;, or UNION /**/ SELECT. Naive regex on raw bytes catches only the lazy. Decode first, judge after.

The KB's central claim: normalization is 80% of WAF quality, because evasion is mostly encoding games. The whole point of normalize(raw, plus_is_space) in waf.rs is to render every equivalent spelling of a payload into one canonical form before a single rule runs. It returns the normalized text plus a small struct of evasion receipts — flags that are themselves scored, because the act of evading is a signal independent of what was hidden.

The decode pipeline, in order

  1. Percent-decode, pass one. %27 becomes ', %20 a space. In query strings only, + becomes a space (plus_is_space); in a path, + is literal data.
  2. Percent-decode, pass two. Run it again. If the second pass changes anything, the input was double-encoded — %252e → %2e → . — and the double_encoded flag is raised. Legitimate clients single-encode, so a changed second pass is suspicious in itself.
  3. Targeted entity decode. Not an HTML parser — a de-cloaking of the specific forms attackers use to smuggle angle brackets and quotes past byte filters: &lt; &gt; &quot; &apos; &#x27; &#39; &#x3c; &#60; &#x3e; &#62;.
  4. Lowercase. UNION, Union, uNiOn collapse to one, so rules are written in lowercase once.
  5. Null-byte flag & strip. A \0 in a URL has no honest use (it is a classic filter-terminator trick); the null_byte flag is raised and the byte removed so it cannot split later matching.
  6. Whitespace collapse. Runs of tabs/newlines/spaces collapse to a single space, so one union select pattern matches UNION\t\nSELECT and every other spacing.
Watch out — a WAF must never 500. Broken escapes stay literal. percent_decode_once keeps %zz and a truncated %2 exactly as-is rather than erroring: normalize("100%zz%2") returns 100%zz%2 unchanged. Hostile input that crashes the firewall is a worse outcome than hostile input that passes — a crash is a denial of service you built yourself. The normalizer is total: every byte sequence has a defined, non-panicking result.

Why the double-encoding flag scores on its own

The flag is worth DOUBLE_ENCODED_POINTS = 4 per surface where it was raised, regardless of what the decoded text turned out to be. The reasoning: single-encoding is normal (every browser does it); double-encoding is a deliberate attempt to slip a payload past a filter that decodes only once. Punishing single-encoding would flag the entire honest internet; punishing double-encoding flags almost exclusively people trying to hide something. So the evasion attempt convicts even before the traversal or SQLi rule underneath it matches.

Analogy: a letter addressed in plain handwriting is normal. A letter where the address is written, photographed, printed, and re-photographed before mailing is not more legible — it is someone trying to defeat an automated sorter. You don't need to open it to be suspicious of the wrapping.
Worked example: %252e%252e%2fetc/passwd through both passes

Pass one decodes %25→% and %2f→/, giving %2e%2e/etc/passwd. Pass two decodes the surviving %2e→., giving ../etc/passwd — and because pass two changed the string, double_encoded is raised (+4). Then canonicalization sees the .. and, since it pops above root, raises the climb flag (+8), and the literal ../ also matches traversal:dotdot (+8) plus /etc/passwd matches the sensitive-file rule (+8). The evasion receipts alone (4) plus the climb (8) already clear nothing on their own — but stacked with the traversal grammar the request is far over threshold. This is quiz question 1.

Canonicalize & the Climb Flag

The Level 2 normalization lesson, weaponized: canonicalize first, judge the result — but here the attempt to climb above root is also recorded, because a path that resolves innocently can still have probed how far up it could walk.

canonicalize_path(path) walks the segments of an already-percent-decoded path, keeping a stack. Empty segments and . are dropped; .. pops the stack; anything else is pushed. If a .. ever tries to pop an empty stack, that is an attempt to climb above the root, and the boolean climbed is set — even if later segments descend again and the final path looks harmless.

Input pathCanonical resultclimbed?
/a/./b/../c/a/cfalse
/a/../../etc/passwd/etc/passwdtrue
/..//../x/xtrue
/normal/path/normal/pathfalse
Why convict the attempt when the result is innocent? Ferrum cannot know how the backend resolves paths. A framework, a static-file server, and a CGI script all disagree on what /a/../../b means; some collapse it to /b, others follow symlinks or resolve against a different root and escape the document tree. The one thing we can observe is that the client wrote a segment sequence that tries to walk above the root. The conservative choice — convict the attempt, worth CLIMB_POINTS = 8 — is correct precisely because the unknown (backend resolution semantics) makes the innocent-looking result untrustworthy. This is quiz question 3.

The inspect function scans both the decoded path (pre-canonicalization) and the canonical form when they differ. Scanning the decoded text means literal ../ sequences score via traversal:dotdot even when canonicalization would have absorbed them; scanning the canonical form catches sensitive-file paths like /etc/passwd that only assemble cleanly after resolution. Two cheap passes over a short string, belt and suspenders.

The Rule Table: Data, Not Code

~16 rules in a static RULES: &[Rule] array. Data, not code — so the quiz can ask "add a rule" meaningfully, and so an operator can read the table by eye and answer "why did this block?"

Each Rule is a name, a point value, and a match kind. Matching is deliberately plain: a Pat enum with three shapes, scanned linearly over the normalized buffer. This is a rejected-alternative worth naming — the KB suggests production shape is RegexSet + Aho-Corasick pre-filters. We already have the regex crate from Level 2, but at ~16 rules a linear pass over an already-normalized string beats the setup cost of set-matching machinery, and the lesson is normalization + scoring, not matcher engineering. Production CRS has thousands of rules; that scale is exactly what the fancier machinery is for. Different scale, different tool.

Pat::Sub

Substring

What: the string is present anywhere. text.contains(s).

Used for: ', <script, javascript:, ../, information_schema.

Pat::All

Conjunction

What: all substrings present, order-free. Cheaper and clearer than a regex with lookaheads.

Used for: union+select — the co-occurrence is the signature.

Pat::Re

Compiled regex

What: for the few shapes where structure matters. Compiled once via OnceLock at first use.

Used for: tautologies, stacked queries, event handlers, scanner UAs.

The tautology rule & the no-backreferences constraint

The precise SQL tautology is (\d+)=\1 — a backreference asserting the two numbers are equal. Rust's regex crate rejects backreferences by design. That refusal is not a limitation to route around; it is the same guarantee that makes it safe to run regexes per request at all. Backreferences force backtracking, and backtracking is how a regex becomes a denial-of-service (catastrophic exponential blowup on a crafted input). The regex crate's linear-time promise is exactly what Level 9's blocking audit relied on when it cleared Level 2's ~regex routes of being a per-request DoS vector.

The over-match is correct. Without backreferences, the rule uses the looser \b(or|and)\s+(\d+\s*=\s*\d+|'[^']*'\s*=\s*'[^']*'), which matches or 1=2 — a false tautology — as well as or 1=1. That "imprecision" convicts exactly the right people: or 1=2 in a query string is how attackers probe blind injection (they compare a true-predicate response to a false-predicate response). The looser pattern catches the probe correctly. This is quiz question 5.

Anomaly Scoring & Conviction

The ModSecurity CRS model: rules don't block, points do. Each hit adds to a running score; conviction happens only at a threshold. This is the single difference between a WAF and a false-positive generator that ops disables within a week.

inspect(req) -> Verdict normalizes each of the four surfaces once, scans each against the whole rule table, and accumulates one Verdict { score, hits }. Points sum across surfaces: a quote in the query, a comment sequence, and a scanner UA are three separate hits whose points add up. The threshold (default DEFAULT_THRESHOLD = 10, tunable per route) is the conviction line. Below it, Continue.

Why these weights

Points follow the CRS spirit: ambient-noise patterns score low, unambiguous attack grammar scores at-or-near threshold.

2 points — a nudge

A lone quote '

O'Brien buys coffee too. Apostrophes appear in millions of legitimate query strings — names, possessives, search terms. A lone quote can never convict alone (2 < 10), but stacked on real signals it tips a borderline score. That is exactly what CRS does with it.

10 points — a conviction

union + select

"Union station" alone scores nothing; "select a plan" alone scores nothing. The conjunction of both words in one normalized surface has no benign URL reading — it is the UNION SELECT exfiltration grammar itself. So the co-occurrence is worth the full threshold on its own.

What breaks if you swap them? Score a lone quote at 10 and you convict O'Brien, union station, and every apostrophe on the internet — ops disables the WAF by Friday. Score union select at 2 and a live exfiltration attempt sails under the threshold — the WAF is decorative. The weights encode how much benign traffic looks like each pattern; inverting them inverts the false-positive/false-negative trade in the worst direction on both ends. This is quiz question 4.

Benign lookalikes are first-class tests

A scoring model is only as trustworthy as its false-positive suite. These are all asserted to stay under threshold in waf.rs's tests, and they are the reason the weights are what they are:

The no-oracle rule

In both modes, the rule hit-list (verdict.hits) goes to the error log at WARN and to metrics — and nowhere near the client. A 403 carries a generic 403 Forbidden\n body; no X-Waf-Score header is added in either mode. The reason: telling an attacker which rule fired is a payload-tuning oracle. With a rule-naming error page, the workflow is trivial — send a payload, read which rule blocked it, tweak to dodge that rule, repeat until 200. A generic 403 tells them only "no," turning a guided search into blind guessing. This is quiz question 7.

score ≥ threshold → block mode: 403 + strike | detect mode: log + forward

Reputation: the Breaker Pointed Inward

Level 4 built a circuit breaker that treats a backend which keeps 500ing as "unhealthy." Reputation is the same philosophy aimed at clients: a source that keeps attacking is unhealthy the same way, and earns a temporary ban.

Reputation is a 16-shard map (Vec<Mutex<HashMap<IpAddr, Offender>>>) keyed by client IP — the same sharded-locking idiom Level 6's rate limiter and Level 11's cache used, so concurrent clients rarely contend on the same lock. Each Offender tracks strikes, the timestamp of the last strike, an optional banned_until, and a bans counter for backoff.

Strike → ban → doubling backoff

  1. A conviction adds a strike with the current timestamp. In block mode; in detect mode strikes are recorded but never enforced.
  2. Strikes ≥ ban_after (default 3) within the decay window trips a ban.
  3. Ban term = ban_base (default 60 s) × 2bans, capped at BAN_CAP = 1 h. First ban 60 s, then 120 s, 240 s… — the Level 4 exponential backoff, applied to clients. On ban, strikes reset to 0 but bans increments, so a source that re-offends the moment a ban lifts earns geometrically longer bans.
  4. Lazy decay on lookup (the Level 11 TTL pattern): there is no sweeper task. On the next is_banned or strike touch, an expired ban lifts and strikes older than the decay window (ban_base × 10) reset to 0. Yesterday's fat-fingered quote doesn't count toward today's ban.
The ban check is cheap, and that is the point. A banned IP is refused for roughly one hash and one short mutex lock — no normalization, no rule scan, no allocation. An inspected request runs the full decode-and-scan pipeline over four surfaces. That asymmetry is why the ban check runs before inspection and why "cheap refusal of known offenders is most of what reputation buys": under a scanner flood, the expensive work is skipped entirely for the IPs generating the most traffic. This is quiz question 9.

Process-wide, memory-only, reload-surviving

The store is a single OnceLock<Arc<Reputation>> (REPUTATION), configured once in main.rs before any route is built and handed to every waf-enabled route via shared_reputation(). This is a deliberate design choice with three consequences:

One offender

Shared across routes

An attacker probing /api and /admin is one offender, not two. A per-route store would let them spread their strikes thin.

Survives reload

Not amnesty

A Level 12 config reload rebuilds the middleware chains but not this store. Strikes and bans persist — rerouting is not an amnesty, and an operator reloading a route change would not want their active bans wiped.

Restart amnesties

Honest limit

Memory-only: a process restart clears everyone. Honest for a teaching proxy — persistent, cross-customer reputation feeds are precisely the commercial vendors' moat.

Analogy: the bouncer's memory of troublemakers lasts the whole shift and survives a change of the guest list (reload), but he goes home at close and starts fresh tomorrow (restart). A real security firm keeps a shared, permanent blocklist across every venue it staffs — that persistence is the product you pay for. Reload-survival and restart-amnesty are quiz question 10.
Fail open, always. If a shard's mutex is poisoned (a thread panicked while holding it), is_banned and strike return "not banned / no ban" rather than propagating the panic. A WAF that panics the whole proxy is a worse outcome than one skipped reputation check — the same fail-open stance Levels 6 and 11 took.

A WAF Is a Middleware — Literally

No new subsystem. impl Middleware for Waf and the existing Level 6 chain machinery supplies everything a WAF needs: short-circuit rejection, response-phase unwind, per-route config, and rejected_by attribution.

Detection is pure sync functions over the request head — exactly the shape the Level 6 trait demands, and the Level 9 "small state machine" pattern. The on_request handler is the whole enforcement path:

  1. Ban check (block mode only). reputation.is_banned(ip, now) — if banned, increment ban_refused and Reject(forbidden()) immediately, uninspected.
  2. Inspect. inspect(req) → Verdict. If score == 0, Continue — the overwhelmingly common case, cheap.
  3. Record the score. ctx.waf_score = Some(score) so the access log carries it (only when > 0; null otherwise).
  4. Convict or not. score ≥ threshold → block mode: count convicted, WARN-log the hits, strike(ip, now, true) (may ban), Reject. Detect mode: count detected, WARN-log, strike(ip, now, false) (never bans), Continue.

Chain order, and the two orderings rejected

Fixed in MiddlewareConfig::build: log → request-id → waf → ratelimit → auth → authz. Two alternatives were considered and rejected, each for a concrete reason (quiz question 6):

Rejected orderingThe concrete failure
WAF before request-idA blocked request's 403 would have no request-id and no clean access-log line — the response-phase unwind that stamps and logs a rejection would have nothing to stamp. You'd lose the ability to correlate a block with the rest of the trace.
WAF after ratelimitA detected attack would consume a rate token before being refused — an attacker could exhaust a route's rate budget with payloads the WAF was going to reject anyway, and the ban check (cheap refusal) would come after the expensive token accounting. Hostility should be refused before it costs anything.

Per-route options & the boot guardrail

waf and waf-threshold joined the Level 6 option keys (L6_KEYS in middleware/mod.rs) because they configure a middleware. Usage: ;waf=block or ;waf=detect, and ;waf-threshold=N (default 10). Off by default, like every security opt-in since Level 8's TLS.

Guardrail: ;waf-threshold= without a ;waf= on the same route is a startup error ("waf-threshold= needs a waf= on the same route"), not a silent no-op. Tuning a threshold for a WAF that isn't enabled is incoherent config, and the Level 5/6 posture is to fail loudly at boot rather than mislead the operator. An unknown mode or a non-numeric/zero threshold is likewise a boot error.

The Honesty Checkpoint

Signature WAFs are a speed bump, not a wall. Build it knowing exactly what it can and cannot promise — the KB kept this verbatim in spirit, and so does the module doc-comment.

Determined attackers bypass regex rules; vendors know it, which is why the commercial layers above signatures exist. The real injection fixes live in the application: parameterized queries defeat SQLi structurally, output encoding defeats XSS structurally. No WAF replaces them. What this level honestly buys:

Buys

The automated 99%

Blocks the constant background noise of scanners and script-kiddie payloads that make up most hostile traffic.

Buys

Time during 0-days

A virtual patch — a new rule — can hold the line for hours or days while the application fix ships.

Buys

Visibility

Metrics and logs turn "we might be under attack" into a counter and a hit-list.

Body inspection is absent by architecture, not by omission. Ferrum streams request bodies in 16 KB windows — Level 1's flat-memory guarantee. A body-inspecting WAF must instead buffer the whole body to scan it, which is a fundamentally different memory architecture (and a DoS surface of its own). So this WAF sees request heads only, and says so rather than pretending otherwise. The consequence it structurally cannot see: an injection payload carried in a POST body (e.g. a form-encoded or JSON SQLi in the request body) passes untouched. This is quiz question 11.

The three commercial layers above signatures (quiz 14)

How Industry Does It

The reference-grade signature WAF is ModSecurity with the OWASP Core Rule Set. Ferrum borrows its model — anomaly scoring, normalization-first — at a teaching scale.

ModSecurity + OWASP CRS

The reference

An engine (originally an Apache module, now libmodsecurity for nginx/Envoy too) plus a community ruleset of thousands of rules. Same anomaly-scoring model we borrowed — paranoia levels, per-rule scores, a blocking threshold. Rich transformation pipeline (t:urlDecode, t:htmlEntityDecode, t:normalizePath, …) that our normalize() is a miniature of.

Cloud WAFs (Cloudflare, AWS WAF, Azure)

Managed + ML

Managed rule groups updated by a vendor research team, ML/bot-scoring, and — the real moat — shared reputation across every customer's traffic. This is exactly the commercial layer our honesty checkpoint names as above signatures.

Envoy / Coraza

Sidecar / library WAF

Envoy runs WAF logic via a filter (often libmodsecurity or the Go-native Coraza) in the L7 filter chain — structurally the same idea as our WAF-as-middleware, at production maturity. Coraza is CRS-compatible Go.

nginx / Apache / HAProxy

Bolt-on

None ship a WAF in core. nginx and Apache load ModSecurity as a module; HAProxy typically uses SPOE to an external agent (or Coraza-SPOA). The WAF is always a layer, which is precisely the framing Ferrum takes literally: middleware with opinions.

Be honest: ours is a teaching build. ~16 rules against CRS's thousands; a linear string scan against RegexSet + Aho-Corasick pre-filters; head-only against full body inspection; a memory-only per-process reputation store against persistent cross-customer feeds. The value here is understanding the model — normalization, scoring, reputation, the honesty about limits — not the rule count. A production deployment fronts Ferrum with a real WAF; this level teaches what that WAF is doing.

Glossary

Normalization

Rendering every encoded/cased/spaced spelling of a payload into one canonical form before matching. The KB's "80% of WAF quality."

Evasion flag / receipt

A boolean raised during normalization (double-encoded, null-byte, traversal-attempt) that is itself scored — the act of evading is a signal.

Anomaly scoring

The CRS model: rules add points; block only at a threshold. Distinguishes a WAF from a false-positive generator.

Conviction

A verdict whose accumulated score meets or exceeds the threshold.

Strike

A recorded conviction against a client IP; ban_after strikes in the decay window trip a ban.

Oracle

Any response signal (rule name, score header) that helps an attacker tune payloads. Ferrum gives none — generic 403, log-only hits.

Detect vs block mode

Detect logs and forwards (watching first); block returns a 403 and enforces bans. Every WAF ships in detect mode.

Lazy decay

Expiring strikes/bans on the next lookup rather than via a sweeper task — the Level 11 TTL pattern.
