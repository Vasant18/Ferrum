Executive Summary

Level 2 turns Ferrum from a one-pipe forwarder into a router: it decides, per request, which backend gets the traffic — deterministically and without taking a lock.

The whole level lives in rproxy/src/router.rs. A RouteTable holds a Vec<Route>, and each Route is a set of match conditions (an optional host, an optional method, and one PathMatcher) plus the backend to forward to. There are five path matchers — Exact, Prefix, Wildcard, Regex, and Any — parsed from a compact CLI syntax like /api/**=api or POST host.com/upload=127.0.0.1:9004.

Because several routes usually match one request, the subtle part is precedence. We do not use declaration order; we compute a numeric specificity for every matching route and pick the highest, so the outcome never depends on how the operator ordered their config. Exact beats wildcard beats longest-prefix beats regex beats catch-all, and host- or method-scoped routes outrank unconstrained ones on the same path.

The table is built once at startup and then treated as immutable, shared as an Arc<RouteTable> that every per-connection task reads concurrently — matching never touches a mutex. Regex support is the one external dependency this level adds (the regex crate), chosen deliberately because it guarantees linear-time matching with no catastrophic backtracking — a property that stops being a mere performance note and becomes a security guarantee once untrusted input reaches the matcher at Levels 9 and 13. This is a teaching build: a linear scan over a Vec, not a compiled radix trie, and the comparison section is honest about where that costs us versus nginx or Envoy.

The Big Picture

Routing is the stage that sits between "we have a parsed request" (Level 1) and "we pick a server from a pool and forward" (Level 3). Level 1 drew the pipeline; Level 2 fills in the route + forward box that was dashed grey on the Level 1 diagram. The proxy extracts three keys from the parsed head — method, host (port stripped), and path (query stripped) — and hands them to RouteTable::find_route_indexed.

Analogy: A RouteTable is a receptionist with a laminated directory. Every visitor states three things — what they want to do (method), who they're here to see (host), and which floor (path). Several directory entries might apply ("anyone → lobby", "engineering floor → 4th", "Jane on the engineering floor → room 412"). The receptionist doesn't pick the first line she reads; she picks the most specific matching line. That "most specific wins" instinct is the entire precedence algorithm.

1 · The Route Model

A Route is "if the request looks like this, send it there." A RouteTable is just an ordered list of them.

What a Route holds

In router.rs, a Route is a plain struct with three match conditions and a destination:

pub struct Route {
    pub host: Option<String>,      // None = match any host
    pub method: Option<String>,    // None = match any method
    pub path: PathMatcher,         // one of five kinds (next section)
    pub upstream: Arc<Upstream>,   // where to forward (a pool, from L3)
    // ... rules (L5), chain (L6), cache_ttl (L11) added later
}

What it is: the Option on host and method encodes "this dimension is unconstrained." A route with host: None, method: None only filters on the path. The why: making "any" the None case rather than a magic "*" string means the matcher never has to special-case a sentinel — a missing constraint literally can't be compared, so it's skipped.

Watch out — the field grew later. In Level 2 the destination was a single backend String. The code you read today shows upstream: Arc<Upstream> because Level 3 replaced the string with a whole pool (a single backend is now a one-member round-robin pool). The fields rules, chain, and cache_ttl are Levels 5, 6, and 11. For Level 2, mentally erase everything after path and read upstream as "the one backend."

The RouteTable and the catch-all

RouteTable wraps a Vec<Route> and is built once via RouteTable::new(routes). The Level 1 behavior — forward everything to one backend — is now expressible as a single rule via Route::catch_all(backend), which sets host: None, method: None, and path: PathMatcher::Any. That is the backward-compatibility seam: cargo run -- 127.0.0.1:8080 127.0.0.1:9000 still works because a bare host:port becomes one catch-all route.

Three read methods sit on the table, all sharing one selection core:

  • find(method, host, path) -> Option<&Arc<Upstream>> — just the pool.
  • find_route(...) -> Option<&Route> — the whole winning route (Level 5 needs its rewrite rules).
  • find_route_indexed(...) -> Option<(usize, &Route)> — the winner plus its table index (Level 11's cache key uses the index).

The why for one shared core: if find and find_route each ran their own ranking, a subtle divergence could route the body to backend A while applying backend B's rewrite rules. Funnelling all three through find_route_indexed makes that class of bug impossible.

2 · Five Path Matchers

The path is where the interesting matching happens. Ferrum offers five kinds, ordered from most to least specific.

The PathMatcher enum in router.rs is the heart of the level. Each variant answers matches(path) -> bool differently:

Exact

Exact(String)

What: path == p. /health matches only /health.

Spec syntax: a plain path with no trailing glob, e.g. /api/health=....

Prefix

Prefix(String)

What: path.starts_with(p). /api/ matches /api/users and /api/v2/x.

Spec syntax: the /** suffix: /api/** becomes prefix /api/.

Wildcard

Wildcard(String)

What: exactly one non-empty path segment after the prefix. /files/* matches /files/report.pdf but not /files/2026/report.pdf (nested) nor /files/ (empty).

Spec syntax: the /* suffix.

Regex

Regex(Regex)

What: a full regular expression tested with re.is_match(path). ~^/v[0-9]+/ matches /v2/users but not /vX/users.

Spec syntax: a leading ~ takes the rest as the pattern.

Any

Any

What: matches every path — the catch-all backstop. Spec syntax: / or /** on their own.

Why the Wildcard exists at all

A single-segment wildcard is a cheap alternative to regex. Its matches body is just strip_prefix plus two conditions — "there is a remainder" and "the remainder contains no /":

PathMatcher::Wildcard(prefix) => match path.strip_prefix(prefix) {
    Some(rest) => !rest.is_empty() && !rest.contains('/'),
    None => false,
}

That is O(path length) with no engine to compile or feed. For the common "one variable segment" case (/files/*, /users/*) you get the ergonomics of a wildcard without paying for regex at all. The design lesson: reach for the cheapest matcher that expresses the intent; keep regex for the cases only regex can express.

Gotcha — the parser's precedence of suffixes matters. In parse_matchers, the order of checks is /** → /-or-/** (Any) → /* → else Exact. Because /** is checked before /*, a path ending in /** can never be mis-read as a wildcard with a trailing *. Get that order wrong and /api/** silently becomes a wildcard.

3 · Host & Method Filters

Path is the primary key; host and method are optional secondary filters that narrow a route.

How the three dimensions combine

Route::matches is an AND across all constrained dimensions — a route matches only if every present constraint is satisfied:

  1. Host: if self.host is Some(h), the request's Host header (port already stripped) must equal h case-insensitively via eq_ignore_ascii_case. None matches any host.
  2. Method: if self.method is Some(m), the request method must equal m case-insensitively. None matches any method.
  3. Path: always checked, by delegating to self.path.matches(path).

The why for case-insensitivity: hostnames are case-insensitive by RFC, and HTTP methods are conventionally uppercase but clients misbehave. Comparing with eq_ignore_ascii_case (ASCII-only, not full Unicode folding) is correct for both and avoids a surprising 404 when a client sends API.EXAMPLE.COM or a lowercase verb.

Where the keys come from

The router doesn't parse the request; Level 1 already did. Two small helpers in http.rs shape the raw fields into match keys:

  • http::target_path(target) — strips the query string, so /api/users?page=2 matches on /api/users. Routing keys off the path, never the query.
  • http::host_without_port(host) — strips a trailing :port, correctly handling IPv6 literals like [::1]:8080 → [::1]. So example.com:8080 and example.com route identically.

The proxy calls these in proxy.rs before invoking find_route_indexed. Keeping the shaping in http.rs and the matching in router.rs is a clean seam: the router never learns about ports or query strings.

Parser limitation, stated honestly. The simple CLI parser does not support a host prefix alongside a regex path — a ~-regex spec always has host: None. If you need host-scoped regex routing you would extend parse_matchers; Level 2 didn't, because the exercise was the matching engine, not a full config grammar.

4 · Specificity Ranking

The one idea to take away from Level 2: precedence is computed, not declared. Most-specific wins, deterministically, regardless of config order.

The problem

Consider three routes and one request to /api/health:

/=B_ANY              (catch-all)
/api/**=B_PREFIX     (prefix)
/api/health=B_EXACT  (exact)

All three match. Which wins? If you picked by declaration order the answer would flip when someone reorders the config file — a fragile, surprising rule. Ferrum instead assigns each matcher a numeric specificity and takes the maximum.

The scoring function

PathMatcher::specificity returns a base rank per variant, with length as a tie-breaker for prefixes and wildcards:

MatcherScoreMeaning
Exact4000one path only — maximally specific
Wildcard(p)3000 + p.len()one segment; longer prefix = more specific
Prefix(p)2000 + p.len()any suffix; longest prefix wins
Regex1000flexible but ranked below the structured matchers
Any0the backstop — only wins when nothing else matches

Then Route::specificity adds tie-breakers for the other two dimensions on top of the path score:

route_score = path.specificity() + (host ? 500 : 0) + (method ? 100 : 0)

So a host-scoped route beats a bare one on the same path (+500), and a method-scoped route beats a bare one (+100). The band widths (1000 apart for path kinds, +500 for host, +100 for method) are chosen so that path kind always dominates host and method — a host constraint can't promote a prefix above an exact match.

The algorithm & its complexity

Selection is a single pass in find_route_indexed:

self.routes.iter().enumerate()
    .filter(|(_, r)| r.matches(method, host, path))
    .max_by_key(|(_, r)| r.specificity())

Complexity: O(n) in the number of routes — test every route, keep the highest score. Tie-break: Rust's max_by_key keeps the first maximum, so two equally-specific routes resolve to the earliest declared — the same behavior nginx gives equally-specific regex locations. This is the one place declaration order matters, and only as a final tie-break after specificity has already decided.

The "longest prefix wins" heritage: the 2000 + p.len() rule is exactly the longest-prefix-match rule from IP routing tables — /api/v2/ (len 8) beats /api/ (len 5). Reusing a battle-tested networking idea, not inventing a new one.

5 · Arc<RouteTable> Sharing

One table, many readers, zero locks on the hot path. The routing table is built once and shared immutably.

Immutable-after-build, shared by reference count

After RouteTable::new returns, the table is never mutated. It is wrapped in an Arc — an atomically reference-counted pointer — and each per-connection Tokio task holds a clone. Cloning an Arc is a cheap atomic increment of a refcount, not a copy of the routes. The why: because the data behind the Arc can't change, no reader needs a lock to observe it consistently. Matching a request is a pure read: iterate, filter, take the max. Thousands of concurrent connections can route simultaneously without ever contending.

The same Arc-sharing idea nests one level deeper: several routes can point at the same declared upstream, so Route.upstream is itself an Arc<Upstream> (a Level 3 detail). RouteTable::upstreams() de-duplicates by Arc::ptr_eq so a pool shared by five routes is health-probed once, not five times.

Honest scope note — Level 2 vs. Level 12. The doc-comment in router.rs foreshadows an "atomic config swap," and the code you read today wraps the table in RwLock<Arc<RouteTable>> in main.rs so it can be hot-reloaded. That RwLock and the swap are Level 12, not Level 2. In Level 2 the Arc is simply cloned per connection and never replaced. The brief is clear elsewhere in the course that this is a plain RwLock swap, not a true lock-free arc-swap — a deliberately crude but correct choice.
Analogy: the Arc<RouteTable> is a laminated directory bolted to the wall. Every receptionist (connection) can read it at once because nobody is allowed to write on it. When management needs to change the directory (Level 12), they don't erase the wall copy while people are reading it — they print a whole new laminated sheet and swap the whole board atomically.

6 · The Regex Dependency Decision

Level 2 adds exactly one external crate — regex — and the reason it's safe to add is the reason it matters for security later.

The decision

Ferrum is otherwise near-dependency-free (Level 1 hand-rolls its HTTP parser). Adding regex (pinned at 1.13.1 in Cargo.toml) was a conscious trade: some path patterns — "any version segment", "a UUID-shaped id" — simply cannot be expressed by exact/prefix/wildcard matchers, and writing a regex engine from scratch would be a multi-week detour off-topic for a proxy course. So we take the dependency, but a specific one.

Why the Rust regex crate specifically

The Rust regex crate is built on finite automata (Thompson NFA / DFA), not the backtracking engines used by PCRE, Perl, Python's re, or JavaScript. Its defining guarantee: matching runs in linear time in the length of the input, O(n), with no catastrophic backtracking. To buy that, it deliberately omits backreferences and lookaround — the very features that make backtracking engines able to blow up.

What "catastrophic backtracking" is: a backtracking engine fed a pathological pattern like (a+)+$ against a long non-matching input can explore exponentially many ways to split the input, taking seconds or minutes on a few dozen bytes. That's a denial-of-service primitive known as ReDoS (Regular-expression DoS).

Why this is a security property, not just a speed note. In Level 2 the regexes come only from the operator's own CLI config, so ReDoS is at most a foot-gun. But later levels feed untrusted, attacker-controlled strings into matchers: Level 9 (OS internals / limits) and Level 13 (the basic WAF) evaluate patterns against request paths, headers, and bodies. A backtracking engine there would hand every client a DoS button — send one crafted URL, pin a core for a minute. Because we chose the linear-time regex crate at Level 2, that entire attack class is structurally impossible by the time hostile input arrives. The dependency decision made in the routing level pays off as a WAF safety guarantee two-thirds of the way through the course.

How Ferrum uses it

A ~-prefixed spec is compiled once at startup with Regex::new(pattern); a bad pattern is a startup error (invalid regex), never a runtime surprise. At request time the compiled Regex lives inside the immutable PathMatcher::Regex variant and is tested with re.is_match(path) — one linear scan, no allocation, no lock. Compile-once / match-many is the same shape as the route table itself.

7 · Parsing Route Specs

The CLI grammar is tiny but has one genuine trap, and the parser is structured to defuse it.

The grammar

A route spec is [METHOD ][host]path_expr=TARGET. Examples straight from the code's doc-comments:

SpecParses to
/=127.0.0.1:9000Any → one-server pool (the catch-all)
/api/**=apiPrefix /api/ → declared upstream named api
/files/*=127.0.0.1:9002Wildcard /files/ → one-server pool
POST /upload=127.0.0.1:9004method POST + exact /upload
api.example.com/=B_APIhost api.example.com + Any
~^/v[0-9]+/=127.0.0.1:9005Regex → one-server pool

The trap: = and ;

The target is separated from the matcher by =, so the parser uses rsplit_once('=') to take everything after the last = as the target. But Level 5+ rewrite options are ;-separated and contain their own = (e.g. ;strip=/api). If you split on = first, rsplit_once('=') would grab the option's value (/api) as the route target — a silent mis-route.

The fix, from parse_matchers: sever the ;-options before splitting on =. Order of operations is the whole defense:

  1. spec.split_once(';') — peel off the options string first.
  2. base.rsplit_once('=') — now the last = is guaranteed the target separator.
  3. Peel an optional leading uppercase METHOD (a word of ASCII letters before a space).
  4. A leading ~ means the rest is a regex; otherwise split host from path at the first /.
  5. Classify the path suffix into one of the five matchers.

A consequence the code documents plainly: because options are ;-severed first, a route's options cannot contain a literal ;. That's an accepted limitation, not a bug.

Validation is at startup, not per-request. An empty target, a missing =, a path with no /, or a bad regex all return an io::Error from parse_matchers/resolve_route, which fails the process at boot. The request-time path never has to handle a malformed route — by the time find_route_indexed runs, every route is known-valid.

Industry: nginx / httpd / HAProxy / Envoy

Every production proxy solves "which backend?" — but with different data structures, config models, and precedence rules. Ferrum is a teaching build; here's where it lands honestly against the field. (Architecture as generally understood; qualify specifics with "as of" — behaviors drift across versions.)

nginx

Location matching

Mechanism: location blocks with prefix and regex forms. Prefix matches use a compiled tree; exact (=) and prefix (^~) can short-circuit before regexes are tried. Precedence is a documented, slightly baroque set of rules (exact, then longest literal prefix, then regexes in file order).

vs. ours: nginx's "regexes tried in order" is declaration-dependent; Ferrum ranks regex uniformly below structured matchers and never depends on order except as a final tie-break. Ferrum's rule is simpler to reason about; nginx's is more expressive and far more optimized.

Apache httpd

Location / Directory / rewrite

Mechanism: <Location>, <LocationMatch>, and the mod_rewrite engine (a PCRE-based rule stack evaluated per request). Merging order across container types is intricate.

vs. ours: httpd's mod_rewrite uses a backtracking PCRE engine — powerful (backreferences, lookaround) but exposed to ReDoS if rules touch untrusted input. Ferrum deliberately gives that up for the linear-time regex crate. We trade expressiveness for a safety guarantee.

HAProxy

ACLs + use_backend

Mechanism: boolean ACLs (path_beg, hdr(host), path_reg, …) combined with use_backend ... if <acl>. Rules are evaluated top-to-bottom; first match wins — precedence is declaration order, by design.

vs. ours: the opposite philosophy. HAProxy makes order authoritative and gives the operator full control; Ferrum computes specificity so order can't surprise you. Both are valid; ours is friendlier to "I added a route and everything broke."

Envoy

RouteConfiguration

Mechanism: virtual hosts → an ordered list of routes, each with prefix / path / safe_regex matchers plus header and query matchers. First matching route wins (order-authoritative), and — notably — safe_regex mandates the RE2 engine (linear-time, no backtracking).

vs. ours: Envoy's safe_regex/RE2 is the same insight as our regex-crate choice — both refuse backtracking for safety. Envoy is order-authoritative and dynamically configurable (xDS) over the network; Ferrum is specificity-ranked and configured once at startup.

ProxyData structurePrecedence ruleRegex engine
Ferrum (ours)linear scan over a Vec<Route>computed specificity; order only breaks tiesRust regex (linear-time, no backtracking)
nginxcompiled prefix tree + regex listexact → longest prefix → regex in file orderPCRE (backtracking)

The honest bottom line: Ferrum's O(n) linear scan is fine for a handful of routes and easy to understand, but it does not scale like nginx's compiled tree or Envoy's optimized matchers to thousands of routes. What Ferrum gets right for a teaching build is the two ideas that matter most: order-independent precedence and a linear-time regex engine. The second one puts us in the same safety camp as Envoy's safe_regex.

Glossary

RouteTable

The immutable Vec<Route> built once at startup and shared as Arc<RouteTable>.

PathMatcher

The five-variant enum deciding whether a path matches: Exact / Prefix / Wildcard / Regex / Any.

Specificity

A computed numeric rank; the highest-scoring matching route wins, independent of declaration order.

Longest-prefix-wins

Among matching prefixes, the longest is most specific — the IP-routing-table rule, encoded as 2000 + p.len().

Arc<T>

Atomically reference-counted shared pointer; cloning is a refcount bump, enabling lock-free concurrent reads of immutable data.

Catch-all

A route with path: Any and no host/method constraints (score 0) — the backstop that only wins when nothing else matches; also how Level 1's single-backend behavior is expressed.

ReDoS

Regular-expression denial of service: a backtracking engine driven to exponential time by a crafted input. Structurally impossible with the linear-time regex crate Ferrum chose.

find_route_indexed

The single selection core; also yields the winning route's table index (used by Level 11's cache key). find and find_route both funnel through it.
