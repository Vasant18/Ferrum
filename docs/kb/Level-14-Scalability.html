Executive Summary

Level 14 is the capstone: a theory level that takes the single-instance proxy built across Levels 1–13 and asks the one question the whole design has been quietly deferring — what breaks when there are N of these instead of one?

The method is Level 9's: read the concepts through Ferrum's own code, verify every claim against the tree, and name precisely what would break at N > 1. Four movements. First, who balances the load balancers — the traffic-distribution ladder (DNS round-robin, VRRP/keepalived floating VIPs, anycast, and the L4-tier-over-L7-tier architecture inside every major cloud), with the pleasing recursion that a Maglev-style L4 tier consistent-hashes flows exactly like balancer.rs's chash ring, and hashes the 4-tuple for the same affinity reason iphash exists.

Second, the centerpiece: a state audit of rproxy/src against the design hierarchy don't share / share approximately / share for real. Routes, health, pools, and metrics ship to N instances unchanged. Rate limits, WAF reputation, and the cache go quietly approximate at N > 1 — each with a remedy. Only exactly-once duties (cert renewal) need real consensus, and the honest rule is use a store, don't implement Raft. Third, high availability: the L4 flap-prevention asymmetry generalizes to fleet membership, L10's /health is what an L4 tier consumes, L12's drain is half a rolling deploy, and failure domains stack process → machine → site. Fourth, CDN integration, which lands on three seams this course already built. The closing claim: distributed systems aren't a different subject; they're the same subject, multiplied. Course complete: 14/14 levels, 280 tests, ~13.4k lines, two dependencies (regex, rustls) — everything else from scratch, on purpose.

Theory level, no code. Like Level 9 (OS Internals), nothing in rproxy/src changed. That is the correct outcome, not a shortfall: the single-instance code was built well enough that the fleet story is mostly about which existing state is safe to duplicate — and the surprising answer is "almost all of it."

The Big Picture

Ferrum spent Levels 3–4 deciding which backend gets a request. At cluster scale the same question recurses one layer up: which proxy gets the connection?

In production a Ferrum-shaped proxy is rarely the first thing a packet touches. Above it sit tiers whose only job is to spread load across the proxy fleet, and below it sit the backends it already knows how to balance. The mandatory diagram for this level is that full stack: anycast (or DNS) gets a client to a site; a thin L4 tier inside the site consistent-hashes the 4-tuple onto the L7 fleet; the Ferrum-shaped L7 proxies do the real work; and each proxy load-balances its backends exactly as Levels 3–4 built. Each layer does what it is cheapest at.

Analogy: a single ticket booth (one proxy) has a maximum throughput and shuts the whole show if the clerk faints. A fleet is a row of booths with a greeter at the door (the L4 tier) who sends you to a booth and remembers which one — so your follow-up questions go to the same clerk who has your file open (4-tuple affinity). A second greeter at a second venue (anycast) means even a fire at one venue doesn't close the show.

1 · Who Balances the Balancers?

Once you run more than one proxy, some layer above must decide which proxy a given connection reaches. There are four standard answers, and they are usually layered, not chosen exclusively.

MechanismHow it worksFailover speedThe catch
DNS round-robinPublish N A/AAAA records; a health-checked DNS provider (e.g. Route 53) pulls dead IPs from the answer setMinutes (bounded by TTL)Resolvers cache and clients disobey TTLs — failover is advisory, not enforced
VRRP / keepalivedThe active proxy holds a floating VIP; the standby claims it via gratuitous ARP when the active diesSub-secondActive/passive wastes half the hardware, and it scales to exactly two
AnycastThe SAME IP is announced from many sites via BGP; the internet's routing delivers each client to the nearest siteRoute-convergence (seconds+)Requires owning IP space and running BGP sessions — this is how Cloudflare puts one IP everywhere
L4 tier over L7 tierThin, near-stateless L4 balancers (LVS, Maglev, NLB) consistent-hash flows onto the L7 proxy fleetSeconds, gracefulThe architecture inside every major cloud — but it's one more tier you have to run

The layering in practice reads top-to-bottom: anycast or DNS gets a client to a site; an L4 tier inside the site consistent-hashes the 4-tuple onto the L7 fleet; Ferrum-shaped proxies do the L7 work. Each layer does what it is cheapest at — coarse geographic steering at the top, cheap per-flow steering in the middle, expensive per-request logic (routing, TLS, WAF, caching) at the bottom.

The recursion worth savoring

The best part of this level is that Ferrum already contains the core idea of the tier that would sit above it. Two grep-verified facts:

Same algorithm, one layer up

Maglev = our chash ring

A Maglev-style L4 balancer spreads flows onto proxies using consistent hashing — the identical algorithm balancer.rs:598 builds a ring for when the route uses Algorithm::ConsistentHash (chash). The reason is the same reason we chose it for backends: adding or removing one node reshuffles only ~1/N of the assignments instead of all of them, so a proxy joining or leaving the fleet doesn't scramble every flow.

Same key, same reason

Hash the 4-tuple, don't round-robin

The L4 tier hashes the connection's 4-tuple (src IP, src port, dst IP, dst port) for exactly the reason IpHash exists at balancer.rs:711: affinity to held state. Every packet of one TCP flow must land on the proxy that holds that flow's TCP/TLS state. Round-robin packets across proxies and you'd shatter every connection — packet 2 arrives at a proxy that never saw the handshake.

Analogy: consistent hashing is a coat-check where each coat's ticket number maps to a fixed peg. Add a peg and only the coats near it move; the rest stay put. That's why a proxy can join the fleet mid-day without the L4 tier dropping every live connection — and it's the same ring we already built one floor down.
Which resource can't you just buy more of? Anycast. DNS records, VIPs, and L4 nodes are things you provision. Anycast requires owning routable IP space and running BGP sessions with transit providers — administrative, not purchasable off a shelf. That's the quiz-1 trap.

2 · The State Audit

N proxies must agree on things Ferrum built as single-instance state. The design hierarchy — don't share; share approximately; share for real (rarely) — maps onto a concrete audit of the tree, done by grepping for every static, OnceLock, and per-process shard.

Tier 1 — Ships to N instances unchanged (don't share)

Don't share

Route table / config

RwLock<Arc<RouteTable>> (L12). The identical ferrum.toml is pushed to every instance; SIGHUP is already the reload interface a config-push pipeline would call. The grown-up version is a control plane streaming config (Envoy's xDS) — and L12 unknowingly built the data-plane half: validate wholesale, swap atomically, never die on bad input. A control plane is just "someone else runs reload() for you, over gRPC."

Don't share

Health state

balancer.rs breakers + health.rs probers. Each instance learns independently. N instances probing one backend N times is mild extra load in exchange for total independence — no consensus, and slight disagreement is harmless: an instance that hasn't noticed a recovery yet just routes around a healthy server briefly. "Let each proxy learn" falls straight out of having built health checking with zero shared state.

Don't share

Connection pool (L7)

Per-instance by nature — a pooled backend socket belongs to the process that opened it. Nothing to share; nothing to change.

Don't share

Metrics (L10)

Prometheus was designed for fleets — the scraper aggregates across instances. ferrum_requests_total summed over N proxies is the fleet number. The per-instance registry needs zero changes; the fleet view is a query, not a code change.

Tier 2 — Breaks quietly at N > 1 (share approximately)

These are the dangerous ones, because they don't crash — they silently do the wrong amount. Verified by grepping the tree for process-local state.

Rate limiting — middleware/ratelimit.rs, 16-shard token buckets

A rate=100/s route behind 3 proxies admits up to 300/s — each instance's buckets are blind to the others. The hierarchy applies cleanly:

  • Remedy A — per-instance ÷N: set 33/s per instance. Often exactly the right trade: zero coordination, and the fleet total is what you wanted.
  • Remedy B — Redis loose counts: an async-replicated counter buys a slightly-loose global limit. The 16-shard design generalizes directly — the shards just move from in-process mutexes to Redis keys.
Why not count exactly? Exact distributed counting costs a synchronous round-trip per request to the shared counter. That latency is almost never worth it; the approximate answer is the right trade. This is the quiz-5 cost that rules out exactness.

WAF reputation — waf.rs REPUTATION: OnceLock (L13)

Strikes and bans live in a process-wide OnceLock at waf.rs:523 — so they are per-instance. An attacker spraying a 3-proxy fleet gets 3× the strike budget before every instance has independently banned them. Same shape as rate limiting (a WAF reputation store IS a rate limiter for hostility), so same remedies. The twist: commercial WAFs share reputation across customers, not merely across their own instances — the network effect the vendors treat as a moat, and something a from-scratch build structurally can't replicate.

The response cache — cache.rs (L11)

N independent caches mean N misses per resource and N revalidations — wasteful but correct. Each cache honors the same RFC 9111 rules; nothing leaks and nothing is served stale that shouldn't be. Two fixes, and "don't fix it" is a legitimate one:

  • Don't fix it: a CDN above absorbs the hit rate, making the local cache a second-order optimization.
  • Consistent-hash the cache keys across the tier so each resource has one home proxy — the L3 chash ring making its third appearance (backends → proxies → cache keys).
The pleasant find — active_connections, request-id seeds, ban backoff clocks are all per-instance and all fine. The request-id scheme (L6) already seeds per-process precisely so N instances don't collide in a shared log. That decision was cluster-ready three levels before clusters were on the table.

Tier 3 — Needs real coordination (share for real — rarely)

Share for real

"Exactly one instance does X"

Renew the TLS cert; run the nightly purge. This is leader election: an etcd/ZooKeeper lease — a TTL'd key the leader must keep renewing; lose it (crash, partition) and another instance takes over — built on Raft/Paxos consensus. The honest engineering rule: use an existing store; implementing Raft is its own course. Nothing in Ferrum needs this today.

Share for real

Sessions

The cluster answer to L3's iphash affinity is to make affinity unnecessary — externalize session state (Redis) or carry it in the token (JWT), so ANY proxy and ANY backend can serve ANY user. Statelessness is what makes horizontal scaling linear. iphash remains the fallback when a legacy backend hoards state in memory.

Wasteful vs. wrong — the distinction that matters (quiz 6). N caches are wasteful but correct: redundant work, identical answers. N rate limiters are quietly wrong: they admit N× the intended traffic. The difference is whether the state is a read-through optimization (cache — being wrong just means a miss) or an enforcement budget (rate limit — being wrong means the limit is a lie). Optimizations tolerate duplication; budgets don't.

3 · High Availability — What Actually Pages You

HA at fleet scale isn't new machinery; it's three single-instance mechanisms this course already built, generalized one level up.

The health-check asymmetry generalizes

L4's "down after 3 failures, up after 2 successes" prevents flapping for backends. Fleet membership uses the identical asymmetry for proxies: an L4 tier health-checks its L7 fleet the way health.rs probes backends. L10's /health endpoint is exactly what it would hit — and that endpoint's deliberate "degraded ≠ dead" distinction is what keeps a backend outage from cascading into the proxy tier's removal. A proxy whose backends are down is degraded, not dead; it should stay in rotation to serve cached content and return honest 502s, not be yanked and pile load onto its siblings.

Graceful everything becomes rolling deploys

L12's drain + Connection: close is the per-instance move. The fleet version is "remove from the L4 tier → drain → replace → re-add", orchestrated by Kubernetes or equivalent. The KB already conceded this at L12: in-process graceful restart (FD passing, SO_REUSEPORT) lost to the platform's rolling deploy, because the orchestrator now rolls pods. L12's drain is half of that dance — the "drain" step — and the other half (remove/re-add from the tier) is the orchestrator's job, not the proxy's.

Failure domains stack

Each domain's failure is the next domain's health-check event:

DomainDetectionRecoveryPer-instance analogue built in
ProcessTokio task panics are contained (L12 worker-processes analysis)Supervisor restarts the processL12 — panic containment per task
MachineVRRP peer / L4 tier health check failsVRRP failover or L4 tier reroutes flowsL4 breakers + health.rs probers
SiteBGP session drops / site monitor failsAnycast withdraws the site's BGP announcement(no per-instance analogue — this is genuinely new)
The one genuinely new problem (quiz 14). Almost everything here is a single-instance mechanism enlarged. The exception with no single-instance analogue in this codebase is distributed consensus / leader election (and its cousin, the network partition — "split brain"). A single process never disagrees with itself about who is the leader; a fleet can, and resolving that needs Raft/Paxos machinery that has no counterpart anywhere in Ferrum's tree. That's why the study doc deliberately ends on it rather than on self-congratulation.

4 · CDN Integration — Know Your Place in the Chain

In production, Ferrum-shaped proxies usually sit behind a CDN. Three consequences, and each lands on a seam this course already built.

Seam: L5 + L8

The "client IP" is a CDN node

L5's trust rules (overwrite X-Real-IP, append to XFF, key limits on the socket peer) need one refinement: a published allowlist of CDN ranges from which X-Forwarded-For may be trusted. L8's CidrList is literally the machinery (security.rs) — --allow-cidr pointed at trust rather than admission.

Seam: L11

The cache becomes layer two

The CDN's edge sites absorb the hit rate; L11's cache catches what leaks through. s-maxage vs max-age (L11 honored both) is exactly how an origin speaks to the two layers differently — a long shared-cache TTL for the CDN, a short/absent private TTL for the browser.

Seam: L7 + L1

Origin pull is a keep-alive client

A CDN node multiplexing thousands of users over a few hot connections is the ideal customer for L7's connection pools and L1's keep-alive loop. Nothing to change — the design that made pooling worthwhile makes CDN origin-pull cheap.

How Industry Does It

Ferrum is a single-instance teaching build; the fleet story is theory. Here's how the production proxies actually solve "who balances the balancers" and the shared-state problem — and honestly where ours would sit.

nginx

Instance + external orchestration

A single nginx is, like Ferrum, one process (well, one master + N workers). Fleet HA is bolted on around it: keepalived/VRRP for VIP failover, or an upstream L4 (nginx itself can be the L4 tier via stream). Shared rate limiting needs the commercial nginx Plus (zone sync) or a Lua/Redis module. Our per-instance ÷N story is exactly the open-source nginx story.

Apache httpd

The oldest model, least fleet-native

httpd's process/thread MPMs predate the cluster era; HA is entirely external (VRRP, a hardware LB, or a CDN in front). Shared reputation/rate state across instances isn't a first-class concept — mod_qos and friends are per-process, the same limitation Ferrum has. It's the clearest example of "the fleet lives outside the proxy."

HAProxy

Built to be the L4/L7 tier

HAProxy is frequently the L4-over-L7 tier itself, and it has real fleet features: stick-tables with peer synchronization propagate rate-limit counters and reputation across a cluster (approximately, async — exactly the Redis-loose-count trade we described). This is the mature version of Ferrum's biggest gap; ours would need Redis to reach parity.

Envoy

Data plane + control plane, split by design

Envoy is a pure data plane; configuration streams in over xDS from a separate control plane (Istio, etc.). This is precisely the split L14 names: L12's validate-wholesale/atomic-swap reload is Envoy's data-plane half already built; the other half (gRPC config streaming, service discovery, fleet-wide push) is what a control plane adds. Envoy is the north star this whole course was quietly triangulating toward.

Honest placement. On shared fleet state, Ferrum today is at the open-source-nginx / httpd tier: per-instance, no cross-instance sync. HAProxy's stick-table peers and Envoy's xDS are the two directions ours would grow. The satisfying part — and the point of this level — is that the shapes already match: our reload IS xDS's data plane, our chash ring IS Maglev's, our breakers ARE fleet membership. The gap is coordination plumbing, not architecture.

Glossary

Anycast — one IP address announced from many physical sites via BGP; the internet routes each client to the nearest. Requires owning IP space + BGP sessions.

VRRP / keepalived — an active proxy holds a floating VIP; a standby claims it via gratuitous ARP on failure. Sub-second failover, scales to exactly two.

L4 tier / L7 tier — L4 balancers steer whole TCP flows (fast, near-stateless); L7 proxies (Ferrum) do per-request logic. Production layers L4 over L7.

4-tuple — (source IP, source port, destination IP, destination port); the identity of a TCP flow. The L4 tier hashes it so every packet of a flow lands on the same proxy.

Maglev — Google's consistent-hashing L4 load balancer; the production embodiment of the same ring Ferrum's chash builds.

Consistent hashing — a hashing scheme where adding/removing one node reshuffles only ~1/N of keys, not all of them. Used at three layers: backends, proxies, cache keys.

xDS — Envoy's family of gRPC discovery APIs by which a control plane streams config to data-plane proxies. L12's reload is its data-plane half.

Control plane / data plane — the data plane moves packets/requests (Ferrum); the control plane decides config and pushes it. L12 built the data-plane half of config management.

Leader election — picking exactly one instance to perform a singleton duty, via a TTL'd lease on a consensus store (etcd/ZooKeeper). The one genuinely new fleet problem with no single-instance analogue here.

Lease — a key with a TTL the holder must keep renewing; losing it (crash/partition) hands the role to another instance. (Distinct from Ferrum's L3 RAII Lease, which is inflight-connection accounting.)

Rolling deploy — replace fleet instances one at a time: remove from the L4 tier → drain → replace → re-add. L12's drain is the middle step.

Failure domain — a blast radius (process / machine / site); each domain's failure is the next domain's health-check event.

Wasteful vs. wrong — duplicated read-through state (cache) is wasteful but correct; duplicated enforcement budgets (rate limits) are quietly wrong because they multiply the limit.
