Caching
a shared RFC 9111 cache — the fastest backend request is the one you never make

Level 11 turns Ferrum into a shared HTTP cache that honors the protocol's caching contract rather than inventing one. Two halves in one file, cache.rs: a bounded, sharded, approximately-LRU, TTL-expiring store that knows nothing about HTTP; and a set of pure functions that encode RFC 9111's cacheability rules and know nothing about locking. The level's whole danger is concentrated in one place — the cache key — because getting it wrong is how a shared cache leaks one user's data to another.

Executive Summary

Level 11 makes Ferrum a shared cache in the RFC 9111 sense: it sits between many clients and an origin, so every rule the protocol writes for shared caches (private, s-maxage) applies to us specifically.

The store (cache.rs) is 16 Mutex<Shard> shards, each a HashMap<Key, Entry> with a running byte total. It is doubly bounded — --cache-max-bytes (default 64 MB, the real bound because bodies dominate) and --cache-max-entries (default 4096, a metadata bound so a million tiny responses can't balloon the map). Recency is approximate: each entry carries a last_used Instant; on an insert that overflows a bound, the shard scans itself for the oldest and evicts. That is not the textbook O(1) linked-list LRU — which is "famously miserable" in safe Rust because aliasing-plus-mutation is exactly what the borrow checker rejects (and rightly: LRU aliasing bugs are real CVEs in C caches). TTL is lazy (checked on lookup, no sweeper task), and bodies are Arc<[u8]> so a hit is a refcount bump and an entry evicted mid-stream stays alive until the response finishes.

The semantics half is pure functions over head structs: GET-only, status 200/301/404, hard no on request Authorization and response Set-Cookie, s-maxage beats max-age for a shared cache, no-cache means store but always revalidate while no-store means never write, private means a shared cache must not, Vary becomes a two-step keyed lookup with a tiny index entry, Vary: * is uncacheable, and the route's default TTL applies only when the response carries a validator.

The cache key is the level's one dangerous decision: route index + pre-rewrite host/target + each Vary header's value, stored in full and compared by struct equality so a hash collision degrades to a miss, never to another user's data. A KeyInput snapshot is taken before Level 5 rewrites the live head, because the cache is consulted twice per exchange.

Lookup runs after the middleware chain (a 401'd client gets no cache read) and instead of the balancer lease on a hit (no socket, no breaker traffic). Both revalidation legs ship: proxy→origin conditional requests (a 304 re-stamps and serves, X-Cache: REVALIDATED) and client→proxy conditionals (client's If-None-Match → 304 with no body). A TeeWriter captures streamed bodies relay-first, capturing only what the wire accepted, and silently cancels the store on overflow. Unsafe methods invalidate per RFC 9111 §4.4. 250 unit tests (230 kept green, +20) and 13 live checks, all green.

The Big Picture

Caching is the one stage in the pipeline that can short-circuit everything downstream of it. On a fresh hit, the request never reaches the load balancer, never opens a backend socket, never touches a circuit breaker — the whole right-hand side of the pipeline goes dark.

The lookup is deliberately placed after the middleware chain and before the balancer lease. That ordering is the design: a cached response must never bypass auth or rate limiting (so the chain runs first), but a hit must skip the backend entirely (so the lease is what it replaces). The highlighted stage below is where this level lives.

Analogy: a shared cache is the concierge desk in a big office building. When a courier asks for "the Q3 report for the 14th floor," the concierge who already has a fresh copy hands it over without calling upstairs (a hit — no backend). If the copy might be stale, the concierge phones up and asks "still the same version?" — a five-second call, not a re-delivery (revalidation). The one thing the concierge must never do is hand a personalized, signed-for envelope (an Authorizationed or Set-Cookie'd response) to the next person who asks — that is the whole reason the desk has strict rules about what it will keep a copy of.

The Store: sharded approximate-LRU

The storage engine (Section 1 of cache.rs) knows nothing about HTTP. It is a bounded, sharded, approximately-LRU, TTL-expiring HashMap<Key, Entry>. Every design choice here is a deliberate rejection of a "more correct" textbook alternative that costs unsafe, a dependency, or speed we cannot measure.

Why NOT the O(1) linked-list LRU

The textbook cache is a hash map into a doubly-linked recency list: O(1) to look up, O(1) to move-to-front on a hit, O(1) to evict the tail. In C it is a rite of passage. In safe Rust it is famously miserable — a doubly-linked list is aliasing (every node points at its neighbours) plus mutation (splicing a node moves those pointers), which is precisely the pattern the borrow checker rejects. And it is right to reject it: LRU splice bugs — use-after-free when a node is evicted while another path holds it — are real CVEs in C caches.

The alternatives are an index arena (a Vec<Node> with integer "pointers", correct but a second allocator to hand-maintain), a dependency (against the course's zero-deps rule), or what concurrent production caches actually do: shard the map and accept approximate recency. Ferrum takes the third. It is Level 6's 16-shard rate-limiter idiom with a bigger value type, so the codebase already contains the pattern.

The cost accounting, stated plainly. Approximate-LRU eviction scans one shard for the entry with the oldest last_used — O(shard), but only on the insert-when-full path. The hit path pays one hash, one short lock, one Instant store — the same as any hash map. A true O(1) recency list would optimize a path already measured in nanoseconds, at the cost of unsafe or an arena nobody asked for. The doc comment in cache.rs says exactly this.

16 shards, per-shard byte + entry budgets

Cache holds Vec<Mutex<Shard>> with SHARDS = 16. A Shard is { map: HashMap<Key, Entry>, bytes: u64 }. The shard is the unit of locking, so it must also be the unit of accounting — otherwise an insert would need two locks and an ordering discipline. Both bounds are enforced per shard at total / 16:

  • max_bytes_per_shard — the real bound; bodies dominate memory. Default 64 MB total → 4 MB/shard.
  • max_entries_per_shard — a metadata bound so a flood of 10-byte responses can't balloon the map itself. Default 4096 total → 256/shard.

The discipline matches every lock since Level 6: a plain fn, a lock scope of a few lines, never held across an .await (compiler-enforced, per Level 9's audit). The probe, insert, restamp, and invalidate methods each take the shard lock, do their map work, and drop it before anything can suspend.

// cache.rs — eviction scans THIS shard only, oldest last_used first
while !shard.map.is_empty()
    && (shard.bytes + new_cost > self.max_bytes_per_shard
        || shard.map.len() + 1 > self.max_entries_per_shard)
{
    let oldest = shard.map.iter()
        .min_by_key(|(_, e)| e.last_used)   // O(shard) scan
        .map(|(k, _)| k.clone());
    // ... remove it, subtract its cost, count an eviction ...
}
Watch out: a single body larger than max_bytes_per_shard is never stored (the final if new_cost > self.max_bytes_per_shard { return; }) — otherwise one giant response would evict an entire shard to make room for itself and still not fit. The store fails open: too-big-to-store is not an error, the request already streamed to the client fine.

Lazy TTL: no sweeper task

Expiry is checked on lookup, via Entry::is_fresh(now) = now.duration_since(stored_at) < ttl. There is no background sweeper. Level 9 counted exactly three spawn sites in the whole proxy; a sweeper would be a fourth, buying memory reclamation a few seconds earlier than the next insert-eviction would anyway.

More importantly, an expired entry is not garbage. If it carries a validator (ETag or Last-Modified), it is a revalidation candidate — worth keeping precisely because a 304 re-stamps it without re-transferring the body. So on lookup an expired entry splits: with a validator → Lookup::Stale; without → treated as a miss and eagerly removed right there (freeing its bytes immediately rather than at the next eviction scan).

Bodies are Arc<[u8]>: refcount-bump hits, evict-during-stream safe

An Entry.body is an Arc<[u8]>, not a Vec<u8>. Three properties fall out for free:

  • A hit is a refcount bump, not a copy. probe returns a CachedResponse holding Arc::clone(&e.body) — one atomic increment, regardless of body size.
  • Eviction racing a streaming hit is safe. If a hit already cloned the Arc and is streaming those bytes to the client when another thread evicts the entry, the Arc's refcount keeps the buffer alive until the streaming response finishes. No copy, no use-after-evict.
  • No lock near an .await. The snapshot is cheap enough that the shard lock is dropped the instant probe returns — the bytes stream to the client with no lock held anywhere near the suspend point.

CachedResponse is a snapshot, not a guard borrowing from the shard, precisely so that nothing borrowed from the map survives past the lock. That is what lets the store hand out a response and immediately release the shard for other threads.

RFC 9111 Semantics

The second half of cache.rs is pure functions over head structs — no locking, no I/O. They encode what the protocol says a shared cache may do. Caching is opt-in per route (;cache[=SECS]); once enabled, the HTTP decides the rest per response.

Opt-in per route, then the protocol decides

A route enables caching with the ;cache option (bare, or ;cache=SECS for a default TTL). This is a new L11_KEYS = ["cache"] arm in the router's existing option partition (router.rs); Route.cache_ttl is Some(default_ttl) when set, None means the route never caches. Off by default — a proxy that silently starts caching is a behavior change an operator must ask for (nginx's proxy_cache is opt-in for the same reason). rewrite.rs and the middleware module needed no changes.

Once enabled, request_is_cacheable and freshness_from_headers gate every exchange:

GateRuleWhy
MethodGET onlyNot HEAD (serving a cached GET body to a HEAD is wrong the other way).
Request Authorizationhard no — no read, no write, no X-Cache at allThe KB's "worst bug class" is a shared cache serving one user's authorized response to another.
Status200, 301, 404 only200 is the point; 301 is permanent by definition; 404 shields the backend from retry storms on dead links.
Response Set-Cookienever storeUser-specific, full stop — replaying one user's cookie is a session-fixation machine.
Body size≤ --cache-max-body (1 MB)Keeps one response from monopolizing a shard's budget.

TTL: s-maxage beats max-age for a shared cache

freshness_from_headers parses Cache-Control and picks the TTL with s_maxage.or(max_age) — s-maxage wins whenever present. This is not arbitrary: s-maxage is the directive addressed to shared caches specifically, and Ferrum is the shared cache it was written for. A browser (a private cache) ignores s-maxage and uses max-age; Ferrum does the opposite.

If neither directive is present, the route's DEFAULT_TTL applies — but only when the response carries a validator (ETag or Last-Modified). Freshness we invent must at least be revalidatable; a response with no explicit freshness and no validator is not stored at all.

// cache.rs — the TTL decision, after directive parsing
let ttl = match s_maxage.or(max_age) {
    Some(secs) => Some(Duration::from_secs(secs)),
    None if has_validator => Some(default_ttl),   // invented, but checkable
    None => None,                                  // do not store
};

The confusables, handled by name

directive

no-store

Never write. Return ttl: None — the exchange is not cached at all, on either the request or response side.

directive

no-cache

Store, but revalidate before EVERY use. Expressed as ttl: Some(Duration::ZERO) + a validator — with no validator, don't store (revalidation would be impossible). Zero TTL means is_fresh is always false, so every lookup returns Stale and revalidates — no special case in the lookup path.

directive

private

The browser may cache this; a shared cache must not. We are the shared cache the directive was written for → ttl: None.

directive

Vary

The named request headers' values join the cache key (two-step lookup below). Vary: * = "depends on things you cannot see" = uncacheable → ttl: None.

Directive names are compared case-insensitively (RFC 9111 §5.2: MAX-AGE = max-age); quoted values are unquoted before parsing.

Vary: the two-step keyed lookup

The caller cannot know which request headers belong in the key until a stored response's Vary says so — a chicken-and-egg the code solves with a probe-then-probe dance and a tiny vary-index entry.

  1. Probe 1 — build the key with an empty Vary list and look it up. For a non-varying resource, this is the entry (a hit or miss, done).
  2. The index entry — for a varying resource, the vary-less slot holds a tiny bodyless entry whose only job is to record which headers matter (its vary_names). It is written alongside every variant on store, and is never itself servable (probe returns Probe::VaryIndex(names) for it).
  3. Probe 2 — rebuild the key with this request's values for those named headers, and look up the real variant. An absent named header contributes the empty string — a distinct variant per RFC 9111 §4.1.

Live-verified: Vary: Accept-Encoding stored a gzip variant and a plain variant separately and served each requester its own body.

The Cache Key: the dangerous decision

The KB names the cache key "the worst bug class in this level" — worse than any crash, because getting it wrong is how a shared cache leaks one user's data to another. Every field of Key, and every casing rule, IS a security argument.

What is in the key, and why each field

// cache.rs
#[derive(Clone, PartialEq, Eq, Hash, Debug)]
pub struct Key {
    pub route: usize,                    // routes must NOT share entries
    pub method: String,                  // GET (invalidation matches on it too)
    pub host: String,                    // ORIGINAL host, port-stripped, lowercased
    pub target: String,                  // ORIGINAL target (path + query), pre-rewrite
    pub vary: Vec<(String, String)>,     // each Vary header's (name, value), sorted
}
  • Route index — two routes can rewrite the same client target into different backend requests; their entries must never mix.
  • Pre-rewrite host + target — keyed on what the client asked for, captured before Level 5 rewrites either. Keying on post-rewrite values would merge distinct client resources that happen to rewrite to one backend path.
  • Host: port-stripped, lowercased — host comparison is case-insensitive; EXAMPLE.com and example.com are one resource. (Verified by test hosts_do_not_share_entries_and_host_is_case_insensitive.)
  • Vary values: names lowercased (case-insensitive lookup), values verbatim (case-sensitive), names sorted — wire order of headers must not split one variant into two entries.

Full-struct equality: a collision degrades to a miss, never to another user's data

The hash only picks the shard (shard_index hashes the key % 16). The lookup itself is HashMap::get(key), which compares by derive(PartialEq) — full struct equality. So if two genuinely different keys happen to hash identically, they land in the same shard but compare unequal, and the lookup is a clean miss. A collision costs a wasted probe; it can never serve the colliding entry's body.

Danger avoided: the alternative — trusting the hash and skipping the field comparison — is the classic cache-poisoning primitive. Two different URLs (or two different Vary variants, or two different routes) that collide would serve each other's bodies. Because the comparison is by content, that is structurally impossible here: this is why the collision test needs no assertion beyond "different keys → miss."

Why KeyInput is a snapshot

The cache is consulted twice per exchange: a lookup before the Level 5 rewrite, and a store/restamp after the response returns. Between those two moments the live RequestHead is mutated in place — target stripped, Host clobbered, headers injected. Keying on the mutated head at store time would silently change what "the same resource" means between the two consultations.

KeyInput is the fix: a cheap struct capturing route, method, the pre-rewrite host, target, and a copy of the request headers, taken once via KeyInput::from_request on caching routes only. Key::build(&input, &vary_names) then produces the same key at lookup and at store — the head can be rewritten in between, and the key does not care.

Note on the returned key. Lookup::Stale carries the key it was found with. By the time a 304 comes back and restamp runs, the live head has been rewritten and can no longer rebuild that key — so the entry can only be found again by the key Stale captured. This is the same "snapshot because the live head moves" reasoning, one layer deeper.

Placement: after middleware, instead of the lease

Where the lookup sits in serve_one is as much a security decision as the key. Two rules: it runs after the middleware chain, and on a hit it runs instead of the balancer lease.

After middleware — a 401'd client gets no cache read

The lookup lives after the Level 6 middleware chain has run (auth, rate limiting, request-id). A cached response must never bypass those. If the lookup ran before the chain, a client blocked by auth or throttled by the rate limiter could still be served a cached body — the cache would neuter the very middleware protecting the resource. So a 401'd or 429'd client never reaches the cache read at all.

This is different from the Authorization gate. The Authorization request-header gate (in request_is_cacheable) is about storage safety — never keep or serve a copy of a per-user authorized response. The after-middleware placement is about access control — never let a cache hit skip a policy check. A resource can be publicly cacheable yet still rate-limited; only the placement rule catches that.

Instead of the lease — the shield goes dark on a hit

A fresh hit calls serve_cached and returns without ever taking a balancer lease. That means, on a hit, three pieces of Level 3/4 machinery never see the request: no backend socket is opened, no circuit-breaker traffic is recorded, no inflight/least-connections count moves. This is the cache as a shield — the backend is protected from load it never learns about.

The hit then runs the same client-leg pipeline as a forwarded response: middleware response phase (request-id, logging), Level 5 apply_response rules, the framing/Connection block. Cached and forwarded responses are indistinguishable to everything downstream except for the X-Cache and Age headers — and those are set before the chain/L5 passes, so an operator's explicit response rule keeps the last word (Level 5's ordering principle, appearing a third time).

// proxy.rs serve_one — the lookup, after the middleware chain
if let Some(default_ttl) = route.cache_ttl {
    let (req_no_store, req_no_cache) = cache::request_cache_control(&req);
    if cache::request_is_cacheable(&req) && !req_no_store {
        let key_input = cache::KeyInput::from_request(route_idx, &req, client_host);
        if !req_no_cache {
            match cache.lookup(&key_input) {
                Lookup::Hit(cached)  => { /* serve_cached, NO lease */ }
                Lookup::Stale { .. } => { /* set If-None-Match, forward */ }
                Lookup::Miss         => { ctx.cache = Some("miss"); }
            }
        }
        cache_plan = Some((key_input, default_ttl)); // remembered for store
    }
}

What is stored: the origin's response, not the client's

The entry captures the origin's response — snapshotted after strip_hop_by_hop(resp) but before the client-leg mutations. Hop-by-hop headers (Connection, Transfer-Encoding) are connection-specific by definition; the client-leg headers describe this client's connection, not the resource. Storing either would poison the next client with the wrong connection semantics.

The one gap found live and fixed. A miss on a caching route originally carried no X-Cache header, making a caching route's miss indistinguishable from an uncached route. X-Cache: MISS is now set on the forwarded path — after the cache snapshot (the stored entry must stay free of per-exchange annotations) and before the chain/L5 passes.

Revalidation, Both Legs

Revalidation is the ETag lesson: instead of re-transferring a payload, ask the origin (or answer the client) "still the same version?" with a one-line conditional. Ferrum implements both directions.

Proxy→origin: If-None-Match → 304 re-stamps and serves

When a lookup returns Lookup::Stale, the entry is expired but has a validator. The outbound request is turned conditional: the cache's ETag is set as If-None-Match (else Last-Modified as If-Modified-Since) on the forwarded head.

  • Origin answers 304 → restamp(key, ttl_from_304(...)) resets stored_at and ttl (TTL from the 304's own Cache-Control, else the route default), then serves the cached body. One tiny round trip, no payload re-transfer. Counted as revalidated, header X-Cache: REVALIDATED. Live-verified with the origin hit count frozen at 1.
  • Origin answers 200 → normal miss path, the entry is replaced via the tee.
  • Entry vanished under us (evicted between lookup and 304) → restamp returns None; the exchange falls back to an uncacheable pass-through, logged as 304 for evicted cache entry; passing through.
The client's own conditional was replaced. If the client sent its own If-None-Match, the proxy→origin leg overwrites it with the cache's validator — otherwise the origin would answer the client's question, not the cache's. The client's conditional is snapshotted first (client_inm) so serve_cached can still answer it locally (next card).

Client→proxy: If-None-Match matches → 304 with no body

On a fresh hit (or after a successful restamp), if the client sent an If-None-Match that matches the entry's ETag and the entry is fresh, the proxy answers 304 with no body, straight from the cache — the client already has the bytes; save the transfer.

The full weak/strong comparison rules of RFC 9110 §13.1.2 collapse to etag_matches: strip any W/ prefix, compare octet-exact (quotes included), and honor * (matches any entity) and comma-lists. The 304 head carries only the caching-relevant subset (ETag, Cache-Control, Vary, Last-Modified, Expires) — never Content-Type/Content-Length, verified by not_modified_head_carries_caching_headers_only.

Scope cut, recorded not forgotten. Client-side If-Modified-Since is not answered at the proxy — it needs HTTP-date parsing and ordering, and the ETag path answers the same question better wherever an ETag exists. Entry still keeps Last-Modified for the proxy→origin leg, where the origin does the comparing, not us.

The Body Tee

The cache must capture streamed response bodies without breaking Level 1's flat-memory guarantee (every byte touched once, no unbounded buffering). TeeWriter is the answer: a thin AsyncWrite wrapper around the client sink that captures a copy as it relays.

Relay first, capture what was accepted

TeeWriter::new(client.stream_mut(), cache.max_body as usize) wraps the client-side sink inside the existing copy_body_to loop. Its poll_write relays first, then captures only the bytes the inner sink actually accepted:

// proxy.rs — TeeWriter::poll_write
match Pin::new(&mut *me.inner).poll_write(cx, data) {
    Poll::Ready(Ok(n)) => {
        if !me.overflow {
            if me.buf.len() + n > me.cap {
                me.overflow = true;
                me.buf = Vec::new();          // free eagerly; store is cancelled
            } else {
                me.buf.extend_from_slice(&data[..n]);  // only the n accepted
            }
        }
        Poll::Ready(Ok(n))
    }
    other => other,
}
Why "only what was accepted" matters. A short write (the inner sink accepts n < data.len()) is normal for a socket. If the tee captured all of data anyway, the cached body would run ahead of what the client actually received — a corrupted entry that later serves bytes the origin sent but this transfer never confirmed. Capturing exactly &data[..n] keeps the buffer in lockstep with the wire.

Overflow cancels the store silently

If the captured buffer would exceed --cache-max-body mid-stream, the tee sets an overflow flag, drops the buffer eagerly, and keeps relaying. The client's transfer is completely unaffected — it never learns the store was abandoned. Overflow cancels the store rather than erroring the exchange because a cache must fail open: the request is already succeeding for the client, and "too big to cache" is not a reason to break a working response.

This is the level-wide stance: cache full, oversized body, poisoned shard mutex — every cache decision fails open. The request proceeds uncached and only the metrics see it.

Invalidation & Observability

Two smaller pieces close the level: RFC 9111 §4.4 invalidation for write-through correctness, and the Level 10 observability surfaces the cache pays forward into.

Unsafe-method invalidation (RFC 9111 §4.4)

A non-error (2xx/3xx) response to an unsafe method (POST/PUT/DELETE/PATCH) through a caching route removes every variant of that URI's cached GET entry — all Vary variants and the index. Cache::invalidate(route, host, target) scans all shards for keys matching route + host + target + method == "GET" and removes them, counting each.

This buys write-through correctness for the common CRUD shape: update-then-read sees the update. Live-verified as HIT → POST → MISS with a fresh origin hit.

Why the next GET is a MISS, not a fresh entry. Invalidation removes the entry; the POST response itself does not refresh the cache. The POST response is the answer to a different request (a POST, not a GET) — caching its body under the GET key would violate the RFC's method-keyed model and could serve a mutation's response to a reader. Correct behavior is: forget what you knew, re-fetch on the next read. No admin purge endpoint this level — a real purge API belongs with Level 12's config story.

Observability: L10 pays forward

  • Metrics: one counter family, ferrum_cache_events_total{result="hit"|"miss"|"revalidated"|"stored"|"evicted"|"invalidated"}, rendered by Cache::render_prometheus inside cache.rs itself and appended to the Level 10 exposition by the admin listener — one scrape, one document. Same no-alloc discipline: fixed label set, atomics, zero-value series elided.
  • Response headers: X-Cache: HIT|MISS|REVALIDATED on cached routes; Age on hits (seconds since stored_at), per RFC.
  • Access log: a "cache" field (middleware/mod.rs ctx.cache: Option<&'static str>) → "hit"|"miss"|"revalidated"|null (null = route not cached / request not cacheable).

Recorded Debt

Some things were deliberately left out — recorded, not forgotten, so the quiz can ask about them. The largest is stampede defense.

No stampede defenses (the level's known debt)

When a popular entry expires, every concurrent request for it misses at once and all of them stampede the origin — the dog-pile. Ferrum ships no defense against this. The three classic mitigations are all out of scope:

debt

Coalescing / singleflight

Let one request fetch while the other 999 wait on the result. The KB calls this "a lovely exercise" — and a second synchronization design on top of a level that already has one. Its own lesson.

debt

stale-while-revalidate

Serve the stale copy immediately while revalidating in the background. Needs a background spawn (the fourth site L9 was avoiding).

debt

TTL jitter

Randomize expiries so a batch stored together doesn't all expire together. Cheap, but pointless without one of the above.

Also out: disk persistence (memory only — a restart is a cold cache, correct for a teaching proxy and most edges), stale-if-error, range requests, and Warning headers (YAGNI). A revalidation against a dead backend follows the existing connect-retry/breaker path and, with no stale-if-error, the client gets the same 502 an uncached request would — the stale entry is not served.

How Industry Does It

HTTP caching is one of the most mature areas in the proxy world — RFC 9111 is a shared contract, so the semantics converge, but the storage engines and stampede defenses diverge sharply. Here is where Ferrum sits, honestly, as a teaching build.

ConcernnginxApache httpdHAProxyEnvoyFerrum (ours)
Storage proxy_cache: on-disk store with an in-memory keys zone; shared across workers. mod_cache + mod_cache_disk (or socache): mostly disk-backed. Small in-memory object cache (cache section); intended for tiny hot objects, not a general store. In-memory by default; pluggable cache filter with custom backends. In-memory only, 16 Mutex shards, Arc<[u8]> bodies. No disk.
Eviction LRU-ish via the cache manager process; inactive + max_size. Time + size limits; periodic htcacheclean. TTL + size; small by design. Configurable; LRU-family. Approximate LRU: per-shard scan for oldest last_used, no recency list.
Key Configurable proxy_cache_key (default scheme+host+uri); Vary honored. URL + Vary-derived. Config-driven key. Route + Vary; customizable. Route index + pre-rewrite host/target + Vary values; full-struct equality so collisions degrade to a miss.
Revalidation Conditional GETs to origin; proxy_cache_revalidate on. Conditional requests via mod_cache. Limited (small-object focus). Full conditional support. Both legs: proxy→origin If-None-Match/304 re-stamp; client→proxy If-None-Match→304.
Stampede defense proxy_cache_lock (coalescing) + proxy_cache_use_stale updating (serve-stale). CacheLock directive. Minimal. Coalescing / request collapsing available. None — recorded debt (coalescing, stale-while-revalidate, TTL jitter all out of scope).
Invalidation PURGE via 3rd-party module; RFC §4.4 on unsafe methods. mod_cache honors invalidation. Limited. Filter-dependent. RFC 9111 §4.4 unsafe-method invalidation only; no purge API this level.
The honest trade-off. Ferrum's cache is a faithful teaching implementation of RFC 9111's semantics — the confusables (no-cache vs no-store, private, s-maxage), the Vary two-step, both revalidation legs, and the security-critical key are all correct. Where it is deliberately crude next to production caches: it is memory-only (nginx and httpd survive a restart with a warm disk cache; Ferrum does not), its eviction is an O(shard) scan rather than an O(1) recency structure (fine at 64 MB, would not scale to a multi-GB edge cache), and it ships no stampede defense at all — the one gap that bites hardest under real load, and the one the KB most wants Vessey to be able to design from first principles (see the last quiz question). It is a shared cache you could read end to end in an afternoon, which is the point.

Quiz

Copied verbatim from PROGRESS.md § "Level 11 quiz — Vessey to answer before Level 12". Answers are Vessey's to write.

  1. The KB calls the cache key "the worst bug class in this level." Walk through what happens, request by request, if the key omits (a) the Vary values, (b) the route index, (c) the original pre-rewrite target. Which of the three leaks one user's data to another?

  2. Why does the lookup compare full key structs when the hash already picked the shard? What exactly goes wrong if two different keys hash identically and the code trusts the hash?

  3. no-cache and no-store differ by one word and by everything. What does each direct this cache to do, and how does the code express "store but revalidate before every use" without a special case in the lookup path?

  4. Why does s-maxage override max-age for Ferrum but not for a browser? What kind of cache is each directive addressed to?

  5. The route's ;cache=SECS default TTL applies only when the response carries a validator. What could a validator-less response with invented freshness do that a validated one cannot, and why is that asymmetry worth a rule?

  6. Vary lookup takes two probes. What does the first probe's entry store for a varying resource, why can't the caller build the right key in one step, and what happens to a request whose named header is absent?

  7. A fresh hit skips the balancer lease entirely. Name three distinct pieces of L3/L4 machinery that consequently never see the request, and argue in each case whether that blindness is correct.

  8. The cache lookup runs AFTER the middleware chain. What specific attack works if it runs before? Which L6 middleware would it neuter, and how is that different from the Authorization request-header gate?

  9. Proxy→origin revalidation replaced the client's own If-None-Match with the cache's validator. Where did the client's conditional go, and how does the client still get its 304 when its validator matches? Trace both the fresh-hit and the revalidated-stale paths.

  10. TeeWriter captures "only what the inner sink actually accepted." What corruption does that clause prevent, and why does overflow cancel the store instead of erroring the exchange?

  11. The stored entry snapshots headers after strip_hop_by_hop but before the middleware response phase, L5 response rules, and the framing block. For each of the three, give a concrete header that would be wrong in the cache if the snapshot moved after it.

  12. POST-invalidation removes the entry but the next GET is a MISS, not a fresh entry. Why doesn't the POST response itself refresh the cache, and what RFC-shaped assumption would that violate?

  13. Eviction scans the shard for the oldest last_used instead of keeping a recency list. State the exact asymptotic costs of both designs on the hit path and the insert-when-full path, and the argument for paying the scan here.

  14. The level ships with no stampede defense. Describe the dog-pile scenario concretely (numbers welcome), then sketch how request coalescing would fit THIS codebase — which type would own the in-flight map, and what Tokio primitive would the 999 waiters block on?

Glossary

TermMeaning
Shared cacheA cache serving many clients from one origin (vs a browser's private cache). RFC 9111's private/s-maxage rules are written for exactly this — Ferrum is one.
Approximate LRURecency tracked with a per-entry last_used timestamp and an O(shard) scan on eviction, instead of an exact O(1) recency list — trades a little accuracy for no unsafe.
Sharded lockingSplitting the map into N independently-locked shards so concurrent access rarely contends. L6's rate-limiter idiom, reused.
Lazy TTLExpiry checked on lookup rather than by a background sweeper; expired-with-validator entries survive as revalidation candidates.
Vary-index entryA tiny bodyless entry at the vary-less key that records which request headers a varying resource depends on, enabling the two-step lookup.
RevalidationAsking "still the same version?" with a conditional request (If-None-Match/If-Modified-Since) instead of re-transferring the body; a 304 answers "yes."
Re-stampResetting a stale entry's stored_at and ttl after a 304 so it is fresh again without re-fetching the body.
TeeSplitting a byte stream so it goes to the client and a capture buffer at once; TeeWriter does this relay-first.
Fail openOn any cache failure (full, oversized, poisoned lock) the request proceeds uncached rather than erroring — a cache must never break a working response.
Dog-pile / stampedeMany concurrent requests all missing on the same freshly-expired entry and hammering the origin at once; Ferrum has no defense (recorded debt).
