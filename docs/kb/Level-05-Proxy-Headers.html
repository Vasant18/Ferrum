Being Honest About the Request
Four forwarded headers, three different policies, and a path rewriter that won't lie to the backend

Level 5 turns a dumb forwarder into a real reverse proxy. It tells the backend who really called (X-Forwarded-For, X-Real-IP, X-Forwarded-Host, X-Forwarded-Proto) and lets the proxy present a different URL space than the backend serves (segment-aware strip/prefix, Host rewrite, request/response header rules). Everything is a pure synchronous transform over a head struct — no sockets, no async — so the whole level is unit-testable. The security lessons live in the differences: XFF appends, X-Real-IP overwrites, XFH/XFP set-if-absent.

Executive Summary

Level 5 is where the proxy stops pretending the request came from itself and starts telling the backend the truth.

Through Level 4 the backend saw a request on the proxy's own terms: the client's IP was lost, the original Host was whatever the client sent, and the path was whatever the client asked for. Level 5 adds the two halves of being a reverse proxy rather than a dumb forwarder. First, forwarded headers tell the backend who really called: X-Forwarded-For, X-Real-IP, X-Forwarded-Host, and X-Forwarded-Proto. Second, rewriting changes what the backend sees — the path, the Host, and arbitrary request/response headers — so the proxy's public URL space can differ from the backend's internal one.

The single most important idea is that the four headers have three different injection policies, and each difference is a security decision. X-Forwarded-For appends — it is a chain of custody, and replacing it would erase the record while trusting an inbound value would let any client forge its origin. X-Real-IP overwrites — it is single-valued, so a client-sent value is a forgery to be replaced, not a hop to be preserved. X-Forwarded-Host and X-Forwarded-Proto are set-if-absent — a legitimate upstream proxy already knows the true original, so we must not clobber it.

The whole module (rewrite.rs) is a pure synchronous transform over a head struct: apply_request mutates a RequestHead, apply_response mutates a ResponseHead, no I/O anywhere. Path rewriting is segment-aware (strip=/api turns /api/users into /users but leaves /apixyz alone) and preserves the query string. Host rewriting captures the original Host before the clobber so X-Forwarded-Host can still report it. Header rules (set-header/remove-header and their response twins) refuse framing headers at boot, and every serialized value is checked for CR/LF so a config string can't smuggle an extra header line. A fixed transform order — path → Host → forwarded → explicit rules — runs entirely before the proxy re-declares its framing, so Level 1's anti-smuggling guarantees stay intact. Ferrum here is a teaching build: no RFC 7239 Forwarded:, no regex path capture groups, and it always appends XFF rather than trusting a configured proxy allowlist. Those gaps are documented, not hidden.

The Big Picture

Level 5 is one fixed transform stage, dropped into the forwarding path between hop-by-hop stripping and framing re-declaration.

Two placement facts anchor the whole level. The transform runs after strip_hop_by_hop — so a client cannot smuggle a Connection-listed header that our rewrite then re-adds — and before the framing re-declaration — so a misconfigured header rule can never displace the Content-Length / Transfer-Encoding / Connection headers the proxy owns. It is deliberately not a middleware pipeline: that is Level 6's job. Level 5 is a single fixed step, which is exactly enough to teach the header and rewriting mechanics without an abstraction the next level would only have to replace.

Analogy — a mailroom that stamps and re-labels. A dumb forwarder just relays the envelope. A reverse proxy is the corporate mailroom: it stamps the envelope with where it actually arrived from (the forwarded headers — and it adds to the routing history rather than erasing it), it can re-address the internal envelope so the outside world's PO-box scheme differs from the internal floor-and-desk scheme (path and Host rewriting), and it refuses to let anyone hand-write the postal barcodes the sorting machines depend on (the protected framing headers). The one rule the mailroom never breaks: it records what it observed, and treats anything the sender claimed as unverified.

The Pure-Transform Design

The whole level is a function from a head struct to a head struct. No sockets, no async, no I/O — and that is the deliberate choice everything else hangs off.

The module rewrite.rs owns RewriteRules (the parsed per-route config) and exactly two transform entry points:

pub fn apply_request(&self, req: &mut RequestHead, ctx: &ForwardContext)
pub fn apply_response(&self, resp: &mut ResponseHead)

Both are pure synchronous functions over a head struct. Neither touches a socket, neither awaits, neither allocates a buffer. That is not an accident of the current implementation — it is the design goal. It makes the entire level unit-testable by constructing a RequestHead by hand, applying rules, and asserting on the mutated head. The same discipline that kept Level 4's Breaker testable without a network, and Level 3's balancer algorithms testable without a backend, keeps Level 5 testable without either. The result is 99 unit tests (72 carried green from Level 4, +27 new) that run in milliseconds and never open a port.

ForwardContext — the facts the head doesn't carry

A request head knows its method, target, version, and headers. It does not know the client's socket-observed IP, nor the scheme of the client leg, nor — crucially — the Host the client asked for before any rewrite mangled it. Those come in through a small borrowed context:

pub struct ForwardContext<'a> {
    /// The immediate peer's IP: the real client, or the last proxy in a
    /// chain. The one value in the forwarded headers that CANNOT be forged —
    /// we observed it on the socket.
    pub client_ip: IpAddr,
    /// The Host the client originally asked for, captured BEFORE any
    /// rewriting. This is why X-Forwarded-Host stays honest.
    pub original_host: Option<&'a str>,
    /// Scheme on the client leg. "http" today; Level 8's TLS termination
    /// sets "https" here and X-Forwarded-Proto follows automatically.
    pub scheme: &'static str,
}

The 'a lifetime lets original_host borrow the captured string rather than clone it, and the scheme being &'static str encodes that today it is always the literal "http" — Level 8 flips it to "https" after TLS termination and X-Forwarded-Proto follows with zero extra code. This is the deliberate seam the spec calls out.

The meaning-preserving Default

RewriteRules hand-writes its Default rather than deriving it, and the reason is a real footgun:

impl Default for RewriteRules {
    fn default() -> RewriteRules {
        RewriteRules { /* all rules None/empty, */ forwarded: true }
    }
}

The single forwarded: bool field is true by default. If we had #[derive(Default)], bool's default is false — the exact opposite of what the struct means. A route declared with no options should still inject the four forwarded headers; forwarding is the near-universal common case, and requiring opt-in would make the common case wrong. So a stray RewriteRules::default() anywhere in the codebase can never silently disable forwarded headers. --no-forwarded is the one thing that flips the field, via RewriteRules::no_forwarded().

Pattern name — the "make the default the safe/expected thing" invariant. When a boolean's semantic default disagrees with the language default, you spell it out. Deriving Default here would be a correctness bug hiding as a convenience.

Four Headers, Three Policies

The lesson of the level is not that we inject four headers. It is that we inject them with three different policies, and each difference is a security decision.

Forwarded injection is on by default for every route — these headers are near-universal, and requiring opt-in would make the common case wrong. --no-forwarded disables all four globally. Injection lives in inject_forwarded, and the append-vs-overwrite-vs-set-if-absent split is the entire point.

HeaderPolicyValueWhy this policy
X-Forwarded-ForAPPENDexisting, client_ipIt is a chain of custody. Replacing erases upstream history; trusting an inbound value lets any client forge its origin.
X-Real-IPOVERWRITEclient_ipSingle-valued by convention — not a chain. A client-sent value is purely a forgery attempt, so replace it.
X-Forwarded-HostSET-IF-ABSENTctx.original_hostA legitimate upstream proxy already knows the true original; it is closer to the truth than we are, so don't clobber it.
X-Forwarded-ProtoSET-IF-ABSENTctx.schemeSame reasoning: the first proxy in the chain knows the real client-leg scheme.
append

X-Forwarded-For — the chain of custody

What it does: appends the socket-observed client_ip to any existing value; creates the header from just our IP when absent.

let xff = match http::header(&req.headers, "x-forwarded-for") {
    Some(existing) if !existing.trim().is_empty() => format!("{existing}, {ip}"),
    _ => ip.clone(),
};
http::set_header(&mut req.headers, "X-Forwarded-For", &xff);

Why append and not replace or trust. A value like 1.2.3.4, 10.0.0.1 means the original client was 1.2.3.4 and it passed through the proxy at 10.0.0.1. Replacing would let this proxy erase the chain recorded by upstream proxies. Trusting an inbound value outright would let any client forge its own origin by simply sending X-Forwarded-For: 1.2.3.4. Appending is honest in both directions: the rightmost entry is always the one we observed on the socket and cannot be forged; anything to its left is hearsay from upstream.

The teaching point that trips everyone up. A backend reading XFF must count from the right, not the left, and must know exactly how many proxies it sits behind. The leftmost entry is the least trustworthy — a client can put anything there. If you trust xff.split(',')[0] you have just built an IP-spoofing oracle.
overwrite

X-Real-IP — never trust inbound

What it does: unconditionally overwrites with the observed peer — http::set_header(&mut req.headers, "X-Real-IP", &ip).

Why overwrite. Unlike XFF, X-Real-IP is not a chain — there is no legitimate multi-hop meaning to preserve. It is single-valued: "the immediate peer." So a client-supplied X-Real-IP: 9.9.9.9 is purely an attempt to spoof its own address, and the only correct response is to replace it with what we actually saw. set_header is remove-then-push, so a forged inbound value leaves exactly one X-Real-IP — no duplicate for a confused backend to pick the wrong one from.

The opposite choice is a vulnerability. If XFF overwrote, you would erase forensic history. If X-Real-IP appended (or trusted inbound), a client could pin any address it liked into the field a backend most naively trusts as "the real client." The asymmetry is the security posture: append what is additive, overwrite what is singular.
set-if-absent

X-Forwarded-Host / -Proto — the first proxy knows best

What it does: sets each only when the header is absent, from ctx.original_host and ctx.scheme respectively.

if http::header(&req.headers, "x-forwarded-host").is_none() {
    if let Some(h) = ctx.original_host {
        http::set_header(&mut req.headers, "X-Forwarded-Host", h);
    }
}
if http::header(&req.headers, "x-forwarded-proto").is_none() {
    http::set_header(&mut req.headers, "X-Forwarded-Proto", ctx.scheme);
}

Why set-if-absent. If a legitimate upstream proxy already set these, its value is closer to the truth than ours — it spoke to the real client and knows the true original Host and scheme; we only know the leg between us and it. Clobbering would throw that away. Absent an upstream value, we fill in what we know. Note that X-Forwarded-Host reads ctx.original_host, not the live Host header — the reason is the ordering bug in its own section below.

Observation, Not Assertion

Every policy above is one principle applied four times: trust what you observed, treat what the client asserted as unverified.

The client_ip in ForwardContext is the only value in the entire forwarded set that the proxy observed — it read it off the socket, and TCP's handshake makes it hard to forge at scale. Every other candidate — an inbound X-Forwarded-For, a client-sent X-Real-IP, a hand-crafted X-Forwarded-Host — is an assertion made by whoever sent the request, and the sender may be an attacker. The design never conflates the two:

  • The observed peer IP is written authoritatively into both XFF (as the rightmost, unforgeable entry) and X-Real-IP (as the sole value).
  • An asserted inbound XFF chain is preserved but demoted — kept for forensic continuity, but only the rightmost entry we added carries our guarantee.
  • An asserted X-Real-IP is discarded — it claims to be the immediate peer, a fact only we can know.
  • An asserted XFH/XFP from a genuine upstream proxy is trusted, because in a correct topology that upstream is itself an observation point closer to the client than we are.
Where this model stops — and who owns the rest. Ferrum always appends XFF and never does trust-and-replace against a configured proxy allowlist. That is the safe default: with no allowlist, you cannot know which inbound values to believe, so you believe none of them and only vouch for your own observation. Selective trust of inbound XFF (a trusted-proxy allowlist that lets you collapse the chain to a known client) is a Level 13 (WAF / reputation) concern, explicitly deferred by this level's spec. Saying "trust nothing you didn't see" is not a limitation to apologize for — it is the correct posture until a reputation layer gives you a reason to relax it.

Segment-Aware Path Rewriting

Two operations — strip and prefix — that let the proxy expose one URL space and the backend serve another, without ever mangling the query string.

Path rewriting operates on the request target's path while preserving everything after the ?. Two forms:

  • strip=/api — remove the prefix. /api/users?p=2 → /users?p=2. The single most common reverse-proxy rewrite: the proxy exposes /api/**, the backend serves /**.
  • prefix=/v2 — prepend. /users → /v2/users.

They compose in a fixed order — strip first, then prefix — so strip=/api;prefix=/v2 takes /api/users?a=b to /v2/users?a=b. The result is always normalized to start with /.

The query string is split off first

rewrite_path splits the target on the first ? before touching the path, and re-appends the query after:

let (path, query) = match target.split_once('?') {
    Some((p, q)) => (p, Some(q)),
    None => (target, None),
};
// ... strip/prefix arithmetic on `path` only ...
match query { Some(q) => format!("{out}?{q}"), None => out }

So a ? (or a # inside the query) can never be swallowed by prefix arithmetic, and a backend that depends on its query parameters keeps getting them intact. This is verified directly: strip=/api on /api/users?page=2 yields /users?page=2.

Segment boundary, not raw byte prefix — the /apixyz trap

The subtle correctness bug this design exists to prevent: a naive str::strip_prefix("/api") would strip /api from /apixyz and yield /xyz. But /apixyz is a different path that merely shares a textual prefix — an operator writing strip=/api means "the /api segment," exactly as nginx and Traefik interpret it. So the strip only fires when what remains after the prefix is empty or begins with /:

if let Some(rest) = out.strip_prefix(s.as_str()) {
    if rest.is_empty() || rest.starts_with('/') {
        out = rest.to_string();   // clean segment break — strip
    }
    // else: /apixyz -> rest is "xyz", no leading '/' — DON'T strip
}

/api/users leaves /users (leading slash → strip). /api leaves "" (empty → strip). /apixyz leaves xyz (no boundary → pass through untouched). A raw prefix strip would silently misroute the third case — and silent misrouting is the worst outcome, because nothing errors and traffic just goes to the wrong place.

Empty target normalizes to "/"

Stripping /api from exactly /api yields "", and an empty request target is malformed HTTP — a backend would reject it. So the code forces a root:

if out.is_empty() { out.push('/'); }
else if !out.starts_with('/') { out.insert(0, '/'); }

/api → /, and /api?x=1 → /?x=1. This distinction matters because / is a valid "the root resource" while "" is a protocol error.

Trailing-slash normalization at parse time

The segment-aware strip introduced a sharp edge: strip=/api/ (trailing slash) against /api/users leaves remainder users — no leading slash — so the strip would silently become a no-op. A trailing slash is a plausible typo, so it is normalized at parse time (config normalization belongs at parse time, not on the hot request path): value.trim_end_matches('/') makes strip=/api/ behave exactly like strip=/api. But strip=/ (all slashes) would trim to "", which names no segment — that is a hard startup error, not a silent no-op.

Non-origin-form targets are left alone. rewrite_path only touches origin-form targets (starting with /). An absolute-form target (http://host/path, used to proxies) or asterisk-form (*, for OPTIONS *) is returned unchanged — rooting or prefixing them would corrupt the request line (http://evil.com/api becoming /http://evil.com/api, or * becoming /*). RFC 9112 §3.2 defines these forms; strip/prefix simply do not apply to them.

Host Rewrite & the Ordering Bug

host=backend.local replaces the Host the backend sees — and the entire reason ForwardContext.original_host exists is to keep X-Forwarded-Host honest when it does.

Host rewriting is one line in apply_request:

if let Some(h) = &self.host {
    http::set_header(&mut req.headers, "Host", h);
}

set_header is remove-then-push, so exactly one Host survives. That matters: a duplicate Host header is a request-smuggling vector — different servers in a chain may disagree about which one is authoritative. One Host in, one Host out.

Capture before the clobber — the load-bearing ordering

Here is the bug the whole design is arranged to prevent. X-Forwarded-Host is supposed to tell the backend what the client asked for. But if injection read the live Host header at injection time, and the Host rewrite had already run, XFH would report backend.local — the rewritten value — and the backend could never learn the client's real Host. The fix is to capture the original into ctx.original_host before any rewriting, at the top of the request path in proxy.rs, and have inject_forwarded read that, never the live header.

Why the step-3/step-4 order is actually not observable — and that's the point. Because injection reads ctx.original_host and not the live Host, the relative order of the Host rewrite (step 3) and forwarded injection (step 4) produces the same honest XFH either way. The ordering would matter if injection ever read the live header; it deliberately does not. Reading the captured context rather than the mutated head is exactly what makes XFH robust against the Host rewrite.
Verified end-to-end (2026-08-07). With /api/**=...;strip=/api;host=backend.local;remove-resp-header=Server, a client GET to /api/users?page=2 (Host example.com) reached the backend as "path": "/users?page=2" (prefix stripped, query intact), "host": "backend.local" (rewritten), and still x-forwarded-host: example.com — the client's original Host, preserved despite the rewrite. That last fact is the whole-level ordering guarantee, observable.

Header Rules & the Protected-Header Guardrail

Four repeatable rules let config add or drop arbitrary headers on both legs — bounded by a guardrail that refuses framing headers at boot.

OptionEffect
set-header=Name:ValueAdd or overwrite a request header.
remove-header=NameRemove a request header (case-insensitive).
set-resp-header=Name:ValueAdd or overwrite a response header.
remove-resp-header=NameRemove a response header (case-insensitive).

set is an overwrite (remove-then-push), not an append, so a rule is idempotent and can't accumulate duplicates across retries. On both legs, removals run before sets, so a (remove X, set X) pair is order-independent — it always lands on a clean slate rather than depending on which was declared first. The response path (apply_response) has only these rules — there is nothing to "forward" back toward the client, since the client is the final hop.

The guardrail — protected headers rejected at boot

A rule may not target a framing or connection header. Attempting it is a hard startup error (exit 1), never a silent ignore — a config that appears to set Transfer-Encoding but doesn't would be a trap, and one that actually did would reopen the Level 1 smuggling holes. The protected set is checked case-insensitively in check_not_protected:

const PROTECTED_HEADERS: [&str; 7] = [
    "content-length", "transfer-encoding", "connection", "host",
    "upgrade", "te", "trailer",
];
HeaderWhy protected
Content-LengthBody framing the proxy owns; a wrong value desyncs the connection.
Transfer-EncodingThe other framing header; a smuggled chunked is the classic request-smuggling primitive.
ConnectionKeep-alive semantics the proxy manages end to end.
HostHas a dedicated host= option that also feeds X-Forwarded-Host — set-header would bypass that.
Upgrade, TE, TrailerThe remaining hop-by-hop headers strip_hop_by_hop deletes. Without protection, step 5's set-header could re-add a hop-by-hop header after the strip, defeating it — a set-header=Upgrade:websocket would sail back onto the wire.
Note the honest discrepancy. The Level 5 spec listed four protected headers (Content-Length, Transfer-Encoding, Connection, Host). The shipped code protects seven — it added Upgrade, TE, and Trailer during a review-finding pass, because those are hop-by-hop headers that a set-header rule running after strip_hop_by_hop could otherwise resurrect. The extra three are the correct call; the spec is the one that was incomplete. Ferrum deliberately does not protect Content-Encoding or Expect: those are hazardous but legitimately settable, so blocking them would be over-reach.

CRLF-Injection Hardening

The protected-header list guards header names. It does nothing about a malicious value — and a \r\n inside a value is a request-smuggling vector all its own.

Three validators run at parse time, because the only place to stop a smuggled byte is before it is ever accepted — once it is stored raw and serialized by write_request_head, it is bytes on the wire.

check_header_value

CR/LF in header values

A set-header=X-Foo:bar\r\nTransfer-Encoding: chunked is a smuggling payload: str::trim() only strips surrounding whitespace, so an interior CRLF sails through and write_request_head renders it as a header separator — turning one config value into an extra header line on the wire. It bypasses PROTECTED_HEADERS entirely, because that guard inspects only the header name. So any value containing a control character (chiefly CR and LF) is a hard error.

Why the framing re-declaration does NOT save you. The framing block in proxy.rs does remove_header("transfer-encoding") then re-pushes it — and remove_header matches on the header name. A Transfer-Encoding smuggled inside another header's value (say X-Foo's value) is not a distinct header entry — it is bytes in X-Foo — so remove_header never sees it and it reaches the backend intact. The value check is the only door that stops it.
check_header_name

Header names must be valid tokens

RFC 9110 §5.1 defines a field name as a token — ASCII letters, digits, and !#$%&'*+-.^_`|~ only. A name like Foo Bar would render as Foo Bar: x, a line this proxy's own Level 1 parser would reject off the wire. So a config-injected name must clear the same bar: spaces, :, control chars, and non-ASCII bytes are refused. Legitimate names using token-special characters (X-My_Header.v1) still pass.

check_host

host= must look like an authority

host flows into the Host header value, so it gets the same CR/LF check (reusing check_header_value, so the two doors enforce identical rules). Beyond that, a Host carries an authority (uri-host [":" port]), so it must look like one: ASCII alphanumerics plus -._~:[] (unreserved chars, host/port separator, IPv6 literal brackets). A space is refused — it would render a malformed header line — while backend.local and backend.local:8080 are accepted.

check_prefix

prefix= lands in the request line

prefix is prepended to the target, which lands in the request line (METHOD SP request-target SP HTTP-version). Two byte classes are catastrophic there: CR/LF (splits the line into a bogus header line) and a literal space — arguably worse, since the request line is space-delimited, so an interior space turns the rest of the target into a bogus HTTP-version field (GET /v2 X-Inj: yes/test HTTP/1.1). Both are refused. strip needs no such check — it is only ever a match argument, never serialized.

Two doors, one rule. set-header and host= both serialize into a header value, so both call check_header_value. A findings review caught that the first fix wave hardened set-header but left the identical vector open through host= and prefix= — both store their values raw and serialize them. All three doors are now closed with the exact reproduced payloads as regression tests.

Fixed Transform Ordering

Inside apply_request the four operations run in a fixed order — and the order is a set of correctness guarantees, not a style choice.

  1. Path rewrite (strip → prefix). First, so everything downstream — including the log line — sees the target the backend will actually receive.
  2. Host rewrite (host=). Remove-then-push, exactly one Host survives.
  3. Forwarded injection (XFF/XRI/XFH/XFP). Reads ctx.original_host, not the live Host clobbered in step 2 — so XFH reports what the client asked for regardless of step-2/step-3 order.
  4. Explicit header rules (removes then sets). Last, on purpose.

Why explicit rules run last. It lets an operator deliberately override an injected forwarded value — for example, pinning X-Forwarded-Proto: https when an external TLS terminator sits in front of Ferrum. If rules ran before injection, the injection would clobber the operator's value back. This is tested with a probe that only bites under the correct order: an explicit set-header=X-Real-IP:10.9.9.9 must win, because injection unconditionally overwrites X-Real-IP — rules-last yields 10.9.9.9, rules-first yields the client IP.

All of this runs before framing re-declaration

The transform sits between strip_hop_by_hop and the proxy's framing re-declaration in serve_one. That placement is the outermost guarantee: after all four steps, proxy.rs re-declares Connection and Transfer-Encoding itself, so no rewrite rule can ever desync Content-Length / Transfer-Encoding — even if the guardrail somehow missed one, the framing the proxy owns has the final word. Level 1's smuggling guarantees stay intact end to end.

The route-spec ; grammar hazard

Rewrite options attach to a route with ;-separated options, the same shape Level 4 used for ;health=. There is a real parsing hazard: option values contain = (strip=/api), so the options must be severed on the first ; before the =TARGET split. The naive order (split on = first) would swallow the target into the option string and mis-route.

CORRECT:  /api/**=api;strip=/api
          └─ sever ';' first ─┘
          route "/api/**=api"  +  options "strip=/api"   ✓

NAIVE (bug): split on '=' first
          key "/api/**"  value "api;strip=/api"
          → target becomes "api;strip=/api", a bogus backend  ✗

Because options are severed on the first ;, a route's options cannot themselves contain a literal ;. And --no-forwarded is applied even to the two friendly catch-all default routes, so the flag is never a silent no-op.

Two ; grammars coexist, verified. An --upstream 'pool=rr:...;health=/health' (Level 4's ; grammar) ran in the same invocation as /api/**=...;strip=...;host=... (Level 5's ; grammar). Both routes served correctly — the two grammars did not interfere.

How the Giants Do It

Every production proxy forwards origin headers and rewrites paths. The interesting differences are in trust defaults, the standardized Forwarded: header, and how much rewriting the config language expresses.

nginx

Explicit, and trust-what-you-configure

nginx sets forwarded headers explicitly with proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for — the $proxy_add_... variable appends the connection IP to any inbound value, the same append semantics Ferrum bakes in. X-Real-IP is typically set to $remote_addr. The realip module can trust inbound XFF from a configured set_real_ip_from allowlist — the trusted-proxy feature Ferrum defers to Level 13. Path rewriting is rewrite regexes plus the proxy_pass trailing-slash rule (the classic location /api/ { proxy_pass http://b/; } strips /api/) — more powerful and more footgun-prone than strip/prefix.

Apache httpd

mod_proxy + mod_remoteip

httpd's ProxyPass/ProxyPassReverse handle path mapping and rewrite response headers (e.g. Location) back to the public space — the reverse-rewrite Ferrum doesn't yet do. mod_remoteip parses X-Forwarded-For from trusted proxies (RemoteIPTrustedProxy) and rewrites the client address the rest of the server sees — again the allowlist model. RequestHeader/Header directives are the analogue of set-header/set-resp-header. Classic C, synchronous per-request hooks.

HAProxy

Declarative, source-IP native

HAProxy sets XFF with option forwardfor (append, with an except for trusted nets) and expresses arbitrary header work with http-request set-header / set-path / replace-path. Its src fetch is the connection IP — the same unforgeable identity Ferrum keys on. Everything is config directives against a tuned C event loop, not pluggable code. Its trust model, like nginx's, is "trust the proxies you name."

Envoy

XFF numbers, and RFC 7239

Envoy is the most explicit about the append-and-count trust model: xff_num_trusted_hops tells it exactly how many proxies sit in front so it can pick the real client from the right of the XFF chain — the counting discipline this page keeps hammering. It supports the standardized Forwarded: header (RFC 7239), which Ferrum deliberately skips. Header manipulation and path rewriting (prefix_rewrite, regex rewrite) are route-config; filters can do far more.

Honest positioning. Ferrum's rewriting is a teaching build. It has strip/prefix, not regex capture groups; it forwards the X-* family, not RFC 7239 Forwarded:; it always appends XFF rather than offering a trusted-proxy allowlist; and it doesn't yet reverse-rewrite Location or Set-Cookie domains. What it gets right — and shares with the giants — is the append/overwrite/set-if-absent trust split, the count-from-the-right XFF discipline, keying trust on the observed socket IP, and refusing to let config touch framing headers. As of the current codebase these comparisons reflect the well-known architectures of each proxy; specific directive names and defaults may drift across versions.
