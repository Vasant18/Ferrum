Security & TLS
The one place we stop building from scratch — and everything around the crypto that is still ours

Level 8 gives Ferrum a lock on the front door and a bouncer beside it. TLS termination arrives through rustls + tokio-rustls — the single deliberate library exception in a from-scratch course, because hand-rolling crypto is this level's named mistake #1. But the crypto is the small part. The interesting engineering is around it: where the handshake runs (inside the spawned task, never the accept loop), how long it may take, a global-plus-per-IP connection limiter released by RAII, hand-rolled CIDR allow/deny, and body/header caps enforced mid-stream. All of it rides Level 1's Conn<S> seam for free.

Executive Summary

Encrypt the transport, then armor the front door — and own everything except the crypto itself.

Level 8 has two halves, both drawn from the knowledge base's own framing. The first is encrypted transport: TLS termination and mutual TLS. The second is armored defaults — the "front door" hardening that answers slowloris, resource exhaustion, and known-bad sources. This is the one level where "from scratch" deliberately stops at the library boundary. Building your own crypto or hand-rolling certificate parsing is listed as this level's mistake #1, because the failure mode is not a visible bug — it is a silent loss of confidentiality.

TLS termination comes from rustls + tokio-rustls (tls.rs), with the crypto provider pinned to ring rather than the aws-lc-rs default: a far lighter build with no cmake/NASM toolchain. These are the first new dependencies since Level 2's regex. The protocol floor is TLS 1.2 with 1.3 preferred, and there is deliberately no knob to go lower — rustls does not implement SSLv3 or TLS 1.0/1.1 at all. ALPN is pinned to http/1.1 because this proxy speaks exactly one protocol and saying so in the handshake is more honest than negotiating h2 and then failing to parse it.

Levels 1–7 run over TLS completely unchanged, because Level 1 made Conn<S> generic over S: AsyncRead + AsyncWrite + Unpin instead of concrete over TcpStream, and tokio_rustls::server::TlsStream satisfies both. Seven levels later, that one decision is this level's entire integration cost: only handle_client and serve_one were generic-ized to pay it off.

The most important decision in the level is not about rustls at all: the handshake runs inside the spawned per-connection task, never in the accept loop. Awaiting it in the accept loop would let one client that sends a single ClientHello byte stall every new connection process-wide — a one-attacker total denial of service that passes every functional test. A TLS_HANDSHAKE_TIMEOUT of 10s bounds it, because otherwise slowloris just moves one layer down.

The armoring half (security.rs) is on by default. ConnLimiter gives a global ceiling plus a per-source-IP cap, checked before the spawn and released by Drop on an RAII guard. Hand-rolled Cidr/CidrList gives allow/deny on the socket peer address (deny beats allow; a non-empty allow list is default-deny; IPv4-mapped addresses normalized at the edge). Body caps are enforced while streaming (413), header count is capped at 431. A denied source and an over-limit connection both close with no response — a TLS-specific reversal of the design doc, because handshaking to answer 403 spends an RSA/ECDHE operation on traffic you already decided to refuse.

The Big Picture

Level 8 wraps a shell around the outside of the request pipeline and adds one counter inside the body loop. Every pre-existing stage — head read, routing, middleware, forwarding — is untouched. The new work lives in the accept loop (CIDR check, connection limits) and in the newly-spawned task (TLS handshake), plus two size caps in the head/body path.

The ordering matters, and it is deliberately cheapest-first. The CIDR check runs before any allocation. The connection limits run before the task spawn. Only then do we spawn, and only inside that task do we perform the handshake. Each gate is arranged so that the check is cheaper than the attack it defends against.

Analogy: Think of a nightclub. TLS is the tinted-glass tunnel from the street to the door — nobody outside can see who is walking in or what they are carrying. The bouncer is the armoring half: he counts heads (global limit), stops any one stag party from filling the room (per-IP cap), keeps a banned-names list (deny CIDR) and optionally a guest list (allow CIDR), and turns away anyone over the fire-code limit at the rope — without walking them inside first to explain why. Crucially, the bouncer stands inside his own booth (the spawned task) so that one slow ID check does not freeze the entire door.

rustls: The One From-Scratch Exception

Every other subsystem in this course is built from primitives. TLS is where that stops — on purpose.

The router's matcher, the balancer's hash ring, the limiter's token bucket, the pool's LIFO stack — all hand-built. Certificate parsing and TLS state machines are the documented exception. tls.rs's own module doc names it plainly: rolling your own crypto is this level's mistake #1, "because the failure mode is not a bug you can see in a test, it is a silent loss of confidentiality." A subtly-wrong AES-GCM or a padding-oracle in your handshake code does not fail a functional test; it quietly leaks. So Ferrum reaches for a library here and only here.

Why rustls, and why ring

The choice is rustls + tokio-rustls: memory-safe, pure-Rust, with no OpenSSL C surface to fuzz or CVE-track. Within rustls, the crypto provider is pinned explicitly to ring rather than the newer aws-lc-rs default. The reason is build weight: ring is substantially lighter and needs no cmake/NASM toolchain. The spec even records the evidence — rproxy/target/ still held ~1.2 GB of stale aws-lc-sys artifacts from an earlier probe of this level.

Because the crate is built with default-features = false, there is no process-wide default provider installed. build_server_config in tls.rs therefore passes it by hand:

let provider = Arc::new(rustls::crypto::ring::default_provider());
let builder = ServerConfig::builder_with_provider(provider)
    .with_safe_default_protocol_versions()   // TLS 1.3 + 1.2, nothing older
    .map_err(|e| bad(format!("tls: {e}")))?;

Naming the provider in one place beats a global install whose absence would surface as a runtime panic on the first handshake — a failure that arrives in production, not at boot.

The protocol floor is an absence, not a setting

with_safe_default_protocol_versions() gives TLS 1.3 (preferred) and 1.2, and there is no path older. This is the strongest form of the level's theme — "the config a lazy user gets must be the safe one." As tls.rs puts it, the strongest version of that idea is "a config where the unsafe option cannot be typed." rustls simply does not implement SSLv3 or TLS 1.0/1.1, so no flag can re-enable them. Contrast nginx or HAProxy, where ssl_protocols is a line an operator can widen back to TLSv1 under pressure from a legacy client.

ALPN pinned to http/1.1

After building the cert, build_server_config sets one line:

config.alpn_protocols = vec![b"http/1.1".to_vec()];

This proxy speaks exactly one wire protocol. Advertising http/1.1 in the handshake is more honest than letting a modern client negotiate h2 and then discovering, after the connection is up, that Ferrum cannot parse HTTP/2 framing. HTTP/2 is not on this course's 14-level map; if it ever arrives, this is the single line that changes.

Watch out: This is a teaching build. rustls's defaults are production-grade — but everything Ferrum wraps around them (session-store tuning, OCSP stapling, backend re-encryption, ACME issuance) is deliberately out of scope. Treat this as "correct TLS termination," not "a hardened edge appliance."

The Conn<S> Seam Pays Off

A generic chosen in Level 1, for reasons that would not fully land for seven levels, is what makes TLS almost free here.

Back in Level 1, the connection wrapper was written as Conn<S> generic over S: AsyncRead + AsyncWrite + Unpin, rather than concrete over TcpStream. A tokio_rustls::server::TlsStream<TcpStream> implements both of those traits. So the entire parsing, framing, routing, middleware, and forwarding core — every line of Levels 1 through 7 — works over an encrypted stream with no change whatsoever. The bytes coming out of the read call are plaintext either way; only the layer underneath differs.

The integration cost, seven levels later, was making exactly two signatures generic (both in proxy.rs):

pub async fn handle_client<S: AsyncRead + AsyncWrite + Unpin>(
    client: S, ...
)
async fn serve_one<S: AsyncRead + AsyncWrite + Unpin>(
    client: &mut Conn<S>, ...
)

Generics, not an enum

The obvious alternative was an enum Stream { Plain(TcpStream), Tls(TlsStream<TcpStream>) }. It was rejected. This is the hottest loop in the program — every proxied byte passes through a read and a write. An enum would force a match on every one of those calls, branching on which variant it holds. Generics give static dispatch: the compiler monomorphizes two copies of the proxy core, each hard-wired to its concrete stream type, with zero per-read branching. The price is two copies of that code in the binary — the correct trade for a proxy, where per-byte cost dominates and binary size does not.

The consequence: set_nodelay moves up

set_nodelay is a TcpStream-inherent method — it lives on the file descriptor. Once TLS wraps the socket, the generic proxy core no longer knows it is holding a TcpStream, so it cannot call it. The fix in main.rs is to apply it to the raw socket in the accept loop, before any TLS wrap:

let _ = stream.set_nodelay(true);   // on the raw fd, before spawn/handshake

This is both necessary and correct: the option lives on the file descriptor, which the TLS stream goes on to own. Disabling Nagle's algorithm matters because Ferrum writes small serialized heads that should not sit in a coalescing buffer waiting for a timer — every reverse proxy disables Nagle for the same reason.

The Level 5 seam, finally closed

Level 5 left a narrower seam: proxy.rs carried scheme: "http", // Level 8 sets "https" after TLS termination. That comment was a promissory note. Level 8 pays it: after termination, the backend has no other way to learn what the client actually spoke, so X-Forwarded-Proto must report it. In main.rs, scheme is "https" on the TLS arm and "http" on the plaintext arm, threaded through handle_client. Critically it is the listener's scheme — an observation — never a client-supplied hint. A backend that gates secure cookies or a redirect-to-HTTPS on that header must be reading a fact, not an assertion.

The Handshake Runs Inside the Task

This is the most important security decision in the level, and it is about our code, not rustls.

The question is deceptively small: where do you await the TLS handshake? There are two candidate placements, and they look almost identical. One of them is a one-attacker, one-line total denial of service.

Wrong

Handshake in the accept loop

loop {
  let (s, peer) = accept().await;
  let tls = acceptor.accept(s).await; // <- BLOCKS
  spawn(handle(tls));
}

The accept loop is single-threaded and sequential. Awaiting the handshake here means the loop cannot call accept() again until this one client finishes its handshake.

Right

Handshake inside the spawned task

loop {
  let (s, peer) = accept().await;
  spawn(async move {
    let tls = timeout(HS,
        acceptor.accept(s)).await;
    handle(tls);
  });
}

The loop spawns immediately and loops back to accept(). The handshake happens off to the side, one task per connection, blocking nobody.

The exact attack

In the wrong placement, an attacker opens a TCP connection and sends a single ClientHello byte, then goes silent. acceptor.accept(s).await sits waiting for the rest of the handshake that will never come. The accept loop is now frozen. Every new connection to the process — legitimate or not — stalls behind that one silent socket. One attacker, one byte, and the whole listener is wedged.

Why every functional test still passes: a proxy that serves one client at a time works perfectly under any test that connects, requests, and disconnects sequentially. The bug is invisible until two clients overlap and one of them is malicious. Level 1's own comment on the accept loop already stated the rule — "anything slow in this loop delays every new client" — but TLS is where breaking it turns from slow into catastrophic.

Ferrum's main.rs does it right, and its comment says so in as many words: "THE handshake ordering decision of this level. This .await is inside the spawned task, NOT in the accept loop above."

The deadline: TLS_HANDSHAKE_TIMEOUT

Moving the handshake into the task fixes the accept-loop DoS, but it opens a subtler hole: a task stuck mid-handshake forever is a leaked connection. So the handshake gets its own deadline — the TLS-layer analogue of Level 1's HEAD_READ_TIMEOUT:

let tls = match tokio::time::timeout(
    tls::TLS_HANDSHAKE_TIMEOUT,          // 10s
    acceptor.accept(stream),
).await {
    Ok(Ok(s))  => s,                     // handshake completed
    Ok(Err(e)) => { debug!("tls handshake failed: {e}"); return; }
    Err(_)     => { debug!("tls handshake timed out"); return; }
};

This deadline is not optional. Without it, slowloris simply moves one layer down. A connection stuck mid-handshake never produces a request head, so Level 1's HEAD_READ_TIMEOUT never arms — it only starts counting once there is a head to read, and there never is. The two deadlines cover disjoint phases: the handshake deadline guards "connected but not yet a TLS session," the head deadline guards "TLS session up but no request head yet."

TLS_HANDSHAKE_TIMEOUT is 10s, deliberately tighter than the 30s head deadline. A handshake is a fixed, small number of round trips with no human think-time in it; anything slower is a broken client or an attack, not a slow-but-honest one.

A failed or timed-out handshake is logged at debug and the connection is dropped — there is no HTTP layer yet on which to answer. This is routine, not exceptional: a probe, a client that does not trust the cert, or (with mTLS required) a client with no certificate.

Measured, not asserted: PROGRESS.md records the live proof — with three handshakes deliberately stalled (one TLS record byte, then silence), a real client was served in 0.03s. And a stalled connection was closed at exactly 10.0s with tls handshake timed out after 10s. This is the level's central claim and the one thing a unit test cannot check.

mTLS & the Startup Guardrails

Normal TLS authenticates the server to the client. mTLS adds the reverse direction — and the config that enables it is a minefield of half-states that must fail at boot.

Three modes

Mutual TLS asks the client to present a certificate that Ferrum validates against a trusted CA. It is authentication without passwords or tokens, at the transport layer — rare for humans-with-browsers, heavily used for service-to-service traffic (mesh sidecars, internal APIs, partner links). The ClientAuth enum in tls.rs has three modes, wired through rustls's WebPkiClientVerifier against a bundle from --tls-client-ca:

Default

Off

No client certificate requested. mTLS is opt-in because turning it on before the fleet is ready is an outage.

Migration

Optional

Request a cert, validate it if presented, but still admit clients that present none. Built via verifier.allow_unauthenticated().

Enforcing

Required

Reject the handshake unless a valid client cert is presented.

Optional looks strictly weaker than Required, so why does it exist? Because it is the only safe migration path onto mTLS. Enable optional, watch the logs to learn which callers actually present certificates, then flip to required. Going straight to required on a live listener drops every client that has not been rolled out yet — an instant, self-inflicted outage. Skip optional and you have no way to see who would break before you break them.

A misspelled mode is a startup error, never a silent downgrade. ClientAuth::parse rejects anything it does not recognize: quietly reading requried as off would disable client authentication on a listener whose operator believes it is enforced — the single most dangerous way this feature could fail.

Four startup guardrails, both directions of the trap

TlsArgs::build validates the whole flag combination before bind, exiting 1 on any incoherent state (the same discipline Level 5 used for protected headers and Level 6 for require-user without auth=). Because TLS is built before the socket is opened, a bad certificate fails with no listener ever announced.

#Rejected combinationWhy it is a boot failure
1--tls-cert without --tls-keyA certificate with no matching private key cannot complete any handshake.
2--tls-key without --tls-certA key with no certificate to present is equally useless.
3client-auth optional/required with no --tls-client-caThere is nothing to validate client certificates against — mTLS with no CA would accept any certificate that merely parses.
4--tls-client-ca with client-auth offThe inverse, easier-to-miss trap: the bundle would be loaded, never consulted, and read as enforcement by whoever wrote the config.

Guardrail #4 is the interesting one. Guardrails #1–#3 catch a missing thing; #4 catches a present thing that does nothing. It is worth an exit-1 rather than a warning precisely because the operator's mental model is wrong: they supplied a CA, so they believe client-auth is on. A warning scrolls past in a log; a refused boot forces them to reconcile the two flags. (There is also a fifth message inside guardrail #1's arm — client-auth alone with no cert/key at all names the missing cert first, since server identity is the more fundamental omission. PROGRESS.md counts "all 8 startup guardrails" across the whole binary; four of them are these TLS ones.)

Watch out — a key permission is a warning, not a refusal. warn_if_key_is_readable logs loudly if the private key file is group- or world-readable (mode & 0o077 != 0), then starts anyway. A hard failure would be wrong here: key material legitimately arrives group-readable from plenty of secret managers, and a proxy that will not start over a permission bit it merely dislikes is one operators route around. The rule of thumb: refuse on incoherent config, warn on suboptimal config.

ConnLimiter: Global Ceiling + Per-IP Cap

A per-connection deadline cannot help when the attacker simply opens more connections. That is the gap this fills.

Level 1 already shipped the head-read deadline and the 16 KB head byte cap — two-thirds of the slowloris answer. But a deadline does nothing against an attacker who opens thousands of connections, each perfectly polite, each holding a slot. ConnLimiter (in security.rs) is the missing third: a global ceiling (DEFAULT_MAX_CONNS = 10,000, the C10K reference point) plus a per-source-IP cap (DEFAULT_MAX_CONNS_PER_IP = 64). A browser opens ~6 parallel connections per host; 64 leaves headroom for a NAT'd office while still meaning one attacker needs 157 distinct source addresses to reach the global ceiling.

It is checked in the accept loop before the spawn — the check has to be cheaper than the attack, or it becomes the attack. An over-limit connection is dropped without a response: writing a 503 would mean allocating and doing I/O on behalf of exactly the traffic we decided to shed.

The RAII guard — the Level 3 Lease pattern, sharper

try_acquire returns a ConnGuard whose Drop releases both counters. There is no public release() — release is private and its only caller is ConnGuard::drop. That is the point: there is no way to decrement without having held a guard. The guard is moved into the connection's task, so its lifetime is exactly the connection's lifetime with no bookkeeping at any exit point.

This is the Level 3 Lease pattern for a sharper reason. A connection ends on many paths — clean close, parse error, head-read timeout, failed TLS handshake, a task unwinding from a panic. An explicit release() would eventually be missed on one of them. And a leaked connection slot is worse than a leaked in-flight count: a leaked in-flight count merely biases least-connections, but a leaked slot is permanent, and enough of them wedge the listener shut for good.

Three subtleties a naive limiter gets wrong

  1. Claim with fetch_update, not load-then-fetch_add. fetch_update makes "claim-if-under-limit" a single atomic step. A bare load then fetch_add would let two accepts both observe total == max - 1 and both proceed — the ceiling would not hold. This is the key contrast with Level 4's breaker, which happily uses Relaxed atomics: there, a lost increment merely delays a state change; here, a lost increment means the limit is wrong.
  2. A per-IP refusal rolls back the global claim. The global counter is claimed first; if the per-IP check then fails, the code does self.total.fetch_sub(1) before returning PerIpLimit. Without the rollback, a source hammering its own per-IP cap would leak the global counter toward exhaustion and take the whole listener down — the refusal path itself becoming the outage. Claiming global first (and rolling back) is cheaper than holding the map lock across both checks.
  3. The map entry is removed on last close, not left at zero. When a source's last connection drops, release calls map.remove(&ip) rather than leaving a 0. Otherwise the HashMap grows one permanent entry per source address ever seen — a slow memory leak reachable by a spoofed-source scan.

The map is guarded by a plain std::sync::Mutex, not tokio::sync::Mutex and not Level 6's 16 shards. The critical section is a HashMap increment with no .await inside it, so an async mutex would buy a scheduler hop for nothing. Sharding is skipped because the access pattern is genuinely light: exactly one lock per accept (from the single accept loop) and one per teardown — unlike Level 6's rate-limiter, which locked on every request from every task.

Hand-Rolled CIDR Allow/Deny

A prefix comparison over 4 or 16 bytes is smaller than half the primitives this project already hand-rolls, so it takes no new dependency.

Ferrum already hand-rolls FNV-1a (L3), duration parsing (L4), base64 and constant-time compare (L6). A CIDR match is smaller than any of those, and IpAddr already does the genuinely fiddly part (parsing the address, including IPv6 forms). So Cidr and CidrList in security.rs are built by hand rather than pulling an ipnet-style crate.

How matching works

Cidr::parse takes ADDR[/BITS]; a bare address is a host route (/32 for IPv4, /128 for IPv6). The network address is masked at parse time, so two spellings of the same block compare equal and matching never has to re-mask that side. mask gives /0 its own arm because u32 << 32 is a debug panic in Rust (and UB-adjacent in C); the same care handles /128. contains compares only within an address family — an IPv4 address never matches an IPv6 block or vice versa.

Two semantics that make the lists mean something

Precedence

Deny beats allow

In CidrList::permits, the deny list is checked first and short-circuits. An address on both lists is being explicitly called out as bad. Honoring the allow entry instead would mean a broad --allow-cidr 10.0.0.0/8 silently re-admitted a specific host the operator had just banned.

Default posture

A non-empty allow list is default-deny

If the allow list is non-empty and the address matches nothing in it, it is refused. This is what makes an allow list mean anything: the alternative (allow merely grants, absence is permitted) would make --allow-cidr a no-op.

pub fn permits(&self, ip: IpAddr) -> bool {
    if self.deny.iter().any(|c| c.contains(ip)) { return false; }  // deny wins
    if self.allow.is_empty() { return true; }                       // no allow list = allow all
    self.allow.iter().any(|c| c.contains(ip))                       // else default-deny
}

Matched on the socket peer, never a header

ip must be the socket peer address, never a value out of X-Forwarded-For or any client-supplied header. A deny list keyed on something the client controls is not a deny list — the banned party simply sends a different value. Level 5 took this stance for X-Real-IP, Level 6 for the rate-limit key; this is the third application of the same rule, and it is why normalize_peer takes a SocketAddr rather than a string.

IPv4-mapped normalization at the edge

A listener bound to [::] reports an IPv4 client as ::ffff:203.0.113.7. Without collapsing that, an operator's perfectly reasonable --deny-cidr 203.0.113.0/24 matches nothing — a deny list that appears configured and enforces nothing, the worst available failure mode for this feature (worse than an outright error, because it fails silently and looks like it is working). normalize_peer collapses the mapped form to plain IPv4 once, at the edge, in the accept loop, so every downstream comparison sees one canonical form. Genuine IPv6 peers are left alone.

The reversed decision: a denied CIDR closes with no response

This is the design decision the team reversed, and the reversal is the lesson. nginx's deny answers 403, so 403 was the obvious default — and it is exactly what an earlier draft of the spec said. But on a TLS listener the proxy cannot send any HTTP status without first completing a handshake, and completing a handshake for an address already refused means spending an RSA/ECDHE operation on the attacker's behalf. That turns the cheapest rejection in the system into one of the most expensive — a DoS amplifier.

Both alternatives were worse:

  • 403 on plaintext, drop on TLS: the same config behaving two different ways depending on a flag — exactly how operators get surprised.
  • Handshake-then-403 everywhere: pay the crypto cost for every refused connection — the amplifier.

So the CIDR check sits before the handshake and before the task spawn, and the connection simply closes. The connection limits shed load the same way for the same reason, which keeps the two gates consistent with each other — the property the earlier design lacked.

Verified: PROGRESS.md records both semantics live — --deny-cidr 127.0.0.0/8 refused the test connection (refused: address not permitted), and --allow-cidr 10.0.0.0/8 (which excludes the tester) also refused, confirming a non-empty allow list is default-deny rather than merely additive.

Body & Header Caps

"Read the whole body, then check the size" is this level's named mistake #1 — by then the damage is done.

Body cap enforced while streaming — 413

The cap lives inside the streaming copy loop, never in a buffer-then-decide step. Level 1's windowed copy_exact already sees every byte, so enforcement is a running total and a comparison — not a new mechanism. The framings are handled deliberately asymmetrically, because they carry different information:

FramingWhen the size is knowableEnforcement point
Content-Length: nBefore a single body byte moves413 before routing, before middleware, before any backend socket opens. Strictly better than stream-and-abort: the client gets a clean answer and the backend is never contacted.
Transfer-Encoding: chunkedNever declared — that is the point of chunkedMid-stream, at a chunk boundary in copy_body_limited / copy_chunked. The only possible point, and by then the head is already at the backend.

The chunked case is why the exchange leaves both connections unusable. By the time the cap trips, the request head has already been forwarded and a partial body streamed to the backend; the client→proxy leg is mid-body too. Neither side is at a message boundary, so neither can be cleanly reused — both must close. This is unavoidable by construction, not a shortcoming: with no declared length, a chunked over-cap body cannot be detected until you are already inside it.

BodyCopy::TooLarge, not an io::Error

copy_body_limited returns a BodyCopy { Done { reusable }, TooLarge } enum rather than io::Result<bool>. "Too large" is not an I/O error and must not be handled like one: the socket is healthy, the client is well-behaved by TCP's standards, and the right answer is a specific HTTP status (413), not a dropped connection with a logged errno. A distinct variant forces the caller to decide — a ? cannot silently swallow a limit breach into the generic error path. That is precisely the property you want at a security boundary: the compiler will not let you forget the case.

Watch out: the chunked cap counts decoded payload, not bytes on the wire. Framing overhead is attacker-controlled — a million 1-byte chunks carry a megabyte of framing around a megabyte of data — so a wire-byte cap would reject honest large-chunk requests while admitting pathological small-chunk ones. The overhead is separately bounded by read_line's buffer check.

Header count capped at 431

Level 1's 16 KB MAX_HEAD_BYTES bounds head size but not field count: roughly 8,000 one-byte header lines fit inside that budget. Every one of them multiplies the linear header scans this proxy performs per request — routing, hop-by-hop stripping, rewriting, framing, the middleware chain. So serve_one checks req.headers.len() > limits.max_headers (default 100) before routing, answering 431 Request Header Fields Too Large (RFC 6585) so the work is refused before it starts.

The two limits differ in tunability by design: max_body is per-route-overridable via ;max-body= (an upload route legitimately allows more than a JSON API), while max_headers is global — a request needing more than a hundred header fields is pathological on every route, so making it per-route would only widen the attack surface.

Verified: with --max-body 100 --max-headers 5, PROGRESS.md records a 50-byte body → 200, a 500-byte body → 413 Payload Too Large, and 12 headers → 431. A baseline-versus-after hit count proved the backend saw only the two measurement probes — zero rejected requests reached it.

How the Industry Does It

Every production proxy solves these same problems; the interesting part is which trade-offs each one took. Ferrum is a teaching build — it terminates TLS correctly and armors sensibly, but it deliberately skips whole subsystems (ACME, session-store tuning, backend re-encrypt) that the incumbents ship. The honest contrasts:

  • Memory safety is Ferrum's one genuine edge. rustls + ring means no Heartbleed-class buffer over-read is reachable in the TLS path — the incumbents' C/C++ stacks have each shipped such CVEs. This is not a teaching-build compromise; it is a real advantage of the language choice.
  • The "no path older than TLS 1.2" posture is stricter than the incumbents by design. nginx, httpd, and HAProxy all let an operator widen the floor back to TLS 1.0 under legacy-client pressure. Ferrum cannot — the unsafe option is not merely defaulted-off, it does not exist in the library.
  • Everything else, Ferrum does more crudely. HAProxy's stick-tables track per-IP state with far more nuance than a single HashMap; nginx's event loop multiplexes handshakes without a task per connection; Envoy's RBAC filter is a general policy engine where Ferrum has two Vec<Cidr>. The point of the level is the reasoning behind each gate, not parity with a decade-hardened appliance.
  • The 403-vs-drop choice is a real divergence. nginx answers 403 on a denied address; Ferrum closes silently. On a plaintext listener that is arguably worse UX; on a TLS listener it is the only choice that does not spend crypto on refused traffic — which is exactly why Ferrum makes both gates behave identically rather than split by protocol.

Glossary

TLS termination — the proxy holds the private key, performs the handshake, and decrypts; backends receive plain HTTP. Required for an L7 proxy: you cannot route on a path or header you cannot read.

mTLS (mutual TLS) — the client also presents a certificate the proxy validates against a CA. Transport-layer authentication with no passwords or tokens.

ALPN — Application-Layer Protocol Negotiation; the handshake extension where client and server agree on the wire protocol (here pinned to http/1.1).

SNI — Server Name Indication; the hostname the client sends in cleartext during the handshake, letting one IP serve certificates for many domains.

RAII / Drop guard — tie a resource's release to the end of a value's scope, so it fires on every exit path (clean, error, panic) with no explicit call to miss. Ferrum's ConnGuard and Level 3's Lease.

CIDR — Classless Inter-Domain Routing notation, address/prefix-bits, describing a block of IP addresses.

Slowloris — an attack that holds many connections open while sending data byte-by-byte, exhausting connection slots without ever completing a request. Answered here by the per-IP cap and the handshake/head deadlines together.

IPv4-mapped IPv6 — the ::ffff:a.b.c.d form a dual-stack ([::]) listener reports for IPv4 clients; normalized to plain IPv4 at the edge so v4 CIDR rules apply.

static dispatch / monomorphization — the compiler generates a specialized copy of generic code per concrete type, eliminating runtime branching. Why Ferrum chose generics over an enum Stream.

TOCTOU — time-of-check to time-of-use; a race where state changes between checking it and acting on it. fetch_update closes the one in the global connection claim.
