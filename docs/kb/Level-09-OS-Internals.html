Executive Summary

Async is not magic. It is a compiler-generated state machine riding a kernel readiness API, and Ferrum has been running on it since Level 1.

A blocking read() on a socket with no data parks the calling thread until bytes arrive. Fine for one connection, fatal for ten thousand — that is the C10K problem, and it is why every serious proxy is event-driven. The fix changes the question from "give me data on THIS socket, I'll wait" to "here are 10,000 sockets, wake me when ANY has data." Two ingredients make that possible: O_NONBLOCK sockets (Tokio sets these, Ferrum never does) and a kernel readiness API.

That API evolved: select() and poll() re-scan every watched FD on every call — O(n) — while epoll (Linux) and kqueue (BSD/macOS) register FDs once in a kernel object and return only the ready ones — O(ready). That O(n) → O(ready) transition is the whole ballgame: it is the precise reason 9,999 idle connections cost nothing until they have data.

On this machine (Darwin 25.6.0 arm64) the reactor is kqueue, not epoll, wrapped by mio 1.2.2 — a transitive dependency Ferrum never names. The runtime is tokio 1.53.1 with features = ["full"], giving a multi-threaded work-stealing scheduler with 8 worker threads (one per core), all implied by #[tokio::main] and stated nowhere in the source.

Read through this lens, Ferrum's own architecture becomes legible. The full path from .await to kevent traces cleanly through Conn::read_head, including a non-blocking fast path that skips the reactor entirely when data is already buffered. Only 3 of 13 files hold a production .await (72 production, 61 test); balancer.rs has zero despite 1,750+ lines of algorithms. And "never hold a lock across an .await" is compiler-enforced here, because every locking function is a plain fn. The reading turned up two honest findings — per-connect DNS re-resolution and an entirely implicit runtime shape — both recorded, neither fixed.

The Big Picture

Level 9 does not add a stage to the request pipeline — it explains the substrate every stage already stands on. The highlighted layer below is the one this level makes visible: the executor + reactor loop that sits underneath every .await in the proxy, from accept() in main.rs through read_head in proxy.rs.

Analogy: Blocking I/O is a waiter standing at your table until you decide your order. Async is the waiter handing you a pager and serving other tables; the kitchen bell (kqueue) tells them which pager to buzz. The waiter never stands idle at a silent table — and 10,000 tables need only as many waiters as there are tables currently talking.

1 · The Problem: read() Blocks

Everything in this level exists to escape one fact: a naive read() parks a whole OS thread just to wait for bytes.

A normal blocking read() on a socket with no data parks the calling thread until bytes arrive. That is fine for one connection and fatal for many. Thread-per-connection at 10,000 connections means 10,000 threads, each with a stack measured in hundreds of KB to megabytes, and a scheduler doing nothing but context-switching between them. This is the C10K problem, and it is the reason every serious proxy — nginx, HAProxy, Envoy, and Ferrum — is event-driven rather than thread-per-connection.

The fix is to change the question being asked:

Blocking asks:       "give me data on THIS socket — I'll wait."
Event-driven asks:   "here are 10,000 sockets — wake me when ANY has data."

One thread now serves them all, sleeping until there is genuine work. Two ingredients are required:

Ingredient 1

O_NONBLOCK sockets

So a read() with no data returns EWOULDBLOCK immediately instead of parking the thread.

Who sets it: Ferrum never sets O_NONBLOCK itself. Tokio does it when constructing every TcpStream and TcpListener — including the ones this proxy gets from listener.accept() in main.rs. It is the first piece of machinery the abstraction hides.

Ingredient 2

A kernel readiness API

So the thread can sleep until something is actually ready, instead of busy-polling every socket in a loop (which would just move the waste from threads to CPU).

Who provides it: the kernel — epoll on Linux, kqueue on BSD/macOS — reached through mio. This is the ingredient whose evolution is the entire story of high-performance servers (next section).

Why a task, not a thread, is the unit here. Async lets you keep the mental model of "one worker per connection" — each connection reads a straight-line async fn — while the physical cost collapses from a thread-with-a-stack to a small heap state machine. You write it like it blocks; it doesn't.

2 · select → poll → epoll/kqueue → io_uring

The whole story of high-performance servers is the evolution of ingredient 2 — and one line of it, O(n) → O(ready), is the whole ballgame.

The one line that matters. The O(n) → O(ready) transition is the entire ballgame. With select/poll, 9,999 idle connections cost you work on every single wait — the kernel walks the whole list to find the one socket that spoke. With epoll/kqueue, those 9,999 idle FDs cost nothing until they have data, because the kernel already holds the interest list and hands back only the ready ones. C10K dissolves at exactly this line.

Readiness vs. completion

There is a second axis worth separating from the O(n)/O(ready) one. epoll and kqueue are readiness-based: they tell you "you may now read without blocking", and you still issue the read() syscall yourself. io_uring and Windows IOCP are completion-based: you hand the kernel the buffer and the operation up front, and it tells you "the read is DONE, here are your bytes". Completion models need fewer syscalls because the read-attempt-and-wait round trip is collapsed into one submission plus one completion, batched through shared-memory rings rather than a syscall per operation.

Ferrum sits on the readiness side. Tokio's TcpStream::read is "wait for readable, then read()". No io_uring experiment was done here — it is Linux-only and this machine is Darwin (kqueue). Reading about the completion model is the whole deliverable, not building one.

3 · This Machine: kqueue, mio 1.2.2, 8 Workers

Every mental model in this KB is written around epoll because Linux is where proxies deploy. The code exercised locally is the BSD path. Verified, not assumed.

Platform

kqueue, not epoll

Darwin 25.6.0 arm64 → the reactor uses kqueue. Same O(ready) idea as epoll, cleaner API surface (kevent covers sockets, files, signals, timers in one call).

Reactor crate

mio 1.2.2

A transitive dependency via Tokio — it is in Cargo.lock, not Cargo.toml. mio is the thin portability layer presenting kqueue, epoll, and IOCP behind one interface.

Runtime

tokio 1.53.1, 8 workers

features = ["full"] → the multi-threaded scheduler. Default worker count is one per core → 8 workers here (hw.ncpu = 8).

That last point is worth pausing on. Ferrum has never called Runtime::new_multi_thread or configured a worker count. #[tokio::main] on async fn main picks the multi-threaded scheduler by default. Eight OS threads exist and steal work from each other, and nothing in this codebase says so anywhere. Level 9's job is that this is no longer invisible — and finding §7.2 records it explicitly as a latent tuning surprise.

Watch out: features = ["full"] reads like "give me every feature" but it is also the thing that selects the multi-threaded scheduler and the blocking pool. The runtime's entire shape — 8 workers, work stealing, a separate blocking pool — is implied by that one line and #[tokio::main], and stated in no comment. See the second finding.

4 · From .await to kevent: the Full Stack

An async fn compiles to a state machine — an anonymous type implementing Future. Each .await is a possible pause point where the machine returns Poll::Pending and parks.

The load-bearing consequence — the thing that trips up everyone from threads or JavaScript promises: Nothing runs in the background. A future is inert until polled. There is no thread behind an un-awaited future. Constructing one does no work at all.

The path, traced through Ferrum's own Conn::read_head

The diagram below is the mandatory one: a single .await suspension and resumption, traced layer by layer through this proxy's real code — not a toy example. Follow the numbered steps beneath it.

  1. The read attempt (fast path first). serve_one reaches client.read_head().await, which bottoms out in self.stream.read(&mut self.buf[self.filled..]).await (proxy.rs:130, inside Conn::read_head). The filled offset is Level 1's over-read buffer, which is why a pipelined request that arrived in the same packet is not lost. Tokio's TcpStream attempts the non-blocking read() syscall right now. If data is already buffered in the kernel, it returns immediately — no waiting, no reactor involvement, no magic. This fast path is the common case.
  2. EWOULDBLOCK? Park. The future registers interest — "wake task #417 when FD 12 is readable" — with the reactor, stores a Waker, and returns Poll::Pending. The task is now parked: zero CPU, no thread held, and its only cost is the memory of its own state machine.
  3. The executor keeps working. It runs other ready tasks on its worker threads. Idle workers steal queued tasks from busy ones, which is why one slow connection does not starve a core.
  4. The kernel signals. Bytes arrive on FD 12. The reactor's kevent() call returns, the reactor looks up FD 12 → waker.wake() → task #417 goes back on a run queue.
  5. Re-poll, resume in place. The executor re-polls task #417. The state machine resumes exactly at the await point — all its local variables intact, because they are fields of the generated struct. The read() now returns data, and execution continues to the next .await. Repeat forever.
Where the locals live. Because a paused future must resume with every local variable it had before the .await, those locals become fields of the compiler-generated struct. That is the whole cost model of async: a 500-line async fn with 100 await points generates a large state machine (many live locals across many suspension points); a pure-sync function generates none. Keep the state machine small — the theme of the next two sections.

Task-per-connection: how C10K is sidestepped here

Exactly three places in production code create tasks:

That is the whole concurrency structure of an 8,800-line proxy. Everything else is .await inside one of those three. Task-per-connection is what sidesteps C10K here: a task is not a thread — it is a state machine on the heap, scheduled onto one of 8 workers. 10,000 connections means 10,000 parked state machines, not 10,000 stacks. This was Level 1's choice, made before there was any vocabulary in the project to justify it; this level supplies the vocabulary.

Four levels, one un-named optimization

The zeros are not an accident. Four separate levels independently chose to keep their logic pure and synchronous:

L1

http.rs

Parsing and framing as functions over byte slices — no sockets in the parser.

L5

rewrite.rs

Pure transforms over head structs — "no sockets, no async, no I/O", in that level's own words.

L6

middleware

Deliberately rejected the textbook async fn handle(req, next) trait for a synchronous two-phase one (see below).

L8

tls.rs

Config construction only; the handshake .await lives in main.rs, not in the module that builds the ServerConfig.

Read through Level 9's lens, those four decisions are the same decision: keep the state machine small. Every .await in a function becomes a suspension point the compiler must be able to resume from, which means every live local becomes a field in the generated future. The pure-sync modules generate none at all. That is why serve_one being long is tolerable but rewrite.rs being async would not have been.

Why L6 rejected async fn handle(req, next) -> Response. An async middleware trait would have forced two things: an owned Response return value (so every body must be buffered into memory before the next stage runs), and an async suspension point in every middleware. The first pre-breaks Level 7's streaming — you cannot stream a body you have already collected into a Vec. So L6 chose a synchronous two-phase trait instead, and the streaming path survived to be built.

6 · No Lock Across .await — Compiler-Enforced

A worker thread that blocks is a worker thread that cannot poll anything else. With 8 workers, blocking one is a 12.5% capacity loss and a mysterious p99 spike; blocking all 8 is an outage that looks like a hang.

The three classic ways to block a Tokio worker:

Cause 1

Synchronous I/O

std::fs, blocking DNS, a synchronous HTTP client.

Cause 2

CPU-heavy work

A pathological regex, crypto, compression — anything that runs long without an .await.

Cause 3

Lock held across .await

The worst: the task parks while holding the lock, and the thread that could release it is now running someone else's code. Also a deadlock risk.

Cause 3 audited: structurally impossible here

Every production function that takes a lock is a plain fn, not an async fn:

FunctionSignature (abbreviated)Guards

Server::return_connfn return_conn(&self, conn: Conn<TcpStream>)L7 idle pool
ConnLimiter::try_acquirefn try_acquire(self: &Arc<Self>, ip) -> Result<ConnGuard, Refusal>L8 per-IP map
ConnLimiter::releasefn release(&self, ip: IpAddr)L8 per-IP map

This is stronger than a code-review convention. You cannot write .await inside a non-async fn — it is a compile error. So the compiler enforces "never hold a lock across an .await" rather than trusting a reviewer to spot it. Three levels each wrote a comment explaining why they used std::sync::Mutex over tokio::sync::Mutex; this signature list is the proof those comments are still true. A comment can rot; a plain fn signature cannot silently grow an .await.

Corroborating facts, verified against the tree: tokio::sync appears in this codebase only inside comments explaining why it is not used — there is not one real use. spawn_blocking appears zero times. thread::sleep appears zero times.

Causes 1 and 2 audited

Cause 1

Synchronous std::fs: present but harmless

tls.rs uses File::open / std::fs::metadata to load certificates. This runs in TlsArgs::build(), which main.rs calls before TcpListener::bind — so it executes once, at startup, while the runtime has no request work to starve. Level 8 chose that ordering to fail with exit 1 before announcing a listener; the async-hygiene benefit is a coincidence, recorded as one rather than claimed as foresight. For it to become a bug, the file read would have to move into the request path.

Cause 2

CPU-bound regex: safe for a non-obvious reason

router.rs:53 runs re.is_match(path) on the worker thread for every request matched against a ~regex route. In nginx or any PCRE-based proxy this would be a genuine hazard — catastrophic backtracking can turn one crafted path into seconds of CPU, freezing a worker. It is safe in Ferrum only because Rust's regex crate has no backtracking and guarantees linear time in the input length; the pathological blowup is not expressible. The safety comes from a Level 2 dependency choice. Swap that crate for a backtracking engine and this line becomes a DoS vector.

7 · Two Findings This Reading Turned Up

Neither is a bug; both are the kind of thing only visible from this level. Both are recorded, not fixed — and the "not fixed" is a deliberate call, not laziness.

7.1 · Backend addresses are re-resolved on every connect

Server.addr is a String (balancer.rs:402). Startup validation (balancer.rs:973) only checks the shape — a non-empty host and a port that parses as a u16 ≥ 1 — and then keeps the string. So TcpStream::connect(&addr) at proxy.rs:853 goes through ToSocketAddrs on every pool miss.

For an IP literal like 127.0.0.1:9001 that parse is trivial. For a DNS name like api.internal:8080, which the shape check happily accepts, it is a getaddrinfo call. Tokio routes that through its blocking pool rather than the worker, so it does not freeze a core — but it does consume a blocking-pool thread per connect, with no DNS caching and no respect for TTLs.

Level 7's connection pooling hides most of this: a pool hit skips connect entirely, so the cost appears only on misses. That is why it has never shown up. The clean-looking fix — resolve once at startup into a SocketAddr — is a worse answer for DNS-named backends, where re-resolution is the only way to follow a backend that moves. The genuinely correct version is a small resolver cache with TTL awareness, which is real work and belongs in a level of its own, not smuggled into a theory chapter.

Recorded, not fixed.

7.2 · The runtime's shape is entirely implicit

Eight worker threads, a multi-threaded work-stealing scheduler, and a blocking pool all exist because #[tokio::main] defaults to them. Nothing in the codebase mentions any of it. features = ["full"] in Cargo.toml is the only hint, and it points the wrong way — it reads like "give me everything" rather than "select the multi-threaded scheduler."

This matters the first time someone tunes the proxy, because the worker count is a real dial and it is currently invisible. Not changed, because changing a default with no benchmark behind it is exactly the "measure, don't guess" mistake the KB warns about in Level 7 — and there is still no benchmark.

Recorded, not fixed.

Deliberately not done, and why. No io_uring experiment (Linux-only; this machine is kqueue). No runtime tuning (see 7.2 — no benchmark to justify it). No DNS caching (see 7.1 — a real feature, not a theory aside). No spawn_blocking added for symmetry (nothing in the request path needs it; adding one would be cargo-culting). No benchmarks — the missing wrk/oha baseline stays Level 7's recorded debt rather than being quietly reassigned here.

9 · How the Industry Does It

Everyone solves C10K the same way — an epoll/kqueue event loop over non-blocking sockets. The differences are who writes the state machines and whether workers share memory.

nginx, read back through this level's vocabulary

With Level 9's words, nginx's design reads fluently:

  • One master process handles config and signals; it forks N single-threaded workers.
  • Each worker runs epoll_wait in a loop — the same loop mio runs.
  • All connection state lives in explicit hand-written C structs, where Ferrum has compiler-generated state machines.
  • SO_REUSEPORT lets every worker accept on the same port, with the kernel spreading load.
The one-sentence version: Tokio and nginx are the same architecture wearing different clothes — both are an epoll/kqueue event loop over non-blocking sockets. The only difference is who writes the state machines: nginx's authors did it by hand in C, and Rust's compiler does it for you at zero runtime cost. That is the entire "fearless async" pitch.

One asymmetry worth naming: nginx's model is process-per-core with no shared mutable state between workers, so it has no lock-contention problem to solve. Tokio's is threads-per-core with shared state and work stealing, which is why Levels 6, 7, and 8 each had to make a deliberate sharding decision (16 hash shards, per-Server pools, one map behind a mutex). Ferrum pays a cost nginx does not — and buys the ability to share a route table and a connection pool across all cores without IPC.

nginx

Process-per-core, hand-written C state machines

Mechanism: master + N single-threaded workers, each an epoll_wait loop; SO_REUSEPORT for accept spreading.

Trade-off: no shared mutable state → no locks, but also no cheap cross-core sharing — caches and state are per-worker or go through shared memory / a separate store.

HAProxy

Event loop, historically single-process

Mechanism: an epoll/kqueue event loop; modern versions run multiple threads, and its heritage is a tightly optimized single-process reactor (as of recent releases).

Trade-off: extremely low per-connection overhead and predictable latency; the concurrency model is more manual than a general-purpose async runtime.

Apache httpd

Pluggable MPMs, incl. thread/process-per-connection

Mechanism: Multi-Processing Modules — prefork (process-per-connection), worker (threads), event (an epoll-style loop to escape one-thread-per-idle-keepalive).

Trade-off: the prefork/worker lineage is exactly the C10K-vulnerable thread-per-connection model Level 9 opens with; the event MPM was the retrofit toward readiness-driven I/O.

Envoy

Threaded event loops (libevent), C++ state machines

Mechanism: N worker threads, each running its own event loop; connections are pinned to a thread, and shared state uses thread-local slots with a main-thread update path to minimize locking (as of recent versions).

Trade-off: a threads-per-core model like Tokio's, but the "avoid locks" work is done by an explicit thread-local architecture rather than by the compiler refusing .await in a locking fn.

Where Ferrum honestly sits. Ferrum is a teaching build. It gets the same O(ready) event loop as all four — for free, via Tokio and mio — and gets its "no lock across await" guarantee from the Rust compiler rather than from hand-written thread-local structures. What it lacks is the years of production hardening: no SO_REUSEPORT accept sharding, no tuned worker count (§7.2), no benchmark to justify any of it. The architecture is right; the mileage is not there yet.

Glossary

C10K

The problem of serving 10,000 concurrent connections. Fatal under thread-per-connection; dissolved by event-driven I/O.

O_NONBLOCK

Socket flag making read()/write() return EWOULDBLOCK instead of parking the thread. Tokio sets it; Ferrum never does.

Readiness vs. completion

Readiness (epoll/kqueue): "you may read now" — you still call read(). Completion (io_uring/IOCP): "the read is DONE" — kernel did it for you.

Reactor

The component (here mio) holding one kernel readiness object, mapping FDs to Wakers, and calling kevent/epoll_wait.

Executor

The scheduler that polls ready futures on worker threads and steals work between them. Tokio's multi-threaded scheduler here.

Future / state machine

What an async fn compiles to. Inert until polled; its live locals are struct fields so it can resume at the await point.

Waker

A handle stored at park time; calling wake() puts the task back on a run queue for re-polling.

Poll::Pending

The value a future returns when it cannot make progress yet — the signal to park the task.

Work stealing

Idle workers pull queued tasks from busy ones, so one slow connection cannot starve a core.

Blocking pool

A separate Tokio thread pool for blocking operations (e.g. getaddrinfo), so they do not freeze a worker — where finding 7.1's DNS resolution lands.
