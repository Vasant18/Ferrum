Core Networking
The accept loop, HTTP/1.1 parsing, body framing & the Conn<S> streaming engine

The foundation everything else stands on. Before Ferrum can route, balance, cache, or defend, it has to turn a raw TCP byte stream into HTTP/1.1 messages it understands — and hand those messages to a backend without becoming a request-smuggling relay. This level builds the task-per-connection accept loop, the from-scratch parser, the four body-framing modes, the 16 KB windowed streaming engine, and the smuggling defenses that make forwarding safe.

Executive Summary

Level 1 is the part of Ferrum that talks to sockets and speaks HTTP/1.1 from first principles — no framework, no hyper, just tokio and the raw protocol.

The accept loop in main.rs pulls completed connections off the kernel backlog and hands each to its own Tokio task via tokio::spawn, so one slow client never blocks another. Inside a task, proxy.rs runs a per-connection loop (handle_client → serve_one) that serves requests sequentially with HTTP/1.1 keep-alive, opening one backend connection per request. http.rs is the pure-logic core: it finds where a message head ends (find_head_end), parses the request/status line and headers into owned structs, and — the security-critical decision — computes how the body is framed via the BodyFraming enum: None, a fixed Length(n), Chunked, or UntilClose.

Bodies never sit in memory whole. Conn<S> streams them through a 16 KB window (BUF_SIZE), so a 2 GB upload costs 16 KB of RAM. The head is capped at 16 KB (MAX_HEAD_BYTES) and must arrive within 30 seconds (HEAD_READ_TIMEOUT), closing two classic denial-of-service holes. And because a proxy that disagrees with its backend about where a body ends becomes a request-smuggling weapon, the parser is deliberately strict: it rejects bare CR/LF in the head, duplicate Content-Length or Transfer-Encoding headers, the Content-Length + Transfer-Encoding combination, and non-numeric lengths.

The whole thing is built on Conn<S>, a buffered reader generic over any stream type S — a design seam that looks like over-engineering at Level 1 and pays off enormously at Level 8, when the exact same code path serves a TLS stream with zero changes. Everything later levels do — routing, load balancing, TLS, caching, the WAF — is layered on top of these primitives. This is a teaching build, not production; where it is cruder than nginx (one backend connection per request, owned-String parsing instead of zero-copy), the comparison section says so plainly.

The Big Picture

Level 1 is the pipeline — every other level inserts a stage into the path this level draws. Here is one request/response exchange, with the Level 1 stages highlighted. Notice the symmetry: the request leg and the response leg run the same read-head → parse → frame → stream shape.

Analogy: TCP is a mail slot that delivers a shredded letter one handful of confetti at a time, in no guaranteed handful size. Level 1 is the clerk who catches the confetti in a tray (Conn's buffer), waits until a blank line proves the letter's header is complete, reads the header to learn how long the letter is, and only then starts copying the body onward — a page at a time, never holding the whole letter. The clerk also refuses letters with forged page-count markers (the smuggling defenses), because passing one along would let a forger sneak a second letter past the mailroom.

1 · The Accept Loop

The front door: pull one completed connection off the kernel backlog, hand it to its own task, repeat. The loop itself does almost nothing — and that is the point.

Task-per-connection with tokio::spawn

In main.rs, after binding a TcpListener, the accept loop is deliberately tiny: listener.accept() yields a (TcpStream, SocketAddr), and the very next thing we do is tokio::spawn a task that owns that stream and runs proxy::handle_client. The loop then immediately goes back to accept(). Nothing that could block — no parsing, no backend dial, no TLS handshake — happens on the loop's own thread.

The why: anything slow inside the accept loop delays every new client, because there is exactly one loop. A model where you parsed the request before spawning would mean one client trickling its header one byte a minute stalls the acceptance of all others — a one-attacker, whole-server denial of service that passes every functional test (a proxy serving one client at a time still "works"). Spawning first makes each connection's slowness that connection's own problem. Tokio multiplexes the thousands of resulting tasks across a small pool of OS threads, so "one task per connection" does not mean "one OS thread per connection."

loop {
    // (Level 12 wraps this in tokio::select! against signals; Level 1's
    // core is just accept-then-spawn.)
    let (stream, peer) = listener.accept().await?;
    let _ = stream.set_nodelay(true);          // disable Nagle (see below)
    let routes = Arc::clone(&routes);
    tokio::spawn(async move {
        proxy::handle_client(stream, &routes, peer, /* ... */).await;
    });
}
What you're reading vs. what Level 1 wrote. Today's main.rs loop is wrapped in tokio::select! against SIGTERM/SIGINT/SIGHUP (Level 12), gated by CIDR and connection-limit checks (Level 8), and threads a metrics handle and cache through (Levels 10–11). Mentally strip all of that: Level 1's loop was accept → set_nodelay → spawn(handle_client), nothing more. The Err arm — logging a transient accept error (e.g. EMFILE when out of file descriptors) and continuing rather than exiting — is Level 1, and it matters: a proxy that dies the first time it runs out of FDs is not a proxy.

TCP_NODELAY: turning off Nagle's algorithm

Right after accept we call set_nodelay(true) on the socket. Nagle's algorithm coalesces small outbound writes, waiting a few milliseconds to see if more data arrives so it can send one larger packet. That is a win for chatty interactive protocols and a loss for a proxy: our serialized request/response heads are small, standalone writes that we want on the wire now. Proxies universally disable Nagle for this reason.

The subtle relocation: in Level 1 this lived inside handle_client, which then held a concrete TcpStream. Level 8 made handle_client generic over the stream type (see §7), and set_nodelay is a TcpStream-inherent method the generic code no longer knows it has — so it moved up to the accept loop, applied to the raw socket before any TLS wrap. That is also the only place it can go, because once the TLS stream owns the TcpStream, the option (which lives on the file descriptor) is no longer reachable.

2 · Parsing the Head

Turn an undifferentiated byte stream into a RequestHead — and answer the two questions everything downstream depends on: where does the head end, and what does it say?

Finding the head boundary: find_head_end

An HTTP/1.1 message head (the request/status line plus all header lines) ends at the first blank line — the byte sequence \r\n\r\n. find_head_end scans a 4-byte sliding window for that terminator and returns the index just past it, or None if it hasn't arrived yet:

pub fn find_head_end(buf: &[u8]) -> Option<usize> {
    buf.windows(4).position(|w| w == b"\r\n\r\n").map(|i| i + 4)
}

None is not an error — it is the signal to Conn::read_head to read more bytes and try again. This is the crux of framing a stream protocol: TCP does not respect message boundaries. One read() may hand you half a head, a whole head, or a head plus the start of the body plus the start of a second pipelined request. The parser cannot assume any read is a message.

The owned-String parse into RequestHead / ResponseHead

parse_request_head takes exactly the head bytes located by find_head_end and produces a struct with owned fields:

pub struct RequestHead {
    pub method: String,
    pub target: String,          // origin-form, e.g. "/api/users?page=2"
    pub version: Version,        // Http10 | Http11
    pub headers: Vec<(String, String)>,
}

The head must be valid UTF-8 (rejected otherwise rather than guessed at); the request line is split into exactly METHOD SP target SP HTTP-version — three parts, no more, no fewer; and each header line is split at the first : into a name and a trimmed value. The response side is symmetric: parse_response_head produces a ResponseHead with version, a status validated into the 100–599 range, a reason, and headers.

Why owned Strings, not borrowed slices? Zero-copy parsing (headers that borrow from the read buffer) is faster and is exactly what Level 7 introduces. At Level 1 we deliberately pay the allocation cost to keep lifetimes out of the picture: the head struct outlives the buffer it came from, can be freely rewritten (Level 5 mutates headers in place), and the code stays legible. Naming that as a conscious trade — "correctness and clarity now, zero-copy later" — is the lesson, not an oversight.

Case-insensitive header lookup. Header names are case-insensitive per RFC 9110, and clients genuinely send host, Host, and HOST. The header() helper compares with eq_ignore_ascii_case, so every downstream lookup (framing, keep-alive, routing) is spelling-agnostic without callers thinking about it.

3 · Body Framing & the BodyFraming Enum

The single most security-sensitive decision a proxy parser makes: given the head, how do we know where the body ends? Get this wrong and you become a smuggling relay.

The four framing modes

HTTP/1.1 delimits a body in exactly a few ways, and Ferrum models them as a four-variant enum — making "how is this body framed?" a value the type system tracks, not a tangle of booleans:

pub enum BodyFraming {
    None,          // no body (GET without length; 204/304; HEAD response)
    Length(u64),   // exactly N bytes follow the head
    Chunked,       // hex-sized chunks until a "0\r\n\r\n" terminator
    UntilClose,    // body runs until the peer closes (responses only)
}

Two functions compute it. request_body_framing and response_body_framing share the ordering rule of RFC 9112 §6: Transfer-Encoding wins over Content-Length. If a Transfer-Encoding: chunked is present it means Chunked; else a Content-Length means Length(n) (or None when n == 0); else — for a request — None, because a request can never legitimately use until-close framing.

Why requests and responses differ

The response function takes the request method and the status code as extra inputs, because some responses are bodiless by definition regardless of their headers: a HEAD response, any 1xx, a 204 No Content, and a 304 Not Modified all carry no body even if they announce a Content-Length. Those are checked first and short-circuit to None.

The decisive asymmetry is the fallthrough. A request with no framing headers has no body — full stop. A response with no framing headers is legal HTTP/1.0-style UntilClose: "the body is everything until the server closes the connection." A request could never use that framing (a client cannot say "my body ends at EOF" and still expect to read a reply on the same connection), so UntilClose is a response-only outcome. Encoding that rule in which function returns which variant means the illegal combination is simply unrepresentable.

Strict Content-Length parsing. parse_content_length accepts ASCII digits only. It rejects a leading +, embedded commas (5, 5), internal whitespace (5 5), and hex (0x5) — every one of which is a framing-desync attempt, because different parsers tolerate different sloppiness. (Leading/trailing whitespace is legitimately trimmed by the header parser first, so a value that arrives as "5 " is fine; it is the internal junk that's rejected.)

4 · 16 KB Windowed Streaming

The memory-safety property that makes Ferrum usable: a body never sits in RAM whole. A 2 GB upload costs 16 KB of memory, not 2 GB.

The window: BUF_SIZE = 16 * 1024

Every Conn<S> owns one BUF_SIZE (16 KB) buffer. When copying a Length(n) body, copy_exact loops: read up to a window's worth of bytes, write exactly the portion that belongs to this body onward, drop those consumed bytes, repeat until n is exhausted. At no point does more than 16 KB of body live in memory — the len counter shrinks toward zero while the buffer is reused in place.

async fn copy_exact<W>(&mut self, dst: &mut W, mut len: u64) -> io::Result<()> {
    while len > 0 {
        if self.filled == 0 {
            let n = self.stream.read(&mut self.buf).await?;
            if n == 0 { return Err(/* connection closed mid-body */); }
            self.filled = n;
        }
        // Take only what belongs to THIS body; the rest may be the next
        // pipelined request and must stay buffered.
        let take = (self.filled as u64).min(len) as usize;
        dst.write_all(&self.buf[..take]).await?;
        self.consume(take);
        len -= take as u64;
    }
    Ok(())
}

The why (and the security tie-in): unbounded buffering of unauthenticated input is how proxies get OOM-killed. A windowed copy makes per-connection memory flat regardless of payload size, and — the deeper payoff — it means there is already a loop that sees every byte. Level 8's body-size cap is therefore not new machinery: it is a running total and one comparison bolted onto this existing loop. Named mistake #1 at that level is "read the whole body, then check the size limit — by which point the damage is done." Level 1's window is what makes the correct, enforce-during-copy version cheap.

Chunked relay: copy_chunked

A chunked body has no declared length; it is a sequence of <hex-size>\r\n<data>\r\n frames, terminated by a zero-size chunk, then optional trailers and a final blank line. copy_chunked relays this framing verbatim, reusing copy_exact for each chunk's data payload so the 16 KB window still bounds memory. Two details are worth noting:

  • Chunk extensions are stripped. A size line like 5;ext=val has everything after the ; removed — we forward only what we understand, and re-emit a clean 5\r\n.
  • Trailers are forwarded. After the zero-chunk, trailer lines are relayed until the terminating blank line.

The UntilClose case is the simplest: relay whatever is already buffered, then pump the stream to EOF with tokio::io::copy. By definition it consumes the connection — there is no "next request" on a socket whose end-of-body is its close.

5 · Forwarding & Keep-Alive

Relay the request to a backend, relay the response back, and — on HTTP/1.1 — keep the client socket open to serve the next request on it. With pipelining handled correctly.

The per-connection loop

handle_client wraps the client stream in a Conn and loops, calling serve_one for each exchange. serve_one returns Ok(true) to keep the connection alive for another request, Ok(false) for a clean close, or an Err that logs and drops the connection. One connection's failure is that connection's problem — the accept loop and every other task are unaffected.

Within one exchange the shape is: read + parse the request head (under the slowloris deadline) → compute request framing → forward the head and stream the body to the backend → read + parse the response head → stream the response body back to the client → decide keep-alive. In Level 1 the backend was a single hard-wired address and a new TCP connection was opened per request; connection pooling to reuse backend sockets is Level 7.

Keep-alive and pipelining

wants_keep_alive encodes the version defaults: HTTP/1.1 is persistent unless the client sends Connection: close; HTTP/1.0 closes unless it sends Connection: keep-alive. When the exchange keeps the connection, the loop goes back to read_head on the same Conn.

Pipelining falls out of the buffer discipline. Because Conn preserves everything it over-read, a client that sends two requests back-to-back — POST .../body...GET /next... — is handled correctly without special code: copy_exact takes only the first body's bytes, consume shifts the leftover GET /next... to the front of the buffer, and the next read_head finds it already waiting. The "bytes read but not yet consumed" problem is solved once, in Conn, and every consumer benefits.

Hop-by-hop headers must be stripped. Headers like Connection, Keep-Alive, Transfer-Encoding, TE, and Upgrade describe one TCP hop, not the end-to-end message. Forwarding a client's Connection: close verbatim would close our backend leg; mishandling Transfer-Encoding here is the literal mechanism of request smuggling. Ferrum strips the whole hop-by-hop set (plus anything the Connection header itself names) and manages each leg's connection semantics itself — re-declaring canonical framing rather than passing the client's through.

The deadlines that close DoS holes

Three timeouts exist so a misbehaving or hung peer can't hold resources forever:

ConstantValueGuards against
HEAD_READ_TIMEOUT30 sSlowloris: a client trickling one header byte a minute gets a 408 and is cut off, instead of pinning a socket forever.
BACKEND_CONNECT_TIMEOUT5 sA backend that never accepts the TCP connect — the kernel default (~2 min) is an eternity to hold client resources.
MAX_HEAD_BYTES16 KBAn unbounded head: read_head errors once the buffer crosses this cap, so an attacker can't stream an infinite header set to exhaust memory.

(The 30 s backend response timeout in today's code is a Level 7 tunable; Level 1's own head-and-connect deadlines are the two above.)

6 · Request-Smuggling Defenses

A proxy sits between a client and a backend. If the two disagree about where one request ends and the next begins, an attacker can smuggle a hidden request past one of them. Level 1's parser is strict precisely to make that disagreement impossible.

What smuggling is, in one sentence

HTTP request smuggling exploits a parsing discrepancy: the proxy thinks a request is N bytes long and the backend thinks it is M, so the leftover M−N bytes the proxy forwards get interpreted by the backend as the start of a new request — one the attacker fully controls, injected in front of some other user's real request. The defenses below all close one avenue for that discrepancy.

The four hardening rules

  1. Reject bare CR/LF in the head. We split header lines strictly on \r\n and reject any residual lone \r or \n. We do not use str::lines(), which treats a bare \n as a line break — that leniency lets an attacker write Foo: bar\nEvil: x that we'd read as two headers but a stricter downstream reads as one (or vice versa). RFC 9112 §2.2 forbids bare CR/LF in field lines; we enforce it. A space before the colon (Host : x, RFC 9112 §5.1) is rejected for the same "lenient parsers disagree" reason.
  2. Reject duplicate Content-Length. Two Content-Length headers let a proxy honor one value and a backend the other. check_framing_headers counts occurrences (case-insensitively) and errors on more than one.
  3. Reject duplicate Transfer-Encoding. Same reasoning; more than one is an error.
  4. Reject Content-Length + Transfer-Encoding together (CL+TE). This is the canonical smuggling combo — the classic attack is a proxy that frames by one header while the backend frames by the other. RFC 9112 §6.1 says treat it as an error at the edge, and we do: both present at once is rejected outright.

Plus a fifth, on the forwarding side: because strip_hop_by_hop removes TE but not Transfer-Encoding, the forward path explicitly removes any inbound Transfer-Encoding before re-declaring its own canonical chunked — so the backend can never receive two Transfer-Encoding lines. The same discipline applies on the response leg toward the client.

Why strictness beats leniency here. Postel's Law ("be liberal in what you accept") is actively dangerous for a proxy's framing parser. Every byte of leniency is a byte where we might disagree with the backend, and a disagreement about framing is a smuggling primitive. So the parser is intentionally, unapologetically pedantic: malformed framing is a 400 Bad Request at parse time, not a best-effort guess forwarded downstream. The request-time path never has to cope with a malformed head — by the time framing is decided, the message is known-valid or already rejected.

7 · The Conn<S> Design

The seam that looks like over-engineering at Level 1 and pays off at Level 8. One buffered-reader type, generic over any stream, so plaintext and TLS ride the exact same code path.

What Conn<S> is

Conn<S> is a buffered reader that owns the "bytes read but not yet consumed" problem. It holds the stream, a 16 KB buffer, and a filled count marking how many buffered bytes are still valid, unconsumed data. Its methods — read_head, copy_exact, copy_chunked, read_line, consume — are all that reads and writes go through. Crucially, its bound is S: AsyncRead + AsyncWrite + Unpin: it works with anything that can be read and written asynchronously, not specifically a TcpStream.

pub struct Conn<S> {
    stream: S,
    buf: Vec<u8>,
    filled: usize,     // bytes [0..filled) are valid, unconsumed
}
impl<S: AsyncRead + AsyncWrite + Unpin> Conn<S> { /* ... */ }

Why generic-over-stream is the whole point

At Level 1 there is only one kind of stream — a plaintext TcpStream — so making Conn (and later handle_client/serve_one) generic over S buys nothing yet. It looks like premature abstraction. Then Level 8 terminates TLS, and the client stream becomes a tokio_rustls::server::TlsStream<TcpStream> — a completely different concrete type that nonetheless also implements AsyncRead + AsyncWrite. Because the entire proxy core was written against the trait bound and never against the concrete type, the same code serves both listeners with zero changes to the hot path. The plaintext branch passes a TcpStream; the TLS branch passes a TlsStream; the proxy engine cannot tell the difference and does not need to.

Generics, not an enum. The alternative — enum Stream { Plain(TcpStream), Tls(TlsStream) } — would cost a match on every single read and write, in the hottest loop in the program. Monomorphizing over S compiles two specialized copies into the binary instead: a little more code size, no per-operation branch. For a proxy, that is the right trade, and it is a clean illustration of Rust's static dispatch versus dynamic dispatch decision.

Analogy: Conn<S> is a universal power tool that accepts any standard drill bit. At Level 1 you only own one bit (plaintext TCP), so the interchangeable chuck seems pointless. At Level 8 you get a second bit (TLS) — and because you bought the tool with the standard chuck, it just clicks in. The foresight cost nothing at purchase and saved a whole second tool later.

Industry: nginx / httpd / HAProxy / Envoy

Every production proxy has to accept connections, parse HTTP/1.1, frame bodies, and defend against smuggling. Here is how the field does it and where Ferrum lands honestly. (Architecture as generally understood; qualify specifics with "as of" — behaviors drift across versions.)

nginx

Event loop + arena parser

Mechanism: a fixed set of worker processes, each running an epoll/kqueue event loop over many connections — an explicit state machine, not one task per connection. Its HTTP parser is a hand-written, zero-copy state machine over per-connection buffers, and it is famously strict about framing.

vs. ours: Ferrum's task-per-connection on Tokio is far simpler to read — the control flow is linear async code — but nginx's explicit event loop and buffer-arena parser are more memory-frugal and faster. Ours allocates owned Strings per head (Level 7 fixes that); nginx never does.

Apache httpd

MPMs: prefork / worker / event

Mechanism: pluggable multi-processing modules. Classic prefork is one process per connection; worker is threads; the modern event MPM adds an event loop to hand off keep-alive connections so a thread isn't pinned while idle.

vs. ours: httpd's event MPM exists to solve exactly the problem Tokio solves for us for free — don't pin an OS thread to an idle keep-alive connection. Ferrum gets that from the async runtime without choosing an MPM; httpd carries the historical baggage of the thread-per-connection models it grew out of.

HAProxy

Single-threaded event loops

Mechanism: a small number of threads, each a tight event loop, with a meticulous internal HTTP state machine (HTX) and a well-earned reputation for strict, security-conscious message parsing and anti-smuggling behavior.

vs. ours: HAProxy is the gold standard for exactly the framing strictness Level 1 aspires to — dup-header and CL+TE rejection are table stakes there. Ours implements the same rules (bare-CRLF, dup CL/TE, CL+TE) but as a teaching-scale hand-rolled parser, not HAProxy's battle-tested HTX engine.

Envoy

Threaded, codec-based

Mechanism: C++ worker threads over libevent, with pluggable HTTP codecs (its own HTTP/1 codec, nghttp2 for HTTP/2). Framing and header validation are handled by the codec layer, with configurable strictness.

vs. ours: Envoy abstracts HTTP/1 vs HTTP/2 behind a codec interface; Ferrum is HTTP/1.1-only and hand-parses it. Envoy's codec is production-grade and multi-protocol; Level 1 is a single-protocol teaching parser — but the concerns (where does the head end, how is the body framed, is this smuggling) are identical.

The honest bottom line: Ferrum's concurrency model (spawn a task per connection, let the runtime multiplex) is the most readable of the bunch and genuinely scales fine for a teaching build — Tokio is doing the hard multiplexing nginx and httpd hand-code. Where Ferrum is deliberately crude is the parser (owned Strings, HTTP/1.1 only) and the backend leg (a fresh connection per request until Level 7). What it gets right, and what actually matters, is the framing strictness: the bare-CRLF, dup-header, and CL+TE defenses put it in the same anti-smuggling camp as HAProxy, which is the correct company to keep for the one decision a proxy cannot afford to get wrong.

Glossary

Conn<S>

Buffered reader generic over any AsyncRead + AsyncWrite stream; owns the 16 KB window and the unconsumed-bytes remainder. The seam that lets plaintext and TLS share one code path.

BodyFraming

The four-variant enum (None/Length/Chunked/UntilClose) that records how a body is delimited on the wire.

Head

The request/status line plus all header lines, terminated by a blank line (\r\n\r\n). Located by find_head_end.

Windowed streaming

Copying a body one 16 KB buffer at a time so per-connection memory is flat regardless of body size.

Request smuggling

Exploiting a proxy/backend disagreement about where a request ends to inject a hidden request. Closed here by strict framing (bare-CRLF, dup-header, CL+TE rejection).

Slowloris

A DoS that trickles a request head slowly to pin a connection forever. Defended by HEAD_READ_TIMEOUT (30 s) and MAX_HEAD_BYTES (16 KB).

Hop-by-hop header

A header describing one TCP hop (Connection, Keep-Alive, TE, Upgrade, ...), stripped before forwarding rather than relayed end-to-end.

Keep-alive / pipelining

Reusing one client socket for successive requests (HTTP/1.1 default); pipelining (back-to-back requests) is handled for free by Conn's preserved over-read buffer.

tokio::spawn

Hands a connection to its own async task so one slow client never blocks the accept loop or other connections; the runtime multiplexes many tasks over few OS threads.
