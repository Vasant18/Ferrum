Production Features
config files, graceful shutdown, hot reload — the gap between a program and infrastructure

A program runs until you kill it. Infrastructure changes its configuration, upgrades itself, and shuts down — without dropping a single in-flight request. Level 12 closes that gap with three deliverables (a config file, a graceful drain, a hot reload) and two things it deliberately explains-but-does-not-build (graceful restart, worker processes). The recurring theme: the machinery was already there — L8's RAII connection counter is a drain tracker, Rust's Weak is a shutdown signal, the CLI parser's last-write-wins is the precedence rule.

Executive Summary

Level 12 makes Ferrum behave like infrastructure: it reads a config file, reloads that file on SIGHUP without a restart, and drains cleanly on SIGTERM/SIGINT.

The config file (config.rs, 481 lines) is a stated TOML subset — key = value, one [upstreams] table, one routes string array, # comments, and loudly nothing else. It is not a second schema: it lowers onto the CLI vocabulary that eleven levels already built (one parser per value, forever). File args are placed first in the argument vector and real CLI args after, so main.rs's existing last-write-wins match arms implement "CLI overrides file" with zero precedence code. Duplicate keys are hard errors — silent last-wins is how config drift hides — and every error carries a line number.

--validate is nginx's nginx -t: parse and exit, but through the full boot path including TlsArgs::build, so a config that parses but has an undeclared upstream or an incoherent TLS setup fails exactly as boot would. Boot, --validate, and reload share ONE extracted parse_settings function rather than a lenient "reload parser" that could drift.

Graceful shutdown is a four-step choreography on machinery already built: tokio::signal streams select!ed with accept(); dropping the listener refuses new connections at the kernel; L8's ConnLimiter — the RAII guard built for security accounting — is the drain tracker; and a process-wide AtomicBool makes each completing exchange answer Connection: close. A --drain-timeout (default 15 s) bounds the wait; a second signal skips it.

Hot reload is the arc-swap pattern with std only: the shared handle is RwLock<Arc<RouteTable>>, snapshotted per exchange. A request mid-flight keeps the table it started with; the next keep-alive request sees the new config. The new table is built and validated wholesale off to the side; only success does one pointer store. An invalid file keeps the old config live. Probers hold Weak<Upstream> and upgrade per tick — the Weak IS the shutdown signal, no kill channels. 261 unit tests (250 kept green, +11), live-verified end to end.

The Big Picture

Level 12 does not add a stage to the request path — it wraps the whole process lifecycle around it. The three deliverables touch startup (config), the accept loop (shutdown + reload signals), and every exchange (the per-request table snapshot and the drain flag).

Where earlier levels added machinery inside a request, this level adds machinery around requests. The one place it reaches into the hot path is the highlighted stage below: each exchange snapshots the current Arc<RouteTable> and checks the shutdown flag on the way out. Everything else — parsing a file, handling a signal, rebuilding a table — happens on the process's control plane, not its data plane.

Analogy: a program is a food truck — it opens, serves, and when the owner leaves, the shutters slam mid-order. Infrastructure is a restaurant: last orders are called (stop accepting), the kitchen finishes the tickets already in (drain), tomorrow's menu is swapped in overnight without closing (hot reload), and there's a hard closing time so one lingering table can't keep the staff till dawn (drain deadline).

The Config File: the CLI, persisted

The most important decision in this level is not how to parse a file — it is refusing to invent a second configuration language. Ferrum already had one: eleven levels of flags, route specs, and upstream specs, each with a parser and startup guardrails.

A config file that invented a second schema — nested tables for routes, a [[middleware]] array, its own duration grammar — would mean every value has two parsers that must agree forever. They wouldn't; config-vs-flag drift is a classic operational bug (the flag accepts 64m, the file's own size parser quietly reads 64). So config.rs parses a stated TOML subset and lowers it onto the CLI vocabulary 1:1. In the file's own words: max-conns = 10000 IS --max-conns 10000, an [upstreams] entry IS an --upstream NAME=SPEC, a routes element IS a positional route spec.

The subset, stated exactly

The parser handles precisely these forms and rejects everything else with a line number:

# ferrum.toml — every value is a CLI flag name, minus the leading --
listen    = "127.0.0.1:8080"
admin     = "127.0.0.1:9100"
log-level = "info"
max-conns = 10000
tls-cert  = "cert.pem"        # startup-only (see Reload Scope)
no-access-log = true          # a switch: true emits --no-access-log, false emits nothing

[upstreams]                    # one table, NAME = "SPEC" (the --upstream grammar)
api = "127.0.0.1:9001,127.0.0.1:9002;health=/health"

routes = [                     # one string array, the route-spec grammar verbatim
  "/api/**=api;cache=60;rate=100/s",
  "/=api",
]

Nothing else. No nested tables, no floats, no datetimes, no dotted keys, no inline tables — "this parser refuses to half-understand a file" (the module doc's phrasing). Values are typed by shape: a leading " is a string, true/false is a bool, all-digits is an integer. Sizes like 64m and durations like 30s are strings to this parser — quoted, and handed unchanged to parse_size/parse_duration downstream. One grammar per value, in exactly one place.

Precedence: CLI beats file, with zero precedence code

The requirement is that rproxy --config ferrum.toml --log-level debug runs the file's config with debug logging. The clever part is the mechanism: config::load() returns a FileConfig { listen, args } where args is a flag vector the CLI parser already speaks. main.rs builds one merged vector — file args first, real CLI args appended after — and feeds it to parse_settings. That function's loop already does last-write-wins (--log-level seen twice keeps the last), so the later CLI value simply overwrites the earlier file value.

// main.rs — the entire "precedence engine"
let mut merged: Vec<String> = Vec::new();
merged.extend(cfg.args.iter().cloned());   // file first
merged.extend(cli_iter);                    // real CLI after
let settings = parse_settings(merged)?;     // last-write-wins does the rest

There is no precedence table, no priority enum, no "if CLI is set, else file" ladder anywhere. The ordering of the vector is the precedence. The one exception is listen: it is positional on the CLI, so it cannot ride inside args. FileConfig.listen is carried separately and applied by main only when the real CLI didn't supply its own listen address.

Duplicate keys are a hard error

TOML-standard-ish behavior would be last-wins. Ferrum makes a duplicate key a hard error instead. The reason is operational, not pedantic: in a 400-line config, max-conns appearing twice is drift in progress — someone edited the wrong copy, a merge doubled a block, a templating system emitted a stray line. Silently honoring the second occurrence is exactly how that stays hidden until 3 a.m. Duplicate upstream names in the same file are caught in the parser too (rather than only downstream in build_routes) purely for the better line number.

Watch out: the # comment stripper is quote-aware. A # inside a quoted string (say a URL fragment) is preserved; only a # outside a string starts a comment. This is why there is a real strip_comment pass rather than a naive split('#').

--validate: nginx -t, the full boot path

A validator that only checks syntax is worse than useless — it gives deploy pipelines false confidence. --validate answers the same question a real boot would.

The flag means "parse and exit," but reaching the exit requires running the entire startup path. If config::load succeeds the file is syntactically fine; the dangerous errors live deeper — a route targeting an upstream that was never declared, a TLS setup where the cert and key don't cohere, a client-CA requested without client-auth. So --validate runs dry_run_build: it calls parse_settings (every guardrail from L5's protected headers through L8's TLS coherence) and then TlsArgs::build() — the one guardrail build_routes does not itself run, because building the rustls config is the moment cert/key mismatches surface.

// main.rs — --validate reuses the whole startup path in a dry run
fn dry_run_build(args: &[String]) -> std::io::Result<()> {
    let s = /* parse_settings + build_routes */;
    let _ = s.tls_args.build()?;   // the one guardrail build_routes skips
    Ok(())
}
// exit 0 + "config OK", or exit 1 + "config INVALID: {e}" — nothing bound.
One path, three callers. Boot, --validate, and SIGHUP reload all run the IDENTICAL parse_settings + build_routes chain. parse_settings was extracted verbatim from main for exactly this reason. The rejected alternative — a separate lenient "reload parser" that accepts a subset — is precisely the drift trap the config-file design spent its whole budget avoiding: a validator that says OK to something boot would reject (or vice versa) is a liar. Live-verified: a route targeting an undeclared upstream fails --validate with the same message boot gives.

Graceful Shutdown

SIGTERM arrives (the orchestrator is rolling the pod). The proxy must stop accepting, let in-flight requests finish, and get out of the way — with a hard deadline so a hung client can't hold the deploy hostage. Four steps, three of which reuse machinery earlier levels already built.

  1. Signal, select!ed with accept. tokio::signal::unix::signal(SignalKind::terminate()) and interrupt() (and hangup() for reload) are registered once, outside the loop. The accept loop is a tokio::select! over listener.accept() and the three signal streams. A SIGTERM/SIGINT simply breaks the loop.
  2. Stop accepting — by dropping the listener. There is no "accepting = false" flag. Breaking the loop drops the TcpListener, which closes the socket; from that instant the kernel refuses new connections. Nothing in userspace has to police it.
  3. Drain — L8's ConnLimiter is the tracker. Level 8 built ConnLimiter to enforce --max-conns: an RAII guard that increments on accept and releases on Drop through every exit path (success, error, panic). That guard is, structurally, a live-connection counter. Shutdown polls limiter.in_flight() to zero on a 100 ms tick. No new counters, no watch channel — the security accounting IS a drain tracker.
  4. Deadline. The whole poll runs inside tokio::time::timeout(drain_timeout, ...), default 15 s (--drain-timeout SECS). On expiry, remaining tasks are cut by process exit; the count is logged first. Exit is 0 whether it drained cleanly or hit the deadline — the deploy succeeded either way, and the log says what it cost.

Keep-alive connections must not linger: the AtomicBool

Dropping the listener stops new connections, but an existing keep-alive connection would happily sit idle waiting for its next request, keeping in_flight() above zero forever. The fix is a process-wide static SHUTTING_DOWN: AtomicBool in proxy.rs, flipped by begin_shutdown(). After each exchange, serve_one checks it: during shutdown the response carries Connection: close (cached responses included), and the connection ends naturally after the in-flight request completes. The check rides the existing client_still_usable computation — it is one more reason the connection can't be reused, alongside the client asking to close or the backend closing.

Why an AtomicBool, not a tokio::sync::watch? A watch channel's whole value-add is waking subscribers when the value changes. But the readers here don't need to be woken — they check the flag at a natural point they already reach (the end of each exchange). A relaxed atomic load is a single instruction with no allocation, no task registry, no plumbing. The channel's extra capability is worthless because the readers are already polling by nature of the protocol.

Hot Reload: swap the Arc

SIGHUP arrives. Re-read the file, validate it wholesale, and atomically swap the route table — so that new requests see the new config while in-flight requests keep the one they started with, and an invalid file changes nothing at all.

The shared handle is RwLock<Arc<RouteTable>> — arc-swap without the dependency, the Rust pattern the KB promised back in Level 2. The read path is routes.read().unwrap().clone(): a refcount bump under a read lock held for nanoseconds, never across an .await (L9's rule, still compiler-enforced). The reload path builds the entire new table off to the side, then does one pointer store under the write lock.

Snapshot granularity is the exchange, not the connection

handle_client loads the current Arc at the top of each serve_one iteration. That single choice has three consequences:

  • A request mid-flight keeps the exact table it started with — a consistent snapshot until it finishes, so a reload can't tear a route match in half.
  • The next request on the same keep-alive connection sees the new config. Per-connection granularity would let one chatty client pin a retired config forever.
  • The old Arc frees itself when its last holder — the last in-flight request that snapshotted it — drops. Ownership solves the torn-read problem by construction; there is no epoch, no generation counter, no RCU library.
// proxy.rs::handle_client — one snapshot per exchange
let table: Arc<RouteTable> = match routes.read() {
    Ok(guard) => Arc::clone(&guard),   // refcount bump, lock released immediately
    Err(poisoned) => Arc::clone(&poisoned.into_inner()),
};
serve_one(&table, /* ... */).await;

Wholesale validation, then one pointer store

reload() runs config::load → parse_settings → build_routes — the full boot-time path — before it touches the write lock. Only on success does it Arc::new the table, spawn probers for it, and store the pointer:

// main.rs::reload — build everything, THEN swap
match config::load(path).and_then(|cfg| parse_settings(cfg.args)).map(|s| s.routes) {
    Ok(table) => {
        let table = Arc::new(table);
        health::spawn_probers(table.upstreams());     // new table's pools
        *routes.write().unwrap() = Arc::clone(&table); // ONE pointer store
        crate::info!("reload: config applied ...");
    }
    Err(e) => crate::error!("reload REJECTED (old config stays live): {e}"),
}

Building before locking buys two distinct correctness properties: (1) the write lock is held for the duration of a single pointer store — no reader ever waits on a parse — and (2) a broken file can't leave the table half-swapped, because the swap is atomic and only reached on total success. Live-verified: a garbage line appended to the file logged reload REJECTED and traffic continued uninterrupted on the current config; and a route swap under a concurrent 4-second request completed on the old table.

A reload can never take a working proxy down. This is the whole contract. An operator who fat-fingers the config and sends SIGHUP gets an ERROR log and a still-serving proxy, not an outage. That is only true because validation is wholesale and the swap is a single atomic store of an already-built table.

The Reload's Lifetime Problem, solved by Weak

The moment route tables stop being immortal, every long-lived reference to their contents becomes a potential leak. Two places held such references — the health probers and the admin plane — and both are fixed by the same insight: hold a Weak, not an Arc.

Probers: the Weak IS the shutdown signal

Before Level 12, spawn_probers handed each background task an Arc<Upstream>. Harmless when tables were immortal; a leak the moment they retire. Trace the chain: a prober owning a strong Arc<Upstream> keeps the Upstream alive → which keeps its connection pool alive → which keeps every idle pooled TCP connection alive → forever, long after a reload retired that upstream. The prober would keep probing servers no live route points to.

Now each task holds a Weak<Upstream> and upgrades it per tick, holding the strong ref only for that tick's work. The strong references live where they should — in the route table(s). When a reload swaps the table and the last in-flight request drops the old Arc<RouteTable>, the old upstream's refcount hits zero, and the prober's next weak.upgrade() returns None → the loop returns. Old pooled connections close with their Upstream.

// health.rs::probe_loop — upgrade per tick; a failed upgrade ends the loop
loop {
    tokio::time::sleep(cfg.interval).await;
    let Some(up) = weak.upgrade() else { return }; // the table retired -> exit
    // ... probe due servers, holding `up` only for this tick ...
}

No kill channel, no generation counter, no task registry. The upgrade must be per-tick, not once at loop start — a strong ref grabbed at start and held would be exactly the leak we're removing; it would pin the pool for the prober's whole life. The old table's probers die within one interval of the last in-flight request finishing.

admin.rs: the boot-Vec capture would pin retired pools

The admin plane's /health endpoint had captured a Vec<Arc<Upstream>> at boot. After a reload this is doubly wrong. The misreporting: /health would report the boot-time upstreams' health, ignoring everything the reload changed. The worse thing: that captured Vec is itself a set of strong refs — it would pin the boot-time pools alive forever, the exact leak the probers just escaped, defeating the whole Weak design from the other side. The fix: /health now resolves upstreams per request through the shared RwLock<Arc<RouteTable>> handle, so it always reflects the live config and holds no long-lived strong ref.

Reload Scope vs Startup-Only

Not everything can be swapped by a pointer store. Ferrum draws the reload line exactly where nginx does: you can reroute live, but you cannot re-listen.

Reloads live

Routes & upstreams

What: the routes array, the [upstreams] table, and their per-route options (cache TTL, rate limits, middleware, strip/rewrite rules).

Why it can: they are entirely contained in the RouteTable, which is exactly the thing behind the swappable Arc. Rebuilding and swapping the table applies them atomically.

Startup-only

listen, admin, TLS, limits, cache bounds, logging

What: listen, admin, TLS material, max-conns, cache byte/entry bounds, log settings.

Why it can't: they are bound to OS resources or fixed-size allocations created once at boot — not to the table.

Two concrete reasons a pointer store can't touch these: listen is a bound socket — changing it means bind()ing a new one and unbinding the old, a kernel resource dance, not a memory swap (this is the same line nginx draws for listeners). TLS material is baked into the rustls ServerConfig constructed at boot; swapping certs mid-flight would mean rebuilding the acceptor and coordinating with connections already mid-handshake. On SIGHUP, startup-only changes in the file are parsed and validated (so a typo is still caught) but not applied; a WARN names the ignored keys and the rest reloads.

The L10 cardinality seam, now real. Metrics label slots are fixed at startup. A reload-introduced upstream name — one that didn't exist at boot — records its metrics under upstream="-" until a restart. This is a direct consequence of Level 10's decision to bound label cardinality at boot. The fix (dynamic label registration) has real cost in the metrics registry, so "document it as a seam" was the right call for now. Documented, accepted, quiz fodder.

Explained, Not Built

The course asks for the explanation of two production features Ferrum deliberately does not implement. The explanation is the lesson — knowing why a thing isn't there is as valuable as building it.

Graceful restart (FD passing / SO_REUSEPORT)

A zero-refusal binary upgrade: swap the executable itself without dropping the listen queue. Two industry mechanisms: FD passing (nginx — the listening socket's file descriptor survives the exec, so the kernel's accept queue never closes across the upgrade) and SO_REUSEPORT overlap (old and new processes bind the same port simultaneously; a brief dual-serving window lets the old drain while the new accepts).

The FOR case: a plain drain-and-restart drops connections that arrive in the gap between the old process releasing the port and the new one binding it — and drops the accept queue's backlog outright. FD passing preserves both: no refused connection, ever, across a binary upgrade.

The AGAINST case: the KB itself concedes the industry answer is increasingly "let the orchestrator roll pods" — Kubernetes drains one replica while another already serves, so the zero-refusal guarantee moves up a layer. Implementing FD passing would be a second process-lifecycle protocol for a teaching proxy that already demonstrates both halves — drain (shutdown) and config swap (reload) — separately. The teaching value is in seeing those halves clearly, not in gluing them into a binary-swap dance.

Worker processes

nginx runs a master and N worker processes. A large part of why is crash containment: nginx is C, C segfaults, and one worker's death must not take the fleet down. That argument does not transfer to Ferrum. Rust's panics are per-task — a panicking request task unwinds and drops its guards (the ConnLimiter releases, connections close) without touching its neighbors. There is no memory-unsafety class of crash to contain. Pingora (Cloudflare's Rust proxy) ships single-process, multi-threaded on exactly this reasoning, and Level 9 already documented Ferrum's 8-thread work-stealing tokio runtime — the parallelism a worker pool would provide, without a second process-management layer.

File watching (inotify / kqueue auto-reload)

Also skipped. SIGHUP is the interface every process manager (systemd, supervisord, k8s lifecycle hooks) already speaks. An inotify/kqueue watcher would add a platform-specific API and debounce logic (editors write files in several syscalls; a naive watcher reloads mid-write) — all to save typing kill -HUP.

How Industry Does It

Config format, reload model, and shutdown are three of the most divergent areas across proxies. Here is where Ferrum sits — honestly, as a teaching build.

ConcernnginxApache httpdHAProxyEnvoyFerrum (ours)
Config format Bespoke block-structured DSL (server { location { } }), one parser. Bespoke directive/container DSL (<VirtualHost>), modules extend it. Bespoke section-based (frontend/backend) keyword config. YAML/JSON against a large protobuf schema; xDS for dynamic delivery. TOML subset that lowers onto the CLI — no second schema, one parser per value.
Validate nginx -t: full parse + config test. apachectl configtest. haproxy -c. --mode validate against the schema. --validate: the full boot path incl TlsArgs::build, same code as boot.
Reload model SIGHUP → master spawns new workers, old workers drain then exit. graceful restart → new gen of children, old finish current requests. SIGUSR2 / new process; classic HAProxy needed a brief connection gap (later versions reduced it). Hot restart via shared-memory + config; xDS pushes updates with no restart. SIGHUP → rebuild + validate wholesale → one Arc pointer swap, same process.
Reload granularity Per-worker: old workers keep old config until they exit. Per-child process. Per-process. Per-connection / xDS resource versioning. Per-exchange: next keep-alive request sees new config; mid-flight keeps its snapshot.
Zero-drop binary upgrade Yes — FD passing across exec. Graceful restart (same-binary); full upgrade less seamless. Yes — SO_REUSEPORT / FD handoff in modern versions. Hot restart preserves listeners. No — explained not built; the halves (drain + swap) exist separately.
Process model Master + N workers (C crash containment). Multi-process / MPM (prefork, worker, event). Multi-process (nbproc, largely superseded by threads). Single process, multi-threaded. Single process, 8-thread tokio runtime (Pingora's argument; L9).
The honest trade-off. Ferrum's per-exchange reload granularity is arguably finer than nginx's per-worker model — a nginx worker can hold old config through a long-lived connection, while Ferrum's next request always sees the swap. But Ferrum gives that up nothing free: it pays with a single-process model (no worker-crash containment, which Rust makes unnecessary) and no binary-upgrade path (which the KB argues the orchestrator now owns). The config-lowers-onto-CLI idea is genuinely distinctive and only possible because Ferrum grew a CLI grammar first; a config-first proxy like Envoy has the opposite shape. Everything here is a teaching build — nginx and Envoy have decades of edge-case hardening (config includes, per-directive contexts, xDS incremental deltas) Ferrum does not attempt.

Weak<T>A non-owning reference that must be upgrade()d to an Arc to use. A failed upgrade means the value was dropped — here, that the route table retired. Serves as the prober's shutdown signal.
Per-exchange snapshotLoading the current Arc<RouteTable> once per request (not per connection), so keep-alive connections pick up reloads on their next request.
