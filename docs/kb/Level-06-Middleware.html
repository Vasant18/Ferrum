The Middleware Pipeline
A synchronous two-phase onion — and why it is NOT the async-trait one

Level 6 stops bolting cross-cutting policy onto the forwarding loop. It introduces a Middleware trait whose two phases are both synchronous, on purpose: on_request runs forward through the chain, the body streams untouched, and on_response runs in reverse — the onion's semantics without ever owning the response body. On that spine we stack five middleware: request-id, access-log, Basic/Bearer auth, require-user authz, and a 16-shard token-bucket rate limiter.

Executive Summary

Level 6 is the level where cross-cutting policy stops tangling into the core loop and starts stacking like Lego.

Levels 1–5 grew serve_one into a long function that reads, routes, balances, retries, and rewrites. Everything in it is forwarding. But auth, rate limiting, request IDs, and access logging are policy applied around forwarding, and adding each one inline would make the loop longer and more tangled. Level 6 builds the architecture that lets those features compose: a middleware pipeline — an ordered chain of interceptors that run before the backend is touched and again as the response leaves.

The central design decision, and the reason this level exists, is that the trait is synchronous and two-phase, a deliberate deviation from the textbook async onion (async handle(req, next) -> Response). That signature needs an owned Response, and serve_one never has one — it streams the body through a 16 KB window, so a 2 GB download costs 16 KB of memory. Buffering every body to satisfy an owned-response contract would throw away Level 1's flat-memory guarantee and pre-break Level 7. So we split the onion into on_request (forward) and on_response (reverse), neither of which awaits — meaning no async fn in a trait object, no Pin<Box<dyn Future>> allocation, and no async-trait dependency.

On that spine sit five middleware in a fixed in-code order: log → request-id → ratelimit → auth → authz. Rate-limit sits before auth so a credential-guessing flood is refused by a cheap bucket check before any comparison runs. The limiter keys on the socket-observed peer IP (never X-Forwarded-For), holds state in 16 sharded std::sync::Mutex maps, and refills lazily with no timer. Auth returns 401 with a WWW-Authenticate challenge; authz returns 403 (not 401); both compare secrets in constant time. A rejected request drains its body up to 64 KB before the connection is reused or closed, because unread bytes at close() make the kernel send a TCP RST that can nuke the very rejection we wrote. Ferrum here is a teaching build — a Vec<Box<dyn Middleware>>, not Tower's static composition; a per-process counter for IDs, not UUIDs — and every gap is documented rather than hidden.

The Big Picture

The chain is one stage of the pipeline, but a stage that wraps two others: it runs on the way in and again on the way out.

Two placement facts make the whole level cohere. First, the chain runs after routing — you cannot pick a per-route chain before you know which route matched. Second, it runs before the balancer lease and connect loop — a rejected request must consume no lease, open no backend socket, and never feed the circuit breaker. Short-circuiting is the entire value: a 429 flood costs the backend fleet nothing.

Analogy — airport security lanes. On the way in you pass through stations in order: the desk that logs your name, the officer who tags your boarding pass with a tracking number, the turnstile that limits how fast people enter, the ID check, the watchlist check. If the turnstile turns you away, the stations behind it (the ID and watchlist officers) never see you at all — but the desk and the tag officer you already passed still watch you leave and note it in their log. A station that itself rejected you doesn't re-screen you on the way out. That asymmetry is exactly how on_response unwinds.

On both legs the chain wraps outside Level 5: on the request leg it runs before strip_hop_by_hop and apply_request; on the response leg on_response runs before apply_response. Two consequences, both wanted: an operator's explicit set-resp-header rule stays the final word over a middleware-injected header, and both stages remain before the framing re-declaration, so nothing a middleware does can displace Content-Length / Transfer-Encoding / Connection. Level 1's anti-smuggling guarantees are untouched.

The Synchronous Trait

One trait, two phases, both synchronous. That single fact is the design decision every other choice in this level hangs off.

A middleware is anything that implements this trait, defined in middleware/mod.rs:

pub trait Middleware: Send + Sync {
    /// Stable name for log lines and rejection attribution.
    fn name(&self) -> &'static str;

    /// Inbound half. May mutate the request head or shared context,
    /// and may short-circuit the exchange by returning Reject.
    fn on_request(&self, req: &mut RequestHead, ctx: &mut ReqCtx) -> Decision;

    /// Outbound half. Default no-op so request-only middleware stay terse.
    fn on_response(&self, _ctx: &ReqCtx, _resp: &mut ResponseHead) {}
}

pub enum Decision { Continue, Reject(Rejection) }

Three things are load-bearing here and worth naming.

Send + Sync — because the chain is shared

The trait requires Send + Sync because the assembled Chain lives inside the Arc<RouteTable> that every connection task shares. A middleware is read concurrently from many tasks and never mutated after startup, so it must be safe to share across threads. This is the same shared-immutable-state discipline the router and balancer already follow.

&self, not &mut self — a deliberate seam

Both phases take &self. The trait can't take &mut self because the chain is shared behind an Arc and read from many tasks at once. Any middleware that needs shared mutable state carries its own interior mutability — the rate limiter is the only one that does, holding an Arc<Limiter> whose buckets sit behind mutexes. The &self signature is also what lets a future async middleware (one that awaits an external OIDC endpoint, say) be added later without churning every signature in the crate.

Reject carries headers — because a bare status is not a valid response

A Rejection is not just a status code:

pub struct Rejection {
    pub status: u16,
    pub reason: &'static str,
    pub headers: Vec<(String, String)>,
    pub body: String,
}

It carries headers because for two of the three rejection statuses, the status alone is incomplete. A 401 REQUIRES a WWW-Authenticate header (RFC 9110 §11.6.1) — without it the client has no idea what challenge to answer. A 429 without a Retry-After tells the client nothing actionable. So Rejection carries the headers the status demands, and RequestId's response phase later stamps X-Request-Id onto even a rejection.

Pattern name — trait object / dynamic dispatch. A Box<dyn Middleware> is Rust's trait object: a fat pointer (data pointer + vtable pointer) that lets the chain hold a heterogeneous list of middleware and call on_request on each without knowing its concrete type at compile time. This is the level's Rust lesson: dynamic dispatch as an explicit engineering choice, chosen over static composition because a runtime-configurable Vec is exactly what a per-route chain wants.

Why NOT the Async Onion

The knowledge base's textbook middleware is async fn handle(req, next) -> Response. We deliberately did not build that. Understanding why is the point of the level.

In the textbook onion, each layer calls next to invoke the rest of the chain and gets back a Response value it can post-process before returning. It is elegant and it is what Tower does. It also has two costs this proxy refuses to pay.

Cost 1

It needs an owned Response

serve_one never has a response value. It reads the backend's response head, writes it to the client, and then streams the body through a 16 KB window (Conn::copy_body_to, backed by BUF_SIZE = 16 * 1024 in proxy.rs). A 2 GB download costs 16 KB of memory today. An owned-response contract would force us to buffer every body — throwing away Level 1's flat-memory guarantee and pre-breaking Level 7's performance work.

Cost 2

async fn in a trait object needs boxing

An async fn desugars to "return a Future". A dyn trait needs a known size, but every async fn returns a differently-sized anonymous future — so each call has to allocate a Pin<Box<dyn Future>> on the heap. That is exactly what the async-trait crate does for you, invisibly, per call. Real allocation, real dependency, and avoidable here.

The two-phase split keeps the onion's semantics without owning the body:

  1. on_request runs forward through the chain, before a backend even exists.
  2. The exchange streams, untouched, exactly as in Level 5 — the 16 KB window, no buffering.
  3. on_response runs in reverse — the onion's "way out" — mutating the response head only, never owning the body.

Because neither method awaits, there is no async fn in a trait object, no boxed future, and no async-trait dependency. The crate stays at tokio + regex. The module docs still explain why that boxing exists in Tower-shaped designs — the teaching point survives even though we don't pay its cost.

The one thing we give up. A middleware that itself awaits — an auth layer calling an external OIDC endpoint, for instance — cannot exist under this trait, because neither phase can await. That is a documented boundary of the design, not an accident. When Ferrum needs it, the &self receiver means the trait can grow an async variant without rewriting the five middleware that don't need one.

ReqCtx & the Chain

Two structs carry the whole pipeline: ReqCtx is the state that crosses middleware, and Chain is the ordered stack that runs them.

ReqCtx — what crosses the chain

ReqCtx is per-request state that middleware read and write, and that survives from the request phase into the response phase. Its existence answers a subtle problem: by the time the response comes back, the request head has been rewritten by Level 5, so a middleware that needs the original method / target / host cannot read them from the (mutated) head — it reads them from the context, captured before the rewrite.

pub struct ReqCtx {
    pub peer: SocketAddr,       // socket-observed client address
    pub started: Instant,       // stamped in new(), before the chain runs
    pub method: String,         // original, pre-rewrite
    pub target: String,         // original, pre-rewrite
    pub host: Option<String>,   // original Host (documented seam)
    pub request_id: String,     // set by RequestId, read by log
    pub identity: Option<String>,// set by Auth, read by Authz
    pub backend: Option<String>, // written by proxy.rs after the pool pick
    pub upstream: Option<String>,
    pub rejected_by: Option<&'static str>, // log attribution
    // ... plus Level 10 timing stamps (t_route, t_connect, t_first_byte),
    //     pooled, cache, waf_score — later levels write these.
}

The field that matters most is identity: it is the one piece of state that genuinely flows between middleware. Auth sets it on success; Authz reads it. Everything else is either set-and-read-by-one-layer (request_id) or written by proxy.rs for the log to consume (backend, upstream). Note that started is stamped inside ReqCtx::new, before the chain runs, so the access log's duration covers every layer including the one that stamps the log line.

Fields for later levels. ReqCtx carries timing stamps (t_route, t_connect, t_first_byte), a pooled flag, a cache outcome, and a waf_score. None of those are Level 6 features — they are documented seams that Levels 7, 10, 11, and 13 fill in. The host field is the same kind of seam: no middleware reads it yet, but it is the natural place a future host-aware layer would look, so it is part of the documented contract (marked #[allow(dead_code)] for exactly that reason).

Chain — the ordered stack

A Chain wraps Vec<Box<dyn Middleware>> plus a human-readable summary for the startup banner. It is built once per route at startup and run per request. It is not Clone — a Box<dyn Middleware> isn't — and it doesn't need to be: Route owns one and is shared through Arc<RouteTable>, never cloned. The chain exposes three run methods:

// Forward on_request. On rejection, returns the rejecting layer's INDEX
// plus the response — the index says how many layers were entered.
pub fn run_request(&self, req, ctx) -> Result<(), (usize, Rejection)>

// Reverse on_response for indices [0, up_to) — the rejection path.
pub fn run_response(&self, ctx, resp, up_to: usize)

// Reverse on_response over EVERY layer — the non-rejected path.
pub fn run_response_all(&self, ctx, resp)

The rejecting index returned by run_request is the linchpin of the reverse-unwind asymmetry, covered next.

Fixed Order & the Reverse Unwind

The chain order is fixed in code, never in config. Which middleware are enabled is config; their sequence is not.

The order is log → request-id → ratelimit → auth → authz, assembled by MiddlewareConfig::build, skipping any layer that is disabled or unconfigured. Each position is justified:

#MiddlewareDefaultRejectsWhy at this position
0logon—Outermost, so its on_response runs last and observes the final status and the full duration, every inner layer included.
1request-idon—Before anything that can log or reject, so every response — including a 401 — carries the ID.
2ratelimitoff429Before auth: throttles a credential-guessing flood without paying for a single credential check.
3authoff401Establishes ctx.identity.
4authzoff403Consumes ctx.identity, so it must follow auth.

Rate-limit before auth — the one contestable choice

Placing rate-limit outside auth is the genuinely debatable decision, and the knowledge base names the trade-off exactly: rate-limit before auth if you want to throttle password-guessing; after, if your limits are per-user. Ferrum takes the security side. The observable proof the order is real: an unauthenticated flood against a route with both auth= and rate= returns 429, not 401 — the flood is refused before a single credential comparison runs. Per-user limits would require the opposite order and a header-keyed bucket; both are documented extensions, not built here.

The ordering proof, verified end-to-end (2026-08-09). An unauthenticated flood against /admin (configured with auth=basic + rate=5/s) returned 401 401 401 401 401 429 429 429 429 429. The first five requests each hit auth and get a challenge (draining the bucket by one token each), then the sixth onward is short-circuited by rate-limit before auth runs at all. Five 401s, then 429s. That sequence is only possible if rate-limit sits outside auth.

The reverse-order asymmetry

When middleware k rejects, on_response runs for middlewares k−1 … 0 only — the layers actually entered on the way in. Middleware k produced the response, so it does not post-process its own output; layers after k never ran at all. Concretely: a 401 from Auth (#3) still gets stamped with X-Request-Id (#1) and still gets logged (#0), while Authz (#4) is never consulted.

This is why run_request returns the rejecting index: the caller in proxy.rs passes it to run_response(&ctx, &mut resp, entered), which iterates self.mws[..up_to].iter().rev() — exactly the entered layers, in reverse. The naive implementation (run on_response for every middleware unconditionally) looks identical until a middleware's on_response depends on its own on_request having run, which is why this gets a dedicated test.

The Five Middleware

Four of the five live in two files: observe.rs (request-id, access-log) and auth.rs (auth, authz). The fifth, the rate limiter, gets its own section.

observe.rs

Request ID

What it does: generates a per-request identifier, injects it as X-Request-Id on the request leg (so the backend logs the same ID we do), and echoes it onto the response in on_response so a client can quote it in a bug report.

Honor valid inbound, replace hostile. An inbound X-Request-Id is honored — that is how a trace stitches across proxy hops — but only after validation: at most 64 characters, and only alphanumerics, -, and _. It is a client-controlled string that lands in log lines, so an unvalidated value is a log-injection vector (a CR/LF in a header value forges a whole log entry). An invalid inbound value is replaced, not rejected — the request is fine, its label isn't.

Not a UUID, and honest about it. Generation is a startup-seeded AtomicU64 counter rendered as {seed:x}-{n} — the seed is the wall-clock nanos at process boot so two proxy processes don't collide in a shared log. It is explicitly not a UUID: globally-unique IDs need randomness or coordination, and a monotonic counter is honest about being per-process and costs exactly one atomic increment.

The log-injection guard is tested directly. An inbound ID of "evil\r\nSet-Cookie: x" is replaced, not echoed. Without valid_request_id, that CR/LF would let an attacker inject a forged line — or a forged header — into the log or the response.
observe.rs

Access Log

What it does: emits one line per completed request from on_response. Because log is the outermost layer (#0), its on_response runs last, so it sees the final status and the full duration including every inner layer.

The Level 6 line was a single key=value record:

id=1a2b-17 peer=127.0.0.1:54321 method=GET target=/api/users status=200 dur=3.1ms upstream=api backend=127.0.0.1:9002 user=admin

A rejection is logged the same way, with rejected_by filled in (status=429 rejected_by=ratelimit) — a refused request is as visible as a served one. proxy.rs writes upstream and backend into ctx after the pool pick, so the log needs nothing from the request head. The old per-request -> {status} println became redundant and was removed; the balancer's pick line stayed, because it fires once per attempt and carries retry attribution the access log does not.

As of now, in the live code: Level 10 later upgraded this line to one JSON object per line (with a --log-plain flag preserving the old prose form) and added json_escape so an attacker-controlled target can't forge JSON fields. That is a later level's work — Level 6 deliberately shipped the single key=value line and left structured export to Level 10.
auth.rs

Authentication — Basic & Bearer

What it does: checks the Authorization header against a per-route set of accepted credentials. Two schemes, both compared in constant time:

  • Basic — decode the base64 payload of Authorization: Basic ..., split on the first colon (so a password may contain colons), and match user:pass against the set.
  • Bearer — match the token in Authorization: Bearer .... On success ctx.identity gets the credential's configured label, not the raw token.

Hand-rolled base64. Rather than add a dependency, auth.rs ships a ~40-line base64_decode that is deliberately strict: input length must be a multiple of 4, padding (=) is legal only in the final chunk and only trailing, and any byte outside the alphabet returns None. Leniency in a decoder that guards auth is exactly how bypasses happen — "AA==AAAA" is rejected, not silently decoded.

Constant-time compare — ct_eq. A plain == on byte slices short-circuits at the first differing byte, so response timing leaks the length and the matching prefix of the secret, one byte at a time. ct_eq bails on a length mismatch (length is not secret — credentials differ in length by design) but within equal lengths ORs every byte difference together, so the running time does not depend on where the mismatch is. It is cheap to do right and embarrassing to do wrong.

The & that must not be &&. Basic auth compares user and password with ct_eq(u, user) & ct_eq(p, pass) — bitwise &, not logical &&. Logical && would short-circuit: if the username didn't match, the password comparison would be skipped, reintroducing a timing signal on the password. Both comparisons always run.

One 401 for every failure. Missing header, malformed base64, no colon in the payload, wrong scheme, unknown user, wrong password — all return the identical 401 with the identical body and a WWW-Authenticate: Basic realm="..." challenge. Distinguishing "no such user" from "wrong password" would be a username oracle. RFC 9110 requires the challenge header, which is precisely why Rejection carries headers.

auth.rs

Authorization — require-user

What it does: reads ctx.identity (set by Auth) and checks it against the route's require-user allowlist. Failure returns 403, not 401.

The 401-vs-403 distinction is the entire reason authz is a separate middleware. 401 means "I don't know who you are, try again with credentials." 403 means "I know exactly who you are, and you may not do this." Returning 401 here would prompt the client to retry credentials that were already accepted — an infinite loop by design.

A route with require-user and no auth= is rejected at startup (nothing could ever populate ctx.identity), so reaching authz with identity == None is unreachable in a valid config. The code still handles it defensively with a 403 and a comment explaining why the branch exists — refusing is safe, and a 401 would loop a client that sent no credentials.

Three statuses, one per stage, verified live. On a route with two valid creds but require-user=admin: intern authenticates but gets 403; admin gets 200; no creds gets 401. Three distinct statuses prove the three stages are genuinely independent.

Config surface — the option partition

Level 6 options extend Level 5's ;option grammar on a route spec. There is a real parsing hazard here: Level 5's RewriteRules::from_options hard-errors on any key it doesn't recognize, so Level 6 keys passed through it would fail startup. The fix is an option partition in router.rs::resolve_route: it splits the severed ;options by key into the Level 5 set (rewrite::L5_KEYS) and the Level 6 set (middleware::L6_KEYS), hands each half to its own parser, and is itself the single arbiter of "unknown option". Neither sub-parser has to know the other's keys, and a typo still fails startup with exactly one clear message.

OptionMeaning
auth=basic:USER:PASSAccept this Basic credential. Splits on the first two colons only, so the password may contain : (but not ;). Repeatable.
auth=bearer:TOKENAccept this bearer token. Repeatable.
realm=NAMERealm in the WWW-Authenticate challenge (default ferrum).

Global flags --no-request-id and --no-access-log turn off the two default-on layers — applied even to the catch-all default routes, so the flags are never silent no-ops (the bug class --no-forwarded had to avoid in Level 5). Default posture: request-id and access-log are ON for every route; auth, authz, and rate-limit are OFF unless configured. A proxy that starts refusing traffic because you upgraded it is a bad proxy.

Startup guardrails — all exit 1 before binding

These are the Level 6 sibling of Level 5's protected-header guardrail: an incoherent config fails at boot, not at 3am.

  • require-user with no auth= — nothing could ever set ctx.identity, so the route would 403 every request forever.
  • rate=0/s — would reject everything; "unlimited" is expressed by omitting the option, so a literal 0 is almost certainly a typo.
  • burst= without rate= — a limiter with no refill drains once and rejects forever.
  • auth= with an unknown scheme, or a basic: value with no user:pass colon.

The Rate Limiter

One algorithm (token bucket), one concurrency shape (16 sharded synchronous mutexes), one refill strategy (lazy), one key (the socket IP). Each choice is deliberate.

Algorithm: token bucket

A bucket holds up to burst tokens and refills at rate tokens/second; each request spends one token or gets a 429. This allows short bursts while capping the sustained rate — unlike a fixed window, which permits 2N requests back-to-back across a window boundary (N at the end of one window, N at the start of the next). That classic fixed-window flaw is exactly what the token bucket avoids.

tokens = min(burst, tokens + elapsed_secs × rate)  // on each access, then spend 1

State: sharded, synchronous

pub struct Limiter {
    rate: f64,   // tokens per second
    burst: f64,  // bucket capacity
    shards: Vec<Mutex<HashMap<IpAddr, Bucket>>>,  // std::sync::Mutex, N = 16
}
struct Bucket { tokens: f64, last_refill: Instant }

Sharded locking (pattern name). The bucket store is split into 16 shards, chosen by hash(ip) % 16. Concurrent clients usually hash to different shards and touch different locks. A single global map would serialize every request in the proxy on one mutex — the exact bottleneck the KB warns about — for the sake of ~10 lines of savings. Sharding buys near-linear concurrency for a tiny code cost.

std::sync::Mutex, not tokio::sync::Mutex — and this is correct, not lazy. The critical section is a few floating-point operations with no .await anywhere inside it. An async mutex would buy a scheduler interaction for nothing. This is the KB's "never hold a lock across .await" rule seen from the constructive side: the reason we can use the cheap synchronous lock is that the whole check is synchronous — which is itself a consequence of the synchronous trait design. The pieces interlock.

Lazy refill — no timer, no sweeper

On access, tokens are recomputed from elapsed time: tokens = min(burst, tokens + elapsed × rate). There is no background refill task and no sweeper. A bucket nobody touches costs nothing and needs no upkeep. Critically, allow(ip, now) takes now: Instant as an explicit parameter rather than calling Instant::now() internally — which is what makes refill behavior testable by advancing a synthetic clock instead of sleeping in tests.

Bounded memory — fail open

An attacker cycling source IPs would otherwise grow the map without limit. Each shard has an entry cap (SHARD_CAP = 4096). On insert into a full shard, the limiter evicts entries that are both full (tokens >= burst) and idle past a TTL (IDLE_EVICT_SECS = 60) — a full bucket carries no rate-limiting information, so dropping it is free. If nothing is evictable, the request is allowed rather than rejected: failing open on an internal capacity limit is correct, because the alternative is that memory pressure becomes a client-visible outage.

Key: the socket IP, never X-Forwarded-For

The limiter keys on ctx.peer.ip() — the address observed on the socket — never X-Forwarded-For. This is the one identity in the request that cannot be forged: we watched it on the socket. Level 5 established the same stance for X-Real-IP (overwrite, never trust); this is that principle applied to policy.

The two-part exploit if you keyed on XFF. (1) An attacker sends a random X-Forwarded-For per request, so every request lands in a fresh bucket — unlimited throughput, the limiter defeated entirely. (2) An attacker sends a chosen victim's IP in X-Forwarded-For, exhausting that IP's bucket — poisoning a real client into being rate-limited. Keying on the unforgeable socket IP kills both.
Documented limitation. When Ferrum runs behind another proxy, every request arrives from that proxy's IP, so all clients share one bucket. The fix is a trusted-proxy allowlist that derives the client from XFF only when the peer is trusted — deferred to Level 13 by the Level 5 spec.

Retry-After. A 429 carries Retry-After computed from the token deficit: ceil((1 - tokens) / rate) seconds, minimum 1 (so a client never gets Retry-After: 0).

The Rejection Drain

Short-circuiting a request is not just "write a response" — there is a real connection-safety trap, and closing it is the subtle half of the level.

Consider a 429 on a POST carrying a 10 MB body. We reject before reading that body. If we then write the 429 and keep the connection alive, those 10 MB are still queued in the socket, and the next read_head() parses request-body bytes as a request line. That is connection desync — the same class of bug Level 1 spent two commits closing.

So on the rejection path, serve_one calls client.drain_body(req_framing, REJECT_DRAIN_CAP) with REJECT_DRAIN_CAP = 64 * 1024. The framing cases are decidable up front, which keeps the drain simple — a request can only use None, Length(n), or Chunked framing (never until-close; http.rs enforces this):

FramingDrain behaviorKeep-alive?
NoneNothing to drain.Always keep alive.
Length(n), n ≤ 64 KBRead and discard exactly n bytes into a sink.Keep alive — decision known before reading a byte.
Length(n), n > 64 KBLeave unread; don't read megabytes we'll discard.Close (Connection: close).
ChunkedDrain up to the cap; length unknown up front.Keep alive if under cap, else close.

Why keep-alive matters — the 401 case

Keep-alive within the cap matters specifically for 401: that status is a challenge, and the client is expected to immediately retry with credentials on the same connection. Closing on every 401 would force a fresh TCP handshake for every authenticated request.

Why close still needs a drain — the TCP RST

The drain is not only about keep-alive. Even on the close path, unread bytes sitting in the receive buffer when we close() cause the kernel to send a TCP RST rather than a clean FIN — and an RST can discard data already in flight, including the 429/401 we just wrote. The client then sees a connection reset instead of the status explaining why it was refused. That is the real reason nginx drains before closing (it calls this lingering close), and it is why the drain runs in both branches: bounded drain, then either keep-alive or a deliberate close.

The distinction the quiz asks for. Keep-alive needs the drain so the next request parses correctly (avoiding desync). The close path needs the drain because of the TCP RST — a close with unread bytes in the receive buffer triggers a reset that can destroy the response already in flight. Two different mechanisms, both requiring the same drain.

To carry the extra headers a rejection needs (WWW-Authenticate, Retry-After, X-Request-Id), the response is built from the Rejection's status/reason/headers, run through the reverse unwind (run_response(&ctx, &mut resp, entered)), and sent via send_rejection with a reusable flag that is reusable && client_keep_alive.

How the Giants Do It

Every production proxy has a middleware/filter model. The interesting differences are in where policy runs, whether the pipeline is async, and how it is composed.

nginx

Phased request processing

nginx runs each request through fixed phases (post-read, rewrite, access, content, log) with modules registering handlers per phase. Auth and rate-limiting (limit_req) live in the access phase, which runs per-location — the same per-route placement Ferrum's chain uses. limit_req is a leaky-bucket variant with a configurable burst; its zones are shared memory keyed by a variable you choose (typically $binary_remote_addr). Event-loop, C, no per-request heap onion.

Apache httpd

Hooks & the module chain

httpd exposes an ordered set of hooks (post_read_request, translate_name, check_access, check_authn, check_authz, log_transaction) that modules attach to — mod_auth_basic, mod_authz_*, mod_ratelimit. The authn/authz split mirrors Ferrum's Auth-vs-Authz 401/403 distinction exactly, because httpd formalized it first. Classically process/thread-per-request (prefork/worker MPMs), so its "middleware" is synchronous C callbacks, not an async onion.

HAProxy

Rules engine, not a code pipeline

HAProxy's "middleware" is its config-driven rules: http-request / http-response directives with ACLs, plus stick-tables for rate-limiting (track a key like src, test a rate against a threshold, deny with a status). It is a highly-tuned C event loop; policy is expressed declaratively rather than as pluggable code objects. Its stick-table rate-limiting is the closest industrial analogue to our token bucket, and it too defaults to keying on the source connection IP.

Envoy

The HTTP filter chain

Envoy is the one that is the async onion at scale: an ordered chain of HTTP filters (each with decode/encode headers+data+trailers callbacks) that map almost one-to-one onto Ferrum's two-phase on_request/on_response — decode is the forward pass, encode the reverse. Envoy's filters can pause and resume asynchronously (the thing our sync trait gives up), and its rate-limiting can call an external gRPC service. Filters are configured via xDS; ext_authz is a dedicated authz filter.

Honest positioning. Ferrum's chain is a teaching build. It is a runtime Vec of trait objects, not Tower's zero-cost static composition; it has five middleware, not a plugin ecosystem; the limiter is a single token bucket keyed on one identity, where HAProxy stick-tables and Envoy descriptors offer multi-dimensional keys and distributed limits. What it gets right — and shares with the giants — is the per-route placement, the authn/authz status split, the source-IP rate-limit key, and the drain-before-close discipline. As of the current codebase these comparisons reflect the well-known architectures of each proxy; specific defaults may drift across versions.
