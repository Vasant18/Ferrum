One circuit breaker per server, fed from two directions

Executive Summary

Level 3 left a deliberate seam: Server::available() was hardcoded true but already consulted by every selection branch. Level 4 fills that seam with a real circuit breaker — and ejection "just worked" with zero changes to the select logic.

The insight that shapes the whole level: active checks, passive checks, failure detection, recovery, circuit breaking, and backoff are not seven independent features. They are facets of one circuit breaker per server. Failure detection and recovery are its transitions; the breaker is the circuit breaker; backoff paces its recovery attempts; and active/passive checks are just two feeders of the same success/failure signal. Only retry is genuinely separate — it acts on the breaker's verdict.

The Breaker (in balancer.rs) is a three-state machine: Closed (serving), Open (tripped, cooling down), HalfOpen (exactly one recovery trial outstanding). It is pure sync — all Relaxed atomics, every method takes an injected now: Instant — so it unit-tests without sockets or sleeping, the same discipline that kept Level 3's algorithms testable.

Two feeds pour into the same breaker counters via Server::record_success / record_failure. Passive: real client exchanges, scored on Lease drop. Active: a background prober in health.rs, one task per upstream, issuing GET /health. Neither feed knows the other exists, so a trafficked server trips from client failures without waiting for a probe, and an idle server still recovers via probes — each feed covers the other's blind spot.

The retry loop in proxy.rs makes a dead backend invisible to clients. It re-picks on connect failure, but only when three gates all hold: attempts remain (cap MAX_RETRIES = 2), the method is idempotent, and no request-body bytes have been forwarded yet. Exponential backoff starts at 1s, doubles on each failed HalfOpen trial, caps at 30s, and resets to base on recovery.

Building this surfaced a real bug: with the default success_threshold = 2, active-only recovery deadlocked. probe_due returned None for HalfOpen after the single admitted trial, so consec_success froze at 1 — and because clients are blocked in HalfOpen too, no passive success could finish the job. The fix and its regression test are covered in full below. 72 unit tests pass; ejection, recovery, retry, and the cap were all live-verified against Python backends with default config.

This is a teaching build. The breaker is strictly per-server and threshold-based — no outlier detection across the pool, no configurable per-request retry budgets, no hedged requests. Those honest limits are part of the lesson.

The Big Picture

Level 4 does not add a new stage to the request path so much as make an existing one honest: the pick() step now genuinely excludes dead servers, and a new retry loop wraps the connect step.

In Level 3, upstream.pick() returned a Lease and the proxy connected to lease.addr() exactly once; a connect failure meant a 502. Level 4 keeps that shape but adds two things around it: pick()'s selection now skips any server whose breaker is not Closed, and a retry loop re-picks on connect failure. Off to the side, a background prober task feeds each server's breaker independently of any client request.

Analogy: think of each backend as a circuit in your house. Under a fault, the breaker trips (Open) — not because someone flipped it, but because too much current flowed. You don't immediately shove it back on; you wait, then flip it halfway and watch (HalfOpen). If the light stays on for a beat, you commit it fully (Closed). If it sparks again, back off — and wait longer this time. The prober is the person testing the switch; the client traffic is the current the breaker was protecting.

The Circuit Breaker

One Breaker per Server. Three states, one source of truth. It is pure sync — no sockets, no async, no sleeping — so every transition is a unit test.

What it is

A circuit breaker is a small state machine that sits in front of a resource and decides, cheaply, whether to let a request through. Closed means "healthy, serve traffic." Too many consecutive failures trip it to Open ("stop — give it a rest"). After a cooldown, it moves to HalfOpen and lets exactly one trial through; if the trial (and enough after it) succeeds, it closes again; if the trial fails, it re-opens and waits longer.

In our code the states are a plain enum backed by an AtomicU8 (Closed=0, Open=1, HalfOpen=2) in balancer.rs. The name "Closed = healthy" trips people up — it is the electrical-circuit convention: a closed circuit conducts, an open one is broken.

State representation — interior mutability, &self throughout

Every field is an interior-mutable atomic, so all methods take &self (the breaker is shared behind an Arc<Upstream> and mutated concurrently by many request tasks plus the prober). From balancer.rs:

  • state: AtomicU8 — the current state.
  • open_until_nanos: AtomicU64 — when the Open cooldown ends, as nanoseconds since a process-start Instant baseline (the same baseline trick Level 3 used for its PRNG seed). The prober reads this to answer "is this server due?"
  • backoff_nanos: AtomicU64 — the current cooldown length; doubles on each failed trial, capped at backoff_max, reset to backoff_base on recovery.
  • consec_fail: AtomicUsize, consec_success: AtomicUsize — consecutive counters, each zeroed by the opposite outcome.
Why an injected clock? Every transition method takes now: Instant rather than calling Instant::now() internally. That is what lets the eight breaker unit tests assert backoff-doubling and cooldown expiry without sleeping — they just hand the machine a fabricated future Instant. This is the type-of-thing that makes a state machine tractable to test: no wall-clock, no flakiness.

The transitions (the meat)

record_failure(now):

  • Closed: consec_fail += 1; when it reaches fail_threshold (default 3) → Open, arm open_until = now + backoff, zero both counters. This is a fresh trip: it keeps the existing backoff (base), it does not double.
  • HalfOpen: immediately → Open, backoff = min(backoff*2, max). A recovery probe just failed, so wait longer.
  • Open: no-op (already open; the cooldown governs the next attempt).

record_success(now):

  • HalfOpen: consec_success += 1; when it reaches success_threshold (default 2) → Closed, reset backoff to base, zero both counters.
  • Closed: consec_fail = 0 — a good result clears a partial failure run, so failures must be consecutive to trip.
  • Open: no-op — shouldn't happen (traffic is blocked in Open), and we ignore it rather than let a stray success silently un-trip the breaker.

allows_traffic() -> bool is simply state == Closed. Because Server::available() now calls it, every Level 3 selection algorithm already respects it — no selection-logic changes were needed.

Watch out: both transition methods return Option<(BreakerState, BreakerState)> — Some((from, to)) only when a transition actually happened. That is what the caller logs as a one-line state-change message; a no-op returns None and logs nothing.

Design decisions & alternatives rejected

Chosen

Per-server, threshold-based

Each server owns its breaker; N consecutive failures trip it. Simple, local, predictable.

Rejected

Outlier detection across the pool

Ejecting the statistical outlier (like Envoy) needs cross-server aggregation. Out of scope — the breaker is strictly per-server.

Chosen

Relaxed atomics, no lock

The counters guide a heuristic, not protect data. Two racing record_failure calls may lose an increment — acceptable: it merely delays a trip by one request.

Rejected

A mutex around the breaker

Correctness never depends on the exact count, so a lock would buy nothing but contention on the hot path.

Passive & Active Feeds

Two independent sources of truth funnel into one set of breaker counters through Server::record_success / record_failure. Neither feed knows the other exists.

Passive feed — real client traffic on Lease drop

Level 3's RAII Lease already wraps every request and fires on Drop. Level 4 extends it with an explicit outcome: an Option<bool> the proxy sets before the lease drops.

  • Lease::mark_success() / mark_failure() set the outcome field.
  • On Drop: release inflight (unchanged, unconditional), record the EWMA if served (unchanged), and if the outcome is set, call the matching breaker method. If the outcome is None (task cancelled mid-flight, or we never got far enough to judge), the breaker is left untouched — we never guess an outcome.

Outcome mapping at the call site (in proxy.rs): connect failure / connect timeout / response-read error / backend status >= 500 → mark_failure(). Response head parsed with status < 500 → mark_success().

Why Option<bool> and not just bool? "No opinion" (None) is a distinct case from "success." If a task is cancelled before we ever hear from the backend, scoring that as a success would keep a dead server Closed on phantom evidence; scoring it as failure would punish a server that never got a fair request. The honest answer is to say nothing.

Why 5xx is a failure but 4xx is a success

A 4xx is the client's fault — bad request, not found, unauthorized — and the backend is perfectly healthy: it parsed the request and answered correctly. A 5xx is the backend failing. Scoring health on 5xx-but-not-4xx mirrors how real proxies grade passive health; counting 404s as failures would trip a breaker every time a client mistyped a URL.

Active feed — the background prober

The prober lives in health.rs (covered in depth in The Active Prober). It issues GET <health_path> to each due server; 2xx → record_success, everything else (refused / timeout / malformed / non-2xx) → record_failure. The mapping lives in apply_probe_result.

The payoff of sharing one breaker: a server under live traffic trips Open from passive failures without waiting for a probe interval, and a server with no client traffic still recovers via active probes. The two feeds cover each other's blind spots — the whole reason they write to the same counters.

Exponential Backoff

A tripped breaker should not be hammered the instant its cooldown ends if it is still sick. Backoff makes each successive probe wait longer — but forgives instantly once the server is healthy again.

Double, cap, reset

The cooldown length lives in backoff_nanos. Its lifecycle:

  • Start: backoff_base (default 1s). The first trip uses this as-is.
  • Double: on each failed HalfOpen trial, backoff = min(backoff * 2, backoff_max). So the Open cooldown grows 1s → 2s → 4s → 8s …
  • Cap: at backoff_max (default 30s) — a saturating multiply, so it never overflows or grows unbounded.
  • Reset: to backoff_base the moment the breaker returns to Closed.

All of this lives in the Open transitions (trip / record_failure) and the recovery arm of record_success. Note the base defaults to 1s independent of --hc-interval (default 2s), so tuning probe frequency doesn't accidentally change recovery pacing.

Why reset matters — the flapping backend

Consider a backend that flaps: healthy for a while, then a burst of failures, then healthy again, repeatedly. With reset, each healthy stretch brings the backoff back to 1s, so recovery is fast when the server is genuinely up. Without reset, the backoff would ratchet upward forever — after a few flap cycles a server that is currently perfectly healthy would still be stuck behind a 30s cooldown, punished for its past. Reset says "the past is settled; judge you on now."

The tension: doubling protects a genuinely dead server from being probed every tick; resetting protects a recovered server from being penalized. Both are needed — that is exactly quiz question 7.

The Active Prober

One tokio task per upstream, in health.rs. It ticks on a timer, asks each server's breaker "are you due?", and probes the due ones concurrently.

One task per upstream

spawn_probers launches one probe_loop task per Upstream at startup. The loop:

  1. Sleep hc_interval (default 2s).
  2. Snapshot the due set before awaiting: iterate the pool, keep servers where breaker.probe_due(now) is Some. Deciding first means the breaker reads are a consistent snapshot of this tick.
  3. Probe concurrently — spawn each probe and join, so one slow server cannot delay the others within a tick.
  4. Map the result via apply_probe_result: 2xx → record_success, else record_failure; log any transition.

Each probe (probe_once) opens a TCP connection under hc_timeout (default 1s), sends a minimal GET <path> HTTP/1.1 with Host and Connection: close, and reads the response head with the existing Level 1 helpers. The prober reuses the connect+write+read-head code rather than re-implementing HTTP; the only new concern is issuing a fixed GET and checking the status class.

The lifecycle detail: Arc at L4, Weak after L12

As designed at Level 4, each prober task held an Arc<Upstream> — harmless while route tables were immortal. Level 12 (hot reload) later changed each task to hold a Weak<Upstream> and re-upgrade per tick: the strong refs live in the route table(s), so when a reload swaps the table and the last request drops the old Arc<RouteTable>, the old pool's prober finds its upgrade failing and exits within one interval. The Weak is the shutdown signal — no kill channel, no registry.

Honesty note: the current health.rs already carries the L12 Weak form. At Level 4 the task simply owned the Arc; the Weak refinement is a later level's fix for a leak that only mattered once tables became mutable.

Non-goals on the probe path

The prober deliberately does not rewrite headers (XFF etc. — that is Level 5; probes send a bare GET), does not reuse connections (Level 7; each probe opens and closes one TCP connection), and emits no metrics (Level 10; observability here is the per-request log line plus a one-line state-transition log). Keeping the prober minimal keeps the breaker the star.

The Retry Loop

The retry loop in proxy.rs is the one genuinely separate piece — it acts on the breaker's verdict. It is what makes a dead backend invisible to a client: re-pick, reconnect, succeed, all before the client sees anything.

Three gates, all required, every time

A connect failure triggers a retry only when all three hold:

Gate 1

Attempts remain

Global cap MAX_RETRIES = 2 (3 tries total). Each retry calls pick() fresh; the just-failed server's mark_failure() already ran, and the algorithm's cursor advanced, so the retry lands elsewhere.

Gate 2

Idempotent method

GET / HEAD / PUT / DELETE / OPTIONS / TRACE retry (is_idempotent). POST / PATCH / unknown do not — replay could cause a second side effect.

Gate 3

Pre-body

Retry only while still at the connect stage, before any request-body bytes have been forwarded to any backend. Once body streaming starts, the request is committed to that backend.

Only a failed connect retries

A failure after the request head was sent — backend 5xx, mid-response I/O error — is not safely replayable: part of a possibly non-idempotent request already reached a backend. Such a failure still records into the breaker (via mark_failure), but the error/response is returned to the client. 502 Bad Gateway surfaces only when attempts are exhausted or no healthy server remains.

Concrete pre-body danger (quiz Q4): imagine a PUT /account/balance that streams a large body. If we dropped the pre-body gate and the connection to backend A failed after half the body streamed, retrying onto backend B would send the whole body again — but A may already have applied the partial write. Even an idempotent method is only idempotent if the whole request is replayed exactly once; a partial-then-full double-send corrupts data. The pre-body gate is what makes "idempotent" actually safe.

The retry log marker

When a retry happens, the per-request log line carries a marker so you can watch it: [retry 1/2] after the first re-pick, [retry 2/2] after the second. Under live verification, a GET at a dead-then-healthy pool showed [retry 1/2] and returned 200; a POST loop returned alternating 502 200 (proving non-idempotent requests are not replayed); and the highest marker ever observed was [retry 2/2], never 3/….

The HalfOpen Recovery-Deadlock Bug

Building Level 4 surfaced a real bug that the direct-call unit tests missed and only live verification (and a prober-shaped test) caught. It is the most instructive part of the level.

The symptom

With the default success_threshold = 2, a server recovering via active probes only (no client traffic) wedged permanently in HalfOpen. The log showed Open->HalfOpen and then … nothing. The backend was up, answering probes, but never rejoined rotation.

The root cause

The original probe_due admitted one HalfOpenTrial per cooldown and then returned None for any subsequent tick while HalfOpen. So the sequence was:

  1. Cooldown elapses → probe_due flips Open→HalfOpen, admits one trial.
  2. The trial succeeds → consec_success = 1. But the threshold is 2.
  3. Next tick: probe_due sees HalfOpen → returns None. No probe fires.
  4. consec_success is frozen at 1 forever. And because allows_traffic() is false in HalfOpen, no passive success can supply the second one either — clients are blocked. Deadlock.
Why the unit test missed it: the original test drove recovery with direct back-to-back record_success calls, which reach the threshold trivially. Real recovery is driven by the prober, one success per tick, gated by probe_due — and probe_due was the broken part. The test exercised the machine in a way the real caller never would.

The fix

probe_due now keeps admitting a HalfOpenTrial while HalfOpen (not just on the first tick), so the prober can accumulate the successes it needs. The anti-hammering ceiling still holds because a failed trial trips straight back to Open with a doubled backoff — so a genuinely dead backend is still probed at most once per (growing) cooldown, never once per tick. The verbatim comment from balancer.rs explains the trade-off:

// Keep probing while HalfOpen so consecutive successes can reach
// `success_threshold`. If we returned `None` here, a recovery that
// needs more than one success would wedge forever ...
// A trial that *fails* still trips us straight back to `Open`
// (doubled backoff), preserving the one-probe-per-cooldown ceiling
// for a server that isn't recovering.

A prober-loop-shaped regression test now guards it: it drives recovery the way the prober does (alternating probe_due / record_success per tick) and asserts the breaker reaches Closed with the default threshold — the exact case the old direct-call test missed. Re-verified live: HalfOpen->Closed, backoff reset to 1s, and the recovered backend split traffic 3/3/3.

The lesson (quiz Q6): "exactly one trial per cooldown" and "keep probing while HalfOpen" sound contradictory but aren't. The ceiling that matters is "at most one probe per cooldown for a server that keeps failing" — and that is enforced by a failed trial re-opening with a bigger backoff, not by refusing to re-probe. A server that is answering should be probed until it clears the bar. Conflating those two invariants is what caused the deadlock.

The honest trade-off: our unifying idea — one breaker fed by both active and passive signals, with rise/fall-style thresholds — is close in spirit to HAProxy's observe + checks. What we deliberately skip is Envoy's league: cross-pool outlier detection, retry budgets, per-try timeouts, and hedged requests. Those are aggregate / statistical machinery; the lesson at this level is the mechanism of one breaker, so we keep it strictly per-server and threshold-based. As of 2026, nginx active checks remain a commercial (Plus) feature; the OSS build is passive-only.

  1. allows_traffic() is true only in Closed, not in HalfOpen. Why must client traffic stay blocked while a recovery probe is outstanding?
  2. Active and passive checks share one set of counters. Give one failure scenario that only the passive feed catches, and one that only the active feed catches.
  3. Lease's outcome is Option<bool>, and None reports nothing. Why is "no opinion" a distinct case from "success"?
  4. Retry requires idempotent + pre-body + attempts-remaining. Construct a concrete request where dropping the pre-body gate would corrupt data.
  5. Why does a 4xx response count as a health success?
  6. probe_due admits exactly one HalfOpenTrial per cooldown. What goes wrong if it admitted one per tick instead?
  7. Backoff doubles on a failed trial but resets on recovery. What would a backoff that never reset do to a backend that flaps?
  8. The breaker uses Relaxed atomics, so two concurrent record_failure calls can lose an increment. Why is that acceptable here?
Note on Q6: read it against The HalfOpen Deadlock Bug — the subtlety is that "one trial per cooldown" is the ceiling for a failing server, while a recovering one must keep being probed. Getting that distinction wrong is precisely what deadlocked recovery.
