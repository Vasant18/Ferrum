Load Balancing
One route, many servers, seven ways to choose

Level 3 turns each route's single backend address into a pool of servers and chooses one per request. Seven algorithms — round-robin, weighted-RR, random, least-connections, least-response-time, IP hash, consistent hash — sit behind one Upstream::pick() call, all grounded in balancer.rs. The linchpin is the RAII Lease: it makes the load-aware counters honest by releasing on every exit path, and gates response-time learning so a failed connect can't teach the proxy to prefer dead servers.

Executive Summary

Level 2 answered "which pool?"; Level 3 answers "which server in that pool?" — and does it seven different ways behind a single Upstream::pick() call, with zero new dependencies.

The core reshape is small but load-bearing: Route.backend: String becomes Route.upstream: Arc<Upstream>. A single bare host:port is no longer special — it is just a degenerate 1-member round-robin pool (Upstream::single), so the rest of the code has exactly one path. Every existing route, and all 36 pre-Level-3 tests, keep working unchanged because a host:port route target auto-wraps into a pool (the second of three resolution rules).

The seven algorithms fall into three teaching groups. Stateless (round-robin, weighted-RR, random) need no shared per-server state — an atomic counter or nothing at all. Load-aware (least-connections, least-response-time) read live per-server atomics and are the reason the Lease exists. Hash-based (IP hash, consistent hash) give client affinity: the same client keeps landing on the same server, cheaply by arithmetic (IP hash) or robustly through a virtual-node ring (consistent hash).

The RAII Lease is the design's keystone. Selecting a server hands back a Lease that counts as one in-flight request; releasing that count lives in Drop, not an explicit release() call, so it fires on every exit path — normal finish, a ? bailing out mid-body, task cancellation, panic. A single leaked in-flight count would permanently bias least-connections against a perfectly healthy server. The lease also folds the observed round-trip time into an EWMA, but only after mark_served() — so a failed (instantly-refused) connect never records a tiny RTT that would trick least-response-time into preferring dead backends.

Every Upstream is built once at startup and shared read-only behind an Arc; the only mutation is through interior-mutable atomics, so pick() takes &self and needs no lock — the same lock-free-shared-config pattern the router used. And Level 3 deliberately left a seam: Server::available() was hardcoded true but already consulted by every selection branch, so Level 4's circuit breaker could snap in with no changes to the select logic.

This is a teaching build, and its limits are the lesson. It uses a single sorted hash ring (Ketama-style, 160 vnodes/server), not Maglev; least-connections tolerates a documented one-request race rather than taking a lock; and a dead server is still picked and still yields 502 — liveness is Level 4's job. 52 unit tests pass; distributions were live-verified against Python backends.

The Big Picture

Level 3 inserts exactly one step into the request path: between "route matched" and "connect to backend", the proxy now calls upstream.pick(client_ip) to choose a specific server.

The router still does match logic only — it answers "which pool?" and returns an Arc<Upstream>. The balancer answers "which server in it?". That clean split is why router.rs barely changed: its find() just returns Option<&Arc<Upstream>> instead of a backend string. The pick produces a Lease, the proxy connects to lease.addr(), forwards, and when the lease drops the per-server counters settle up.

Analogy: a route is like a phone number for a whole department; Level 2 dials the department. Level 3 is the receptionist who decides which desk in that department picks up — round-robin (next desk in line), least-connections (whoever's least busy), or IP hash (always the same desk for the same caller, so they don't have to re-explain themselves). The Lease is the sticky note on the desk saying "one call in progress here" — and it comes off the moment the call ends, no matter how the call ends.

Upstream Pools & Resolution

An Upstream is a named group of Servers plus one Algorithm. The CLI declares pools with --upstream NAME=SPEC; routes then bind to a pool by name, or auto-wrap a bare address.

What a pool is

In balancer.rs, Upstream holds a name, an algorithm, a Vec<Server>, and a few precomputed helpers: a cursor: AtomicUsize for round-robin, a wrr_index (the weight-expanded index list, empty unless weighted), and a ring: Vec<(u64, usize)> (the consistent-hash ring, empty unless chash). Each Server owns its addr plus the two live atomics the load-aware algorithms read: inflight: AtomicUsize and ewma_us: AtomicU64.

The spec grammar is SPEC = algo:server[*weight][,server...]. The algorithm tag is optional and defaults to round-robin. Telling a tag apart from a hostname is the one subtlety: a leading token is treated as an algorithm keyword only when it is all ASCII letters and the remainder still contains a : (so it really looks like tag:host:port). Thus lc:127.0.0.1:9001 parses as tag lc, but localhost:9001 has no tag (its remainder 9001 has no colon) and defaults to round-robin.

--upstream api=lc:127.0.0.1:9001,127.0.0.1:9002,127.0.0.1:9003
--upstream web=wrr:10.0.0.1:80*5,10.0.0.2:80*1
--upstream cache=chash:node1:6379,node2:6379,node3:6379

The three-rule route resolution

A route's target resolves in a strict order (in main.rs / route wiring), which is what preserves backward compatibility:

  1. Declared name: the target matches a --upstream name → bind to that pool.
  2. Auto-wrap: otherwise it parses as host:port → wrap it as a single-server rr pool via Upstream::single. This is what lets every pre-Level-3 invocation and all 36 old tests keep working unchanged — a lone backend is genuinely just a 1-member pool.
  3. Error: otherwise → startup error unknown upstream "x" and exit 1.

The shape check is_host_port splits the port off from the right, so IPv6 hosts survive ([::1]:8080 → host [::1], port 8080). It validates shape only; DNS resolution happens at connect time.

Startup validation — fail loud, fail early

Misconfigurations are rejected at startup with exit 1 rather than surfacing as confusing runtime behavior. From the spec parser:

  • Empty pool (no servers) → error.
  • Unparseable address (not host:port, or port 0) → error.
  • Unknown algorithm (bogus:127.0.0.1:9001 looks like a tag, isn't known) → error.
  • Zero weight (*0) → error: a zero-weight server can never be picked, so it is certainly a typo.
  • Duplicate upstream name → error.
Accept-but-warn, one exception: a *weight suffix on a non-weighted algorithm (e.g. rr:...*5) is not an error — it warns on stderr and ignores the weight. Rationale: a harmless no-op misconfiguration should not stop the proxy from starting. Only wrr consumes the weight; everywhere else it is dead text.

The RAII Lease

This is the level's keystone. A Lease is an RAII handle to a picked server: holding it counts as one in-flight request, and releasing that count lives in Drop — never an explicit call. That single design choice is the whole reason the type exists.

Why release must live in Drop

Two algorithms are load-aware: least-connections reads a per-server inflight count, least-response-time reads a per-server EWMA. Those counters only stay honest if every increment is paired with exactly one decrement — including on the error paths. An explicit release() call is always one early return, one ?-propagation, or one task cancellation away from being skipped. So Lease::new does inflight.fetch_add(1, Relaxed) and impl Drop for Lease does inflight.fetch_sub(1, Relaxed), which the Rust compiler runs on every exit path.

The leak this prevents (quiz Q1): suppose release were an explicit call at the end of serve_one, and the request bails out mid-body via ? after a read error. The fetch_sub never runs, so that server's inflight is now permanently one too high. Under least-connections, the scan sees a phantom in-flight request forever and steers traffic away from that server — a perfectly healthy server, penalized by a counter that never came back down. Every leaked request makes it worse. This is precisely the bug the RAII design exists to make impossible, and test #6 (lease_releases_on_every_path) asserts the counter returns to 0 after an early return.

The served gate: don't let dead servers look fast

The lease also records round-trip time into the server's EWMA on drop — but only after mark_served() has been called (which proxy.rs does after a successful connect + forward). The gate is a plain served: bool field, checked in Drop before record_rtt(started.elapsed()) fires.

Why gate it? Because the fastest possible way to "respond" is to refuse the connection instantly. If a failed, instantly-refused connect recorded its tiny RTT into the EWMA, least-response-time would learn to prefer the dead server — it appears to have the lowest response time in the pool. The served gate ensures only a real, completed exchange teaches the EWMA anything. (Samples are also floored at 1µs so a genuinely fast reply can never masquerade as the 0 = "untried" sentinel.)

This is quiz Q2. The in-flight decrement is unconditional (it must fall no matter what), but the RTT record is conditional on served. Two different rules for two different fields, both enforced in the same Drop body.

Borrowing, not owning

Lease<'a> holds server: &'a Server — it borrows the chosen server rather than copying anything out. The backend address is read via lease.addr() straight from the Server, keeping a single source of truth. The borrow works cleanly because serve_one holds the Arc<Upstream> for the whole exchange, so no 'static bound and no owned-index workaround is needed. pick() returns Option<Lease<'_>>; None only when the pool has no available server — a case startup validation already forbids, so the call site treats it as a defensive 502.

Stateless Algorithms

Round-robin, weighted round-robin, and random need no live per-server state — just an atomic counter, a pre-expanded list, or nothing at all. All three are O(1) per pick.

Round Robin — the atomic counter

The sensible default. One shared cursor: AtomicUsize; each pick does cursor.fetch_add(1, Relaxed) % n and cycles through servers in order. Over four picks of a 3-server pool the sequence is 0,1,2,0 (test #1). Complexity: O(1), one atomic.

Why Relaxed (quiz Q3)? We want a distinct-ish index, not a synchronization edge. Round-robin has no data that a later thread must observe in a particular order — the counter is the whole state, and fetch_add is atomic regardless of ordering. SeqCst would impose a global total order across all atomics in the program and cost a memory fence, buying nothing here: two racing picks might still land on the same index under either ordering, and that's fine. Relaxed is the honest expression of "I need atomicity, not ordering."

Weighted Round Robin — pre-expanded index vector

Weights are expanded once at startup into an index vector: weights 5:1 become [0,0,0,0,0,1]. A pick is then plain round-robin over that vector (cursor.fetch_add(1) % wrr_index.len(), then index into it). Complexity: O(1) pick, O(sum of weights) memory. Test #2 confirms the 5:1 ratio holds over 100 picks.

Bursty vs. smooth (quiz Q4): the simple expansion produces a bursty run — AAAAAB for 5:1, i.e. five consecutive hits on A, then one on B. Nginx uses smooth weighted round-robin, which interleaves (roughly AABAAB) so the heavy server isn't hammered in a contiguous streak. When does the difference matter? Under high concurrency with slow requests, a bursty run can transiently pile several simultaneous requests onto A before B gets any — a momentary imbalance smooth WRR avoids. We keep the simple expansion because the burst is harmless for a teaching proxy and the array makes the weighting visually obvious.

Random — no shared state at all

A uniform random choice: next_random() % n. The teaching point is that random balancing needs no coordinated state whatsoever — and is surprisingly competitive in practice (cf. power-of-two-choices). The PRNG is a small xorshift64 living in a Cell<u64> inside a thread_local!, so each worker thread rolls its own and never contends a shared cache line. No rand crate is added.

Seeding: each thread mixes the process-start Instant's elapsed nanos with a per-thread SEED_COUNTER value (golden-ratio multiply) so two threads seeded in the same nanosecond still diverge, and a zero seed is nudged to a constant (xorshift is stuck at 0 forever if it ever reaches 0). Complexity: O(1), no state shared across threads. Test #3 confirms every server gets picked over 300 rolls.

Load-Aware Algorithms

Least-connections and least-response-time read live per-server atomics that the Lease maintains. Both are an O(n) scan for the minimum. This is the group the whole RAII design serves.

Least Connections — O(n) inflight scan

Scan all servers, pick the one with the fewest in-flight requests (min_by_key(|s| s.inflight())); ties go to the lower index. The inflight count is exactly what the Lease bumps and drops. Complexity: O(n), per-server AtomicUsize. Tests #4 and #5 confirm it picks the idle server while leases are held and rebalances once they drop.

The documented race (quiz Q8): two tasks scanning at the same instant can both see the same server as least-loaded and both pick it, briefly over-loading it by one request. This is acceptable: the error is one request deep and self-corrects on the very next pick (the just-picked server's inflight is now higher). The fix — a lock around the scan-and-pick — would serialize every request through a single mutex, destroying the concurrency the whole proxy exists to provide. Living with a one-request transient beats serializing the hot path. That trade-off is the lesson.

Least Response Time — EWMA of RTT

The same O(n) scan, but keyed on an exponentially-weighted moving average of observed round-trip time, stored as AtomicU64 microseconds. The update rule, done in integer math with α = 0.2, is new = (old*4 + sample) / 5. Higher α reacts faster but is noisier; 0.2 is a calm, common choice.

Two subtleties make it fair. First, untried servers sort first: 0 is the sentinel for "no samples yet", and since 0 is the minimum, a freshly-added server gets traffic instead of being starved behind servers with (non-zero) history. Test #7 confirms both the untried-first rule and that the fastest server wins once all are tried. Second — and this is why the served gate matters — only a completed exchange folds into the EWMA, so a dead server's instant connection-refusal can never register as a blazing-fast response time.

EWMA (α = 0.2, integer):  new_us = (old_us × 4 + sample_us) / 5  |  first sample: new_us = sample_us

Hash-Based Algorithms

IP hash and consistent hash both give client affinity — the same client keeps landing on the same server. The difference is what happens when the server set changes: IP hash reshuffles almost everyone; consistent hash barely moves anyone.

The shared hasher: hand-written FNV-1a

Both algorithms hash with an explicit FNV-1a (64-bit) written out in ~6 lines, not std's DefaultHasher. Two reasons (quiz Q7): (1) FNV's arithmetic is visible and teachable — XOR the byte, multiply by the prime, repeat; and (2) DefaultHasher's output is explicitly unspecified across Rust versions, so a routine toolchain upgrade could silently remap every client to a different server, quietly breaking affinity for the whole fleet. A named, fixed algorithm keeps affinity stable forever. The client IP is hashed by its raw octets (4 for v4, 16 for v6), avoiding textual quirks like ::1 vs its expanded form mapping differently.

IP Hash — affinity by arithmetic accident

hash(client_ip) % n. The same IP hashes to the same index — as long as n never changes. Complexity: O(1), no state. Test #8 confirms stability for one IP; test #9 confirms a range of IPs spreads across all servers.

The modulo-rehash disaster (quiz Q5): when n goes from 4 to 3, the divisor in hash % n changes, so almost every client's result changes — roughly 3/4 of clients move to a different server, not just the 1/4 that lived on the removed server. Every remapped client loses its session affinity at once. For a cache pool this is a thundering herd of misses; for sticky sessions it's a mass logout. This fragility is exactly what consistent hashing was invented to fix, and test #11 asserts plain IP hash keeps < 40% of keys on their original server under a 4→3 change.

Consistent Hash — the virtual-node ring

Place VNODES_PER_SERVER = 160 virtual nodes per real server onto a u64 ring by hashing "addr#vnode_index" with the same FNV-1a. Sort the Vec<(u64, usize)> once by hash. To pick: hash the client, binary-search (partition_point) for the first ring entry with hash ≥ the client's, and walk clockwise (wrapping to 0) to the first available server. Complexity: O(log(n·v)) lookup, sorted ring of n×160 entries.

Why 160 vnodes (quiz Q6)? If each server owned just one point on the ring, two problems appear: the arcs between points would be wildly uneven (one server might own a huge span and get most traffic), and removing a server would dump its entire single arc onto exactly one neighbor. Scattering 160 vnodes per server across the ring makes each server's total ownership close to 1/n (smooth distribution), and removal orphans only the ~1/n of keys on that server's vnodes, redistributed among many neighbors rather than one. With 1 vnode per server, consistent hashing degrades toward the same imbalance and single-neighbor dumping it was meant to avoid.

The headline result: under the identical 4→3 change, consistent hashing keeps ≥ 70% of keys on their original server (theory says ~75%; the 70% bound leaves headroom for vnode imbalance), versus IP hash's < 40%. Test #11 asserts both numbers — the contrast is the lesson, and a one-sided assertion would pass even if the ring were secretly behaving like modulo.

Arc-Shared Upstreams & the L4 Seam

Every Upstream is built once at startup and shared read-only behind an Arc. And every selection routes only among available servers — a seam that was hardcoded true at Level 3 so Level 4 could fill it with zero call-site changes.

Lock-free sharing via Arc<Upstream>

A Route holds upstream: Arc<Upstream>; matching a route is an Arc clone, no lock. The pool itself is never mutated after construction — the only "mutation" is through interior-mutable atomics (cursor, per-server inflight/ewma_us). So pick() takes &self and many request tasks call it concurrently without any lock. This is the same lock-free-shared-config pattern the router uses for its route table: build immutable, share via Arc, mutate only atomics. Multiple routes can point at the same Arc<Upstream>, sharing one pool (and one set of counters) across routes for free.

The Level 4 seam: Server::available()

Every selection branch filters on Server::available(). At Level 3 it is hardcoded to return true, so nothing is filtered — a genuinely dead backend is still picked and still yields 502. The O(1) algorithms express the filter through a helper first_available_from(start): a linear probe from the chosen index, wrapping, for the first available server. With everything available, the first probe always succeeds, so O(1) stays O(1); the loop is latent, waiting for Level 4. The O(n) scans simply add .filter(|s| s.available()), and consistent hash walks the ring past unavailable servers.

Why leave a seam instead of building it later? Because retrofitting a filter into seven algorithms after the fact is where bugs breed — you'd inevitably miss a branch. By threading available() through every selection path up front (even as a no-op), Level 4 only had to flip one function's body from true to breaker.allows_traffic(). The end-to-end test confirms the seam works today: rr over [alive, dead] alternates 200 502 — the dead server is still picked, proving the filter is wired and merely disabled.

Industry Comparison

Every serious proxy load-balances, and the algorithm menu is broadly similar. The differences are in the affinity machinery, the smoothness of weighting, and how much statistical sophistication they layer on top. Ours is a teaching build.

The honest trade-off: our algorithm menu is genuinely the same list the big proxies offer, and our consistent-hash ring is the same Ketama idea nginx/HAProxy expose. Where we stop short, deliberately: weighted RR is bursty (nginx smooths it), the ring is a single sorted Vec (Envoy's Maglev has tighter disruption guarantees and O(1) lookup), least-connections tolerates a one-request race rather than locking, and there is no cookie-based session affinity (that needs header rewriting from Level 5 and middleware from Level 6). Each simplification is a lesson about the mechanism underneath, not a claim to production parity. As of 2026, nginx's random two (power-of-two-choices) is stock OSS; Envoy's Maglev remains its distinguishing consistent-hash implementation.
