Executive Summary

A reverse proxy is the front door of modern internet infrastructure — and building one from scratch is the single best way to learn how the internet actually works.

Every serious web deployment on Earth puts something between the public internet and the application servers: Nginx at a startup, Envoy inside a service mesh, HAProxy at a bank, Cloudflare in front of half the web, an Application Load Balancer in AWS. That "something" is a reverse proxy: a server that accepts client connections, understands the HTTP conversation, decides which backend should handle the request, forwards it, and relays the response — while adding security, load balancing, caching, and observability along the way.

This course builds that machine from first principles in Rust, layer by layer, over 14 levels:

Levels 1–2

Speak the protocol

Raw TCP sockets, parsing HTTP/1.1 by hand, keep-alive, chunked encoding, and a routing engine that picks a backend by host, path, and method.

Levels 3–7

Be reliable & fast

Load-balancing algorithms, health checks and circuit breakers, proxy headers, an extensible middleware pipeline, connection pooling and performance tuning.

Levels 8–14

Be production-grade

TLS termination, epoll/kqueue internals, metrics and tracing, HTTP caching, graceful restarts and config reload, a basic WAF, and horizontal scaling.

How to use this page: before implementing a level in the Rust project, read its section here. Each section explains the theory, where the feature sits in the request lifecycle, the trade-offs production systems make, and the mistakes almost everyone makes on the first attempt. The code itself lives in your rproxy crate — you write it; this page tells you why.

Analogy: a reverse proxy is a hotel receptionist. Guests (clients) never wander into the kitchen or the laundry room (backend servers). They talk to the front desk, which knows which department handles what, hides how many staff are working, keeps troublemakers out, remembers frequent answers ("breakfast is 7–10"), and can reroute work when the kitchen is slammed. The guest experience stays the same even as the hotel reorganizes behind the desk.

What Is a Reverse Proxy?

"Proxy" means someone acting on another's behalf. The question is: whose behalf?

Forward proxy vs reverse proxy

A forward proxy acts on behalf of clients. Your corporate network's outbound proxy hides the employees from the internet: websites see the proxy's IP, not each laptop's. The client knows about the proxy; the server doesn't care.

A reverse proxy acts on behalf of servers. The client thinks it is talking to example.com, but it is actually talking to a proxy that hides an entire fleet of backend servers. The server operator configures the proxy; the client has no idea it exists.

FORWARD PROXY (protects/represents clients)

 [Client A] ---\                            /---> site1.com
 [Client B] ----+--> [Forward Proxy] ------+----> site2.com
 [Client C] ---/       (one exit IP)        \---> site3.com

REVERSE PROXY (protects/represents servers)

                                            /---> [Backend 1]
 [Any client] ------> [Reverse Proxy] -----+----> [Backend 2]
                       (one entry IP)       \---> [Backend 3]

Why does every serious deployment use one?

Single public entry point

One IP, one TLS certificate, one place to enforce security policy. Backends can live on private IPs, unreachable from the internet.

Load distribution

Ten small servers behind one proxy behave like one big server. Add or remove backends without clients noticing.

Protocol shielding

The proxy handles slow clients, malformed requests, ancient HTTP versions, and attacks — backends see only clean, well-formed traffic.

Cross-cutting features in one place

TLS, compression, caching, auth, rate limiting, logging — implemented once at the edge instead of in every application.

Why the proxy terminates the client connection

A reverse proxy is not a dumb pipe. It runs two independent connections: one with the client, one with the backend. The client's TCP connection ends (terminates) at the proxy; the proxy opens its own TCP connection to the backend. This is the fundamental design decision everything else builds on:

  1. It must read the request to route it. Choosing a backend by path or hostname requires parsing HTTP — which requires being a real endpoint of the connection (and, for HTTPS, holding the TLS keys).
  2. Client and backend lifetimes decouple. A client on hotel Wi-Fi can take 30 seconds to send a request; the backend only sees the request when it's complete. Slow clients stop poisoning backend resources.
  3. Connections can be reused independently. 10,000 client connections can share 50 pooled backend connections. Keep-alive on each side is negotiated separately.
  4. Each side can speak a different dialect. HTTP/2 from clients, HTTP/1.1 to backends. TLS outside, plaintext inside the datacenter.
Watch out: "terminates the connection" confuses beginners — it does not mean closing or dropping it. It means the connection's endpoint is the proxy (like a bus terminal: the end of the line), rather than the proxy passing raw bytes through untouched. A device that just forwards packets without being an endpoint is a router or an L4 passthrough, not a reverse proxy.

Key mental model: the proxy is a translator sitting between two phone calls. Level 1 · Core Networking

Before a proxy can be clever, it must speak. This level builds the mouth and ears: TCP connections and the HTTP/1.1 protocol, parsed by hand.

TCP: the reliable byte pipe

TCP gives you exactly one abstraction: a bidirectional, ordered, reliable stream of bytes between two endpoints. Not messages. Not requests. Bytes. Everything HTTP-shaped is something you must construct on top.

A connection is identified by a 4-tuple: (client IP, client port, server IP, server port). The server side is created in three steps that Unix has used for 40 years:

  1. socket() — ask the kernel for a socket, receiving a file descriptor (a small integer; sockets are files in Unix).
  2. bind() + listen() — attach it to an address/port and tell the kernel to queue incoming connections (the backlog queue).
  3. accept() — pop one completed connection off that queue, receiving a new file descriptor for that specific client. The listening socket keeps listening.

Before accept() ever returns, the kernel has already completed the three-way handshake with the client:

 Client                                Server (kernel)
   | ------------ SYN ------------------> |   "I want to connect, my seq=x"
   | <--------- SYN+ACK ----------------- |   "OK, my seq=y, I heard x"
   | ------------ ACK ------------------> |   "I heard y"        [ESTABLISHED]
   |                                      |   --> connection waits in backlog
   |                                      |       until your accept() call
Watch out: the handshake happens in the kernel before your code runs. If your accept loop is slow, connections pile up in the backlog queue; when it overflows, clients get connection refused or silent SYN drops. This is why production proxies obsess over accept-loop latency — and it's your first performance lever in Level 7.

HTTP/1.1: text framing over the byte pipe

HTTP/1.1 is a text protocol with a brutal framing problem: given an endless byte stream, where does one request end and the next begin? The message format:

GET /api/users?page=2 HTTP/1.1\r\n        ← request line: METHOD SP PATH SP VERSION
Host: example.com\r\n                     ← headers: Name ":" value
Connection: keep-alive\r\n
Content-Length: 0\r\n
\r\n                                      ← empty line: end of headers
(body bytes, if any)

Framing rules you will implement, in order of increasing pain:

RuleHow the body endsGotcha
No bodyGET/HEAD typically have none…but a GET may have Content-Length. Parse honestly.
Content-Length: NExactly N bytes after the blank lineRead exactly N — one byte more steals from the next request on the connection.
Transfer-Encoding: chunkedSeries of <hex size>\r\n<bytes>\r\n, ending with 0\r\n\r\nUsed when the sender doesn't know the length up front (streaming). Chunk sizes are hex!
Connection closeBody ends when the peer closesLegacy HTTP/1.0 style; only valid for responses.
Analogy: TCP hands you a ticker tape of letters with no spaces. HTTP framing is the grammar that lets you cut the tape into sentences: "read until blank line, then check the length label to know how much more to cut." Get the cut wrong by one character and every following sentence is garbage — this failure mode is called desync, and it's the root of request-smuggling attacks (Level 13 territory).

Keep-alive and persistent connections

In HTTP/1.0, each request required a fresh TCP connection: handshake, request, response, teardown — three round trips of overhead for one exchange. HTTP/1.1 made connections persistent by default: after a response, both sides keep the socket open and the next request flows immediately. Connection: close opts out. For a proxy this doubles in complexity: keep-alive is negotiated independently on the client side and the backend side — a closing client must not force you to discard a perfectly reusable backend connection (that's connection pooling, Level 7).

Streaming, not buffering

A naive proxy reads the whole request into memory, then writes it out. A 2 GB file upload = 2 GB of your RAM per client. Real proxies stream: read a chunk from one socket, write it to the other, reuse the buffer. Memory per connection stays constant (typically 8–64 KB) regardless of body size. You'll build this with two copy loops running concurrently — one per direction.

Rust concepts this level introduces

Async

Tokio tasks & async/await

One lightweight task per connection instead of one OS thread per connection. tokio::spawn is your "handle this client concurrently" verb. Deep dive on how in Level 9.

Ownership

Moving sockets into tasks

accept() gives you a TcpStream; you move it into the spawned task. Ownership makes "who is responsible for closing this socket?" a compile-time answer.

Errors

Result everywhere

Every read/write can fail (client vanished, reset, timeout). Rust forces you to acknowledge each one — the ? operator keeps it readable.

Buffers

&[u8] vs String

HTTP is bytes that are mostly ASCII. Parse from byte slices; convert to &str only what you've validated. Bodies may be arbitrary binary — never assume UTF-8.

Production notes

  • Nginx does not use one task per connection — one worker process per core runs an event loop over thousands of connections (Level 9 explains why both designs land in the same syscalls).
  • Real parsers are incremental: production parsers (like httparse, used under Hyper) handle "headers split across two TCP reads" without re-scanning from the start. Your first parser can re-scan; know that it's O(n²) in the worst case.
  • Robustness principle, revised: old wisdom said "be liberal in what you accept." Modern proxies are strict — lenient parsing differences between proxy and backend are exactly what request smuggling exploits.
Common mistakes: (1) assuming one read() returns one complete request — TCP guarantees no such thing; a request may arrive in 1 byte or 1000 requests may arrive in one read. (2) Forgetting \r\n is two bytes. (3) Writing a response without Content-Length and wondering why curl hangs waiting for more. (4) Buffering entire bodies in RAM.

Level 2 · Routing

Routing answers one question per request: given this method, host, and path — which backend group handles it?

The routing decision

A route is a predicate over the parsed request plus a target. Real-world examples:

Host: api.example.com                        → api-servers
Host: example.com, path starts with /static/ → static-file servers
Host: example.com, path = /health            → answered by proxy itself
method = POST, path matches ^/upload/.*$     → upload-servers

Match dimensions stack: host (virtual hosting — one IP serving many domains, read from the Host header), path (exact, prefix, wildcard, regex), and method. The engine evaluates them in a defined precedence order, because multiple routes usually match:

  1. Exact path match beats everything: /api/users.
  2. Longest prefix match next: /api/users/ beats /api/ beats /. ("Most specific wins" — same logic as IP routing tables.)
  3. Regex routes in configuration order (first match wins) — this is Nginx's model.
  4. Catch-all (/) as the default backstop.
Analogy: a mailroom sorting letters. "Addressed exactly to the CEO" (exact) is checked before "anything for the finance floor" (prefix), before "anything mentioning invoices anywhere on the envelope" (regex), before "everything else goes to the front office" (catch-all).

How routing engines work internally

Data structureLookup costUsed byTrade-off
Linear scan of route listO(routes)Your v1; fine <100 routesTrivially correct, easy precedence; slow at scale
Hash map (exact matches)O(1)Everyone, for exact hosts/pathsOnly exact matches
Trie / radix tree on path segmentsO(path length)Nginx locations, Envoy, most Go routersPrefix matching is free — longest match falls out of the walk naturally

The production pattern is a hybrid: hash for exact, radix trie for prefixes, ordered regex list as fallback. Route tables are built once at config load into an immutable structure that request tasks read lock-free (in Rust: Arc<RouteTable>, swapped atomically on reload — foreshadowing Level 12's hot reload).

Common mistakes: (1) matching on the raw path without normalizing — /api/../admin must be canonicalized before route matching or attackers route around your rules (this reappears in Level 13 as path-traversal detection). (2) Recompiling regexes per request. (3) Undefined behavior when two routes tie — precedence must be explicit and documented.

Level 3 · Load Balancing

Routing chose a backend group; load balancing picks the instance. The goal: spread work so no server drowns while others idle.

Random beats smart, surprisingly often: the "power of two random choices" result — pick two servers at random, use the less-loaded one — gets you close to least-connections quality with O(1) cost and no full scan. Envoy ships it as a first-class policy. Interviewers love this one.

Consistent hashing, the 5-minute version

The problem with mod N: when N changes 4→5, 80% of keys remap. Any cache affinity you had is annihilated at exactly the wrong moment (scaling events). Consistent hashing fixes this:

  1. Imagine hash outputs arranged on a circle (0 to 2³²−1, wrapping).
  2. Place each server on the circle at hash(server_id) — actually at ~100–200 points each (virtual nodes, to smooth out imbalance).
  3. For a request, compute hash(key) and walk clockwise to the first server point. That's your pick.
  4. Adding/removing a server only remaps the keys in its arc segments: ~1/N of traffic, not 80%.
              hash ring (clockwise)
                     0/2^32
               S3 .---------. S1
                 /           \
                |   key K -->|--> lands here, walk clockwise,
               S2\           /S1'    first server point is S1'
                  '---------'     (S1' = virtual node of S1)
   remove S2: only keys in S2's arcs move; S1/S3 traffic untouched

Nginx offers it as hash $key consistent (ketama); Envoy as ring-hash and the cheaper Maglev table variant. In Rust, the ring is a sorted Vec<(u32, ServerId)> + binary search — that's the O(log N).

Session affinity & the shared-state problem

Affinity ("sticky sessions") means one client keeps hitting one server — needed when servers hold local state (in-memory sessions, WebSocket rooms). Options: IP hash (crude), consistent hash on a cookie (better), or a proxy-issued affinity cookie (what ALB does). The modern stance: make backends stateless and stop needing affinity — but proxies must support it because the world is not modern.

Rust concept unlocked here: the balancer is the first shared mutable state across your connection tasks (RR counter, connection counts). You'll meet Arc<AtomicUsize> (RR), Arc<RwLock<Vec<Backend>>> (server lists that health checks mutate), and learn why a Mutex around the whole pool would serialize your beautiful concurrent proxy into a queue.

Failure scenarios to design for: all algorithms assume "up" servers — without Level 4's health checks, RR happily sends every Nth request into a dead machine. Least-connections has a morbid failure mode: a fast-failing server finishes "requests" instantly, always has zero connections, and therefore attracts all traffic (the "black hole" effect). Health checking isn't optional.

Level 4 · Health Checks & Circuit Breakers

Servers fail constantly — deploys, OOM kills, network partitions. A proxy that keeps sending traffic to a corpse turns one server's failure into every user's outage.

Two ways to learn a backend is sick

Active

Active health checks

The proxy probes on a timer: every N seconds, send GET /health to each backend; expect 200 within a timeout. Fail K consecutive probes → mark down; pass M probes → mark up again.

Pro: detects failure even with zero traffic. Con: probe traffic scales with fleet size; a passing /health doesn't prove real requests work.

Passive

Passive (outlier detection)

Watch real traffic: count errors and timeouts per backend; too many in a window → eject it temporarily. Envoy calls this outlier detection.

Pro: free, and measures what actually matters. Con: real users are your canaries; needs traffic to detect anything.

Production systems run both: active checks as the baseline heartbeat, passive ejection to catch what probes miss. The counters that health checks flip are the same Arc<RwLock<...>> backend list your Level 3 balancer reads — your first real writer-vs-many-readers concurrency problem.

Retries, backoff, and the retry storm

A request fails — try another backend, right? Yes, but with three guards, or retries cause outages:

  1. Only retry what's safe. Connection refused before sending the request: always retryable. Timeout after sending a POST /charge-card: retrying might double-charge. Rule of thumb: retry idempotent methods (GET, HEAD, PUT, DELETE), or any request that provably never reached a backend.
  2. Cap the budget. Max 2–3 attempts, and cap fleet-wide retries as a percentage of traffic (Envoy's retry budgets) — otherwise a 50%-degraded fleet gets doubled traffic from retries, and dies completely.
  3. Exponential backoff + jitter for anything on a timer (reconnects, probe intervals after failure): wait 1s, 2s, 4s, 8s… with randomization. Without jitter, every client that failed together retries together — the thundering herd.
delay = min(cap, base × 2ⁿ) × random(0.5…1.5) — exponential backoff with jitter

Level 5 · Proxy Headers & Rewriting

Terminating connections has a side effect: the backend no longer sees the client — it sees you. Proxy headers are how you tell the backend the truth it can no longer observe.

The identity problem

To the backend, every TCP connection now comes from the proxy's IP. Without help: logs show one "user," rate limiting throttles the proxy itself, geo-features locate everyone in your datacenter, and https-only redirects loop forever (backend sees plain HTTP from the proxy). The fix is a set of conventional request headers the proxy adds:

HeaderCarriesNotes
X-Forwarded-ForClient IP chain: client, proxy1, proxy2Each proxy appends the address it accepted from. Leftmost = original client… allegedly (see below).
X-Real-IPJust the immediate client IPNginx convention; simpler, no chain.
X-Forwarded-Protohttps or http as the client usedCritical after TLS termination — backend sees plaintext but must generate https:// URLs.
X-Forwarded-HostOriginal Host the client sentNeeded if the proxy rewrites Host for the backend.
Forwarded (RFC 7239)All of the above, standardized: for=1.2.3.4;proto=https;host=example.comThe official version nobody quite migrated to. Support reading it; the X- headers rule in practice.
The security rule that everyone gets wrong once: clients can send a forged X-Forwarded-For themselves. If your proxy blindly appends, the chain starts with a lie (attacker-chosen-IP, real-IP) — and backends that naively "take the leftmost value" for rate limiting or IP allowlists are spoofable. Correct policy at the trust boundary (the first proxy): strip or overwrite inbound X-Forwarded-* from untrusted clients, then append the socket-observed peer address. Backends should trust only the rightmost N entries, where N = number of proxies you control.

Rewriting: URL, Host, and header surgery

The proxy often presents a different universe to the backend than the client sees:

  • Path rewriting: client requests /api/v2/users; the API service expects /users — strip the routing prefix before forwarding. (Watch for double-slash and empty-path edge cases: /api/v2 → /, not ``.)
  • Host rewriting: forward with Host: internal-api.local when the backend virtual-hosts by a different name than the public one. Preserve the original in X-Forwarded-Host.
  • Hop-by-hop header removal: HTTP defines headers that describe one connection, not the message: Connection, Keep-Alive, Transfer-Encoding, Upgrade, Proxy-Authorization, TE, Trailer. A correct proxy must strip them and generate its own for the backend leg — forwarding a client's Connection: close verbatim would close your pooled backend connection; mishandling Transfer-Encoding is the literal mechanism of request smuggling.

Rust concepts: header manipulation is an ownership playground — efficiently editing a parsed request without cloning every header teaches Vec<(HeaderName, Value)> surgery, Cow<'_, str> for maybe-modified values, and why zero-copy parsing (borrowing from the read buffer) fights with mutation (needing owned data). Most real proxies compromise: borrow while inspecting, allocate when rewriting.

Level 6 · Middleware

Auth, logging, rate limiting, compression… none of these belong in your core forwarding loop. Middleware is the architecture that lets features stack like Lego instead of tangling like spaghetti.

The onion model

A middleware wraps request handling: it sees the request on the way in (before inner layers) and the response on the way out (after them). Layers compose into an onion around the core proxy handler:

 request → [ logging [ request-ID [ auth [ rate-limit [ PROXY CORE ] ] ] ] ] → response
              |          |            |        |             |
              in: start  in: gen ID   in: 401? in: 429?      forward to backend
              out: log   out: header  out: -   out: -        ← response bubbles out

Two contracts every middleware honors: it can short-circuit (auth failure returns 401 immediately — inner layers and the backend never run), and it must pass through otherwise, possibly annotating the request (request ID) or the response (server header). Order matters and is config-defined: rate-limit before auth if you want to throttle password-guessing; after, if limits are per-user.

Analogy: airport security layers. Ticket check → passport control → baggage scan → gate. Each station can reject you (short-circuit), stamp you (annotate), or wave you through. The airline (backend) only ever meets passengers who passed every station — and the stations don't know about each other, which is exactly the point.

Designing the trait (the Rust heart of this level)

This level is where Rust's type system earns its keep. The design space, roughly the same one Tower (the ecosystem's service abstraction) navigates:

  • A Middleware trait with an async handle(request, next) → Response where next invokes the rest of the chain — the onion made explicit.
  • Dynamic dispatch (Vec<Box<dyn Middleware>>): config-driven ordering, one vtable hop per layer. This is your v1 — flexible and fast enough.
  • Static composition (nested generics, how Tower's ServiceBuilder works): zero-cost, monomorphized… and the compile errors are legendary. Understand it; don't start there.
  • Async traits: async fns in traits need care (they desugar to returning futures; trait objects need boxing — async-trait crate or manual Pin<Box<dyn Future>>). This level teaches why that boxing exists.

Rate limiting: the flagship middleware

The industry algorithm is token bucket: a bucket holds up to burst tokens, refilled at rate tokens/sec; each request takes one token or gets 429. It allows short bursts while capping the sustained rate — unlike a fixed 10-per-second window, which allows 20 back-to-back at a window boundary (the classic fixed-window flaw). Per-client buckets live in a concurrent map keyed by client IP (from Level 5's trusted XFF logic — the levels interlock).

Production comparison: Nginx has fixed phases (rewrite → access → content → log) that modules hook into; Envoy has an explicit ordered filter chain, closest to what you're building; Traefik/Caddy do config-composed middleware chains like your Vec<Box<dyn>>. Every mature proxy converged on the same idea: an ordered pipeline of composable interceptors around a forwarding core.

Level 7 · Performance

Correct is table stakes. This level is about the difference between "works with 10 curls" and "works with 10,000 concurrent connections without falling over."

Connection pooling: the biggest single win

Without pooling, every proxied request pays a fresh TCP handshake to the backend (+TLS handshake if the backend leg is encrypted — far worse). With pooling, finished backend connections go into a per-backend idle pool and the next request reuses one:

  no pool:   [req] --SYN,SYNACK,ACK--> backend   every request pays ~1 RTT
                                                  (+2 RTT TLS) before byte one
  pooled:    [req] --> idle conn from pool --> backend   0 RTT setup
             done  --> conn returns to pool (if reusable)

The rules that make pools correct, not just fast: a connection returns to the pool only if the response was fully read and neither side sent Connection: close; pools need a max size (don't hold 10,000 idle sockets), an idle timeout (backends kill silent connections — stale pooled conns cause mysterious resets), and a health rule (a conn that just errored doesn't go back). In Rust this is a classic Arc<Mutex<Vec<Idle>>>-per-backend with an RAII guard that returns the connection on drop.

Timeouts: every await gets a deadline

An await without a timeout is a resource leak with a delay. The full set, each protecting a different phase:

TimeoutProtects againstTypical value
Client header readSlowloris: clients trickling a byte a minute to hold sockets open (also Level 8)5–30 s
Backend connectDead/blackholed backends eating 2-minute kernel TCP timeouts1–5 s

In Tokio: tokio::time::timeout(dur, future) wraps any await. The subtle part is what you do after — a timed-out backend connection must be dropped, not pooled (its state is unknown).

Memory: buffers, allocation, and copies

  • Buffer reuse: allocating fresh 8 KB read buffers per request hammers the allocator. Reuse per-connection buffers across keep-alive requests; the bytes crate's Bytes/BytesMut give cheap reference-counted slicing of one buffer (zero-copy views of header values into the read buffer).
  • Streaming copy loops (from Level 1) keep per-connection memory flat. Your memory budget is roughly connections × (2 buffers + task stack) — at 10k connections with 2×16 KB buffers, ~320 MB of buffers alone. Buffer size is a real dial.
  • True zero-copy: kernels can splice socket-to-socket without data touching userspace (splice()/sendfile()). L7 proxies mostly can't use it for headers (they must inspect), but can for large streamed bodies after the headers are parsed. Know it exists; measure before reaching for it.
  • Lock contention: shared state (pool mutexes, metrics counters) becomes the bottleneck as cores multiply. Weapons: shard the state (per-core pools), atomics over mutexes for counters, RwLock for read-mostly config, never hold a lock across an .await (deadlock-adjacent and stalls the executor).
Throughput vs latency — they fight: batching, bigger buffers, and Nagle's algorithm raise throughput but add latency; TCP_NODELAY (which proxies enable) and small buffers cut latency but cost syscalls. Nginx is event-driven precisely because at 10k connections, thread-per-connection dies on memory and context-switch overhead — the C10K problem. Tokio gives you the same event-driven substrate with task-shaped ergonomics; Level 9 shows the machinery.
Measure, don't guess: benchmark with wrk or oha before and after every optimization. The profile will surprise you — it's usually syscall count or allocator pressure, not the code you thought. cargo flamegraph is your friend. Also: raise the file-descriptor limit (ulimit -n) before any 10k-connection test, or you'll benchmark your OS's error path.

Level 8 · Security & TLS

The proxy is the one machine you deliberately expose to every stranger on the internet. This level makes that survivable: encrypted transport and armored defaults.

TLS termination

Termination means the proxy holds the certificates and private keys, performs the TLS handshake with clients, and decrypts traffic — backends receive plaintext HTTP (or re-encrypted traffic, below). Why terminate at the proxy? One place to manage certs and rotate keys, hardware/CPU concentrated where it's needed, and the proxy must decrypt anyway to route by path or inspect for the WAF.

   client ==== TLS (encrypted) ====> [proxy: decrypt] ---- plaintext ----> backend
                                          |
                              certificates + private keys
                                     live here only

   variants:  re-encrypt:  proxy ==== new TLS ====> backend   (zero-trust networks)
              passthrough: proxy routes by SNI only, never decrypts (L4 mode)

The handshake itself (TLS 1.3, one round trip): client sends supported ciphers + SNI (Server Name Indication — the hostname, in cleartext, which is how one proxy IP serves certs for many domains); server replies with its certificate and key-exchange material; both derive symmetric session keys via ECDHE. The asymmetric crypto happens once per handshake; the bulk traffic uses cheap symmetric AES-GCM/ChaCha20. Session resumption lets returning clients skip most of it — a big deal at scale.

In Rust: rustls (a memory-safe TLS stack, no OpenSSL C code) + tokio-rustls, which wraps your TcpStream into a TlsStream. Beautifully, everything you built in Levels 1–7 works unchanged on top — both implement AsyncRead + AsyncWrite, so your proxy core becomes generic over the stream type. This is trait-based design paying off.

Mutual TLS (mTLS)

Normal TLS authenticates the server to the client. mTLS adds the reverse: the client must present a certificate the proxy validates against a trusted CA. Humans-with-browsers rarely use it; service-to-service traffic (Envoy sidecars in a mesh, internal APIs, partner integrations) uses it heavily — it's authentication without passwords or tokens, at the transport layer.

Armoring the front door

Attack

Slowloris

Hundreds of connections each sending one header byte per minute — never finishing, never idle, holding your sockets forever. Defense: header-read deadline (whole request line + headers within N seconds), cap on connections per source IP, and a global connection ceiling with LRU eviction of the stalest.

Attack

Resource exhaustion

A 10 GB request body, a 1 MB header line, 10,000 headers. Defense: hard limits on request-line length (~8 KB), header count and total size (~16–64 KB), and body size (per-route: an upload route allows more than an API route). Reject with 431/413, don't buffer then decide.

Control

IP allow/deny lists

Deny lists block known-bad sources (fed by Level 13's reputation logic); allow lists gate admin paths to office/VPN ranges. Implementation detail that matters: match against CIDR ranges, not exact IPs, and check the socket peer address, never client-supplied headers.

Posture

Secure defaults

TLS 1.2 minimum (1.3 preferred), strong cipher allowlist, timeouts on by default, size limits on by default, server-version header suppressed. The theme: the config a lazy user gets must be the safe one — Caddy won mindshare largely on this principle (HTTPS automatic, defaults hardened).

Common mistakes: (1) reading the whole body then checking the size limit — the damage is done; enforce while streaming. (2) Private keys readable by the world (chmod 600, and never in git). (3) Forgetting that limits apply to responses too when backends are semi-trusted. (4) Building your own crypto or hand-rolling cert parsing — use rustls; this is the one level where "from scratch" stops at the library boundary, deliberately.

Level 9 · OS Internals: What Async Actually Is

You've written stream.read(&mut buf).await a hundred times by now. This level opens the floor and shows the machinery: non-blocking sockets, epoll/kqueue, and the Tokio runtime as a well-organized event loop.

The problem: read() blocks

A normal read() on a socket with no data parks the calling thread until bytes arrive. Thread-per-connection at 10k connections means 10k threads: gigabytes of stacks, and the scheduler melts (the C10K problem, historically). The fix is to change the question:

Blocking asks: "give me data on THIS socket, I'll wait." Event-driven asks: "here are 10,000 sockets — wake me when ANY has data." One thread now serves them all, sleeping until there is actual work.

Two ingredients: (1) set sockets O_NONBLOCK, so read() with no data returns EWOULDBLOCK immediately instead of parking; (2) a kernel readiness API to sleep until something is ready. The evolution of that API is the whole story:

APIModelCost per waitFatal flaw / why it won
select() (1983)Pass a bitmask of FDs each callO(n) scan, ~1024 FD capKernel re-scans every FD every call; the cap is compiled in
poll() (1986)Pass an array of FDs each callO(n) scan, no capStill re-passes and re-scans everything each time
epoll (Linux, 2002)Register FDs once in a kernel object; epoll_wait() returns only ready onesO(ready)Kernel keeps the interest list; waiting costs nothing per idle FD. This is why 10k idle connections are cheap
kqueue (BSD/macOS, 2000)Same idea, arguably cleaner API (kevent for files, signals, timers too)O(ready)What Tokio uses on your Mac
IOCP (Windows) / io_uring (modern Linux)Completion-based: "start this read; tell me when it's DONE" (vs "tell me when I may read")O(done), fewer syscallsio_uring batches submissions/completions in shared-memory rings — the current performance frontier

From epoll to async/await: the Tokio stack

An async fn compiles to a state machine (an anonymous type implementing Future). Each .await is a possible pause point where the machine returns Poll::Pending and parks. Nothing runs in the background — a future is inert until polled. The layers that do the polling:

  1. Your task calls stream.read(buf).await. Tokio's TcpStream tries the non-blocking read() syscall right now. Data available? Return it — no waiting, no magic.
  2. EWOULDBLOCK? The future registers interest — "wake task #417 when FD 12 is readable" — with the runtime's reactor (mio, wrapping epoll/kqueue), stores a Waker, and returns Pending. The task is now parked: zero CPU, ~KBs of memory (its state machine), no thread held.
  3. The executor (Tokio's scheduler) runs other ready tasks on its worker threads (one per core, with work stealing: idle workers steal queued tasks from busy ones).
  4. Kernel sees bytes arrive on FD 12. The reactor's epoll_wait/kevent call returns; the reactor looks up FD 12 → calls waker.wake() → task #417 goes back on a run queue.
  5. The executor re-polls task #417; the state machine resumes exactly at the await point; this time read() returns data; execution continues to the next await. Repeat forever.
   your async fn  ==compiles to==>  state machine (Future)
        |                                  |
   .await point                    Poll::Pending + register Waker
        |                                  |
   [ EXECUTOR: worker threads, run queues, work stealing ]
        |                                  ^
   parks task                        wake(task)
        |                                  |
   [ REACTOR (mio): one epoll/kqueue instance, FD -> Waker map ]
        |                                  ^
   epoll_ctl(ADD, fd)              epoll_wait() returns: fd 12 readable
        +----------------- KERNEL ---------+
Analogy: a restaurant with one waiter (per core) and pagers. Blocking I/O = the waiter stands at your table until you decide your order. Async = the waiter hands you a pager and serves others; the kitchen bell (epoll) tells them which pager to buzz. The waiter never stands idle at a silent table — and 10,000 tables need only as many waiters as there are simultaneously talking tables.
The cardinal sin: blocking the executor. A synchronous std::fs read, a CPU-heavy regex, a Mutex held across an await — any of these freezes a worker thread, and every task queued on it stalls (your p99 latency spikes mysteriously). Rules: use tokio::fs/spawn_blocking for sync work, keep lock hold times tiny and never across .await, and remember async helps I/O-bound work only — CPU-bound work needs threads, not futures.

Nginx, revisited: now you can read its design fluently. One master process (config, signals) forks N single-threaded workers; each worker runs epoll_wait in a loop, with all connection state in explicit C structs instead of compiler-generated state machines. SO_REUSEPORT lets all workers accept on the same port with kernel-level load spreading. Tokio and Nginx are the same architecture — epoll event loop — wearing different clothes: Nginx hand-writes the state machines; Rust's compiler writes them for you at zero runtime cost. That's the entire "fearless async" pitch in one sentence.

Level 10 · Observability

At 3 a.m., "the site is slow" is the ticket. Observability is the difference between knowing which backend, which route, which percentile in 30 seconds — and restarting things at random.

The three pillars, proxy edition

Logs

Structured events

One JSON line per request (the access log): timestamp, method, path, status, duration, bytes, backend chosen, client IP, request ID. Structured (JSON/logfmt) beats prose because machines aggregate it: jq 'select(.status>=500)' vs regex archaeology. Plus a separate error log for proxy-internal events at leveled severity.

Metrics

Aggregated numbers

Counters (requests_total by status/route), gauges (active connections, healthy backends), histograms (request duration — percentiles, not averages!). Cheap enough to record on every request, queryable over months. Exposed on GET /metrics in Prometheus text format for scraping.

Traces

The request's journey

Spans with timing per stage (parse → route → backend), correlated across services by propagated context headers (W3C traceparent). The proxy's superpower: it's positioned to start the trace and stamp the request ID everything downstream logs.

p50 = typical user   p99 = 1-in-100 users, and your biggest customers hit it hourly   average = a lie that hides both

Why histograms: an average of 40 ms can hide 1% of requests taking 4 seconds. Prometheus histograms bucket observations (≤1ms, ≤10ms, ≤100ms…) so you can compute percentiles across the fleet. Latency is a distribution; treat it as one.

Implementation notes for your proxy

  • Request ID first: generate a UUID (or accept a trusted inbound one) in the earliest middleware, attach it to every log line for that request, forward it as X-Request-ID, return it in the response. When a user reports an error, this one string finds every relevant log line across every system. Highest value-to-effort ratio in the level.
  • The tracing crate is Rust's standard: spans (enter/exit with timing) + events (points in time), with structured fields; subscribers format to JSON. It's designed for async — spans follow tasks across await points, which naive thread-local logging gets wrong.
  • Metrics are shared state done cheap: atomics (AtomicU64 counters) and pre-allocated histogram buckets — never a mutex on the hot path, never an allocation per request. Your Level 7 instincts apply to your own instrumentation.
  • Timing capture: record Instant::now() at accept, after parse, after backend connect, at first response byte, at completion — the deltas (queue time, backend time, transfer time) tell you where slowness lives, which is the entire 3 a.m. question.
Production comparison: Nginx ships a text access log and a bare status module (detailed metrics are the paid tier); Envoy went the other way — hundreds of Prometheus metrics, native tracing, and that choice is a big reason service meshes standardized on it. HAProxy's runtime stats socket lets you inspect and even reconfigure live. The industry lesson: proxies are the best vantage point in the whole system — they see every request, every backend, every failure — so instrument yours like it's the flight recorder, because it is.

Level 11 · Caching

The fastest backend request is the one you never make. A response cache turns your proxy into a shield that absorbs repeated traffic before it touches a backend.

HTTP's caching contract

HTTP has caching built into the protocol — your job is to honor it, not invent it. The response headers are instructions from the origin to caches:

HeaderMeaning for your cache
Cache-Control: max-age=300Fresh for 300 s; serve from cache without asking anyone.
Cache-Control: no-cacheCache it, but revalidate with the origin before every use (confusingly named — it does not mean "don't cache").
Cache-Control: no-storeNever write this to cache at all. (This one means what no-cache sounds like.)
Cache-Control: private / s-maxageprivate: browser may cache, shared caches (you!) must not. s-maxage: TTL specifically for shared caches, overrides max-age.
ETag: "abc123" / Last-ModifiedVersion identifiers enabling cheap revalidation (below).
Vary: Accept-EncodingThe response depends on that request header → it must be part of your cache key, or you'll serve gzip to clients that can't read it.

Revalidation is the elegant trick: a stale cached entry isn't discarded — the proxy asks the origin If-None-Match: "abc123"; if unchanged, the origin answers 304 Not Modified with no body, and the proxy re-stamps the cached copy fresh. One tiny round trip instead of re-transferring the payload.

What is safe to cache?

Default: GET (and HEAD) with 200/301/404 status, without Authorization or Set-Cookie, respecting no-store/private. Never cache POST/PUT/DELETE. The cache key: method + host + path + query + each Vary header value. Getting the key wrong is how caches leak one user's data to another — the worst bug class in this level.

LRU with TTL: the storage engine

Memory is finite; the cache needs an eviction policy. LRU (least-recently-used) is the standard: on insert when full, evict the entry unused the longest. The classic O(1) implementation is a hash map whose values link into a doubly-linked recency list — lookup via map, bump-to-front via list, evict from back. TTL stacks on top: entries also expire by time regardless of popularity (check expiry lazily on lookup, rather than running a sweeper).

In Rust, the linked-list version is famously miserable to write safely (aliasing + mutation = the borrow checker objects — it's right, LRU aliasing bugs are real CVEs in C). Sane options: index-based arena (Vec slots + integer links), the lru crate, or a sharded map with approximate LRU — which is what concurrent production caches actually do, because one big Mutex<LruCache> serializes every request through a single lock (Level 7 lesson, again).

Cache stampede (dog-piling): a popular entry expires; 1,000 concurrent requests all miss and all hit the backend at once — the cache caused a spike. Defenses: request coalescing (first miss fetches; the other 999 wait on it — "singleflight"), serving stale during refresh (stale-while-revalidate), and TTL jitter so popular keys don't expire simultaneously. Coalescing in Tokio is a lovely exercise: a map of in-flight keys to a shared watch/broadcast channel.
Analogy: a coffee shop regulars' board. "Marco always orders a flat white" is pinned (cached) so the barista starts pouring on sight (cache hit). Notes older than a week get re-confirmed with a quick "same as usual?" (revalidation, 304 = thumbs-up). The board holds 20 notes; the least-glanced-at gets erased for new ones (LRU). And "no-store" is the customer who says "never write my order down" — you make it fresh, every time.

Level 12 · Production Features

The gap between a program and infrastructure: infrastructure changes configuration, upgrades itself, and shuts down — all without dropping a single in-flight request.

Graceful shutdown

kill -9 mid-request means a user's upload dies at 99%. Graceful shutdown is a choreography:

  1. Catch the signal. SIGTERM (polite: "please stop") and SIGINT (Ctrl-C). SIGKILL is uncatchable by design — your process just ceases. In Tokio: tokio::signal, awaited in a select alongside the accept loop.
  2. Stop accepting. Drop/close the listener. New connections get refused (or, in a cluster, go to your peers — Level 14).
  3. Drain. Let in-flight requests finish; on keep-alive connections, answer the current request with Connection: close and let it end naturally.
  4. Deadline. Wait up to a drain timeout (10–60 s); whatever is still running gets cut — a hung client mustn't hold your deploy hostage. Tokio tools: a watch channel broadcasting "shutting down" + task counters, or TaskTracker/JoinSet awaited under tokio::time::timeout.

Graceful restart: the harder trick

Upgrading the binary with zero refused connections means old and new processes must overlap on the same port. The classic techniques:

  • FD passing (Nginx): the old master forks/execs the new binary, passing the listening socket file descriptors through the exec (or over a Unix domain socket with SCM_RIGHTS). New workers accept on the inherited socket; old workers drain and exit. The listen queue never closes, so no connection is ever refused.
  • SO_REUSEPORT: both old and new processes bind the same port simultaneously (the kernel spreads accepts between them); the old one then stops accepting and drains. Simpler; a brief window where both serve.
  • Envoy's hot restart: a shared-memory handshake between generations — and notably, in Kubernetes environments people increasingly skip in-process restarts entirely and let the orchestrator roll pods behind a Service. Sometimes the production answer is "this is now the platform's job."

Configuration: file, validation, hot reload

Hard-coded addresses die here. A real proxy reads a config file (TOML is the Rust-native choice; YAML is what Envoy/Traefik users expect) declaring listeners, routes, upstreams, health checks, limits — plus CLI arguments (clap crate) for overrides like --config path and --validate (parse-and-exit, like nginx -t; deploy pipelines depend on this).

Hot reload re-reads config without restarting: on SIGHUP, parse and validate the new file — reject it wholesale if invalid, keeping the old config live — then atomically swap the active configuration. The Rust pattern is the payoff of Level 2's foreshadowing:

active: ArcSwap<Config>          // or RwLock<Arc<Config>>
request path:  let cfg = active.load();   // cheap clone of Arc, lock-free
reload path:   active.store(Arc::new(new_cfg));  // swap; old Arc drops
               // when the last in-flight request using it finishes

In-flight requests keep the Arc they started with (a consistent snapshot); new requests see the new config; the old one frees itself when the last holder drops. No locks on the hot path, no torn reads, no restart. This is Rust's ownership model solving a genuinely hard systems problem by construction.

Worker processes — do you need them? Nginx's master/worker split exists partly because C crashes: a segfaulting worker is replaced by the master while others keep serving. In Rust, memory-safety bugs largely can't crash you that way (panics are catchable per-task), so single-process multi-threaded Tokio is the norm (Pingora made this exact argument, plus better connection-pool sharing). Understand the pattern; you likely don't need it.

Level 13 · Basic WAF

A Web Application Firewall is a reverse proxy that grew an immune system: it inspects requests for attack patterns, not just protocol validity. You already built the platform — the WAF is middleware with opinions.

What you're detecting

Injection

SQL injection

Input that escapes a query's data context into its code context: ' OR 1=1--, UNION SELECT, comment tricks (/**/), stacked queries. Signatures: quotes + SQL keywords + comment sequences in params. Attackers evade with encoding and case games — hence normalization (below).

Injection

Cross-site scripting (XSS)

Input that becomes executable script in someone's browser: <script>, event handlers (onerror=), javascript: URLs. Reflected XSS is visible in the request — which is why a proxy can catch a useful fraction of it.

Traversal

Path traversal

../../../etc/passwd — escaping the web root via .. sequences, including encoded (%2e%2e%2f), double-encoded (%252e), and mixed forms. Defense = canonicalize the path fully, then check it (your Level 2 normalization, weaponized).

Volumetric

Bots & abuse

Credential stuffing, scraping, scanners. Heuristics: impossible or absent User-Agents, request rates beyond human capability, header fingerprints that don't match the claimed browser, known scanner signatures (sqlmap, nikto). Real products add JS challenges and ML fingerprinting — your heuristics are their first layer.

Plus two coarse filters that do outsized work: IP reputation (score sources by their own recent behavior: 403s, WAF hits, error rates → temp-ban repeat offenders; commercial feeds share this across customers) and geo blocking (IP→country lookup against policy; your implementation can mock the GeoIP database with a small table — the interesting part is the middleware plumbing, not the data file).

The engine: normalize, then match, then score

  1. Normalize first — this is 80% of WAF quality. URL-decode (twice, flagging double-encoding), lowercase, collapse whitespace, decode HTML entities, canonicalize the path. Evasion is mostly encoding games; naive regex on raw bytes catches only lazy attackers.
  2. Match rules against each inspected field (path, query params, headers, body samples): compiled regex sets (RegexSet matches all patterns in one pass) plus cheap substring pre-filters (Aho-Corasick) so most-traffic-is-innocent stays fast.
  3. Score, don't hair-trigger. ModSecurity's CRS model: each rule adds points (that lone quote: 2; quote + UNION + comment: 15); block only above a threshold. Anomaly scoring is the difference between a WAF and a false-positive generator that ops teams disable within a week.
  4. Act & observe: block (403), rate-limit, tarpit, or log-only — every WAF ships in detection mode first, watching real traffic for false positives before enforcement is switched on.
Honesty checkpoint: signature WAFs are a speed bump, not a wall — determined attackers bypass regex rules, and vendors know it (that's why Cloudflare/Barracuda layer ML, reputation networks, and managed rule updates on top). The real fixes for injection live in the application: parameterized queries, output encoding. A WAF buys time during 0-days, blocks the automated 99%, and gives visibility. Level 14 · Scalability & High Availability

One proxy instance, however fast, is a single point of failure with a ceiling. The final level: what changes when "the proxy" becomes "the proxy tier."

Getting traffic to N proxies

Who balances the load balancers? The real-world answers, usually layered:

  • DNS: multiple A/AAAA records, clients pick one (round-robin-ish); health-checked DNS (Route 53) pulls dead IPs. Cheap, but TTL caching makes failover slow and clients disobey TTLs.
  • Virtual IP failover (VRRP/keepalived): an active proxy holds a floating IP; a standby claims it via gratuitous ARP on failure. Sub-second failover, the classic two-box HAProxy setup — but active/passive wastes half the hardware and only scales to 2.
  • Anycast: announce the same IP from many sites via BGP; internet routing delivers each client to the nearest. This is how Cloudflare/Google put one IP everywhere on Earth. Requires owning IP space and BGP; the lesson is the concept.
  • L4 tier over L7 tier: a thin, nearly-stateless L4 balancer (LVS, Maglev, AWS NLB) spreads flows across your L7 proxies via consistent hashing on the 4-tuple — each layer does what it's cheapest at. This is the architecture inside every major cloud.
   internet --> [ anycast / DNS ] --> [ L4 tier: consistent-hash flows ]
                                           |         |         |
                                        [proxy]   [proxy]   [proxy]     ← your rproxy, xN
                                           \         |         /
                                            [ backend fleet ]

The state problem (and how to dodge it)

N proxies must agree on things you built as single-instance state. The design hierarchy, best first:

  1. Don't share. Routing/config: identical files pushed to all instances (or streamed from a control plane, à la Envoy xDS — note the pattern: data plane proxies stay simple; a separate control plane handles distributed truth). Health state: let each proxy learn independently — slight disagreement is harmless.
  2. Share approximately. Rate limits: per-instance limits × N is often fine; when it isn't, an async-replicated count (Redis) gives a slightly-loose global limit. Exact distributed counting is expensive; approximate is usually the right trade.
  3. Share for real (rarely). Truly global coordination — leader election for "exactly one instance renews certificates," distributed config stores — means consensus: etcd/ZooKeeper leases (a leader holds a TTL'd lease and renews; lose it and another takes over) built on Raft/Paxos. Use an existing store; implementing Raft is its own course.
  4. Sessions: the cluster answer to Level 3's affinity — externalize session state (Redis) or put it in cookies (JWT) so any proxy and any backend can serve any user. Statelessness is what makes horizontal scaling linear.
CDN integration — know your place in the chain: in production your proxy usually sits behind a CDN (Cloudflare, CloudFront): the CDN handles global TLS, caching at 300 edge sites, and DDoS absorption; your tier does routing, auth, and app-specific logic. Consequences you're now equipped to reason about: the "client IP" is a CDN node (Level 5's XFF trust rules, now with a published list of trusted CDN ranges), your cache (Level 11) becomes the second layer of two, and origin pull means the CDN is just another keep-alive client of yours (Level 7's pools serve it beautifully).

Where this leaves you: every level of this course reappears at cluster scale wearing a bigger hat — consistent hashing balances proxies themselves, health checks become fleet membership, config reload becomes a control plane, graceful restart becomes rolling deploys. Distributed systems aren't a different subject; they're the same subject, multiplied. You now have the vocabulary to read the Envoy architecture docs, the Maglev paper, or the Pingora blog posts as a peer rather than a tourist.

Glossary

Anycast

One IP announced from many locations via BGP; routing delivers each client to the nearest. How global CDNs put "one" address everywhere.

Backlog

Kernel queue of completed-handshake connections waiting for your accept(). Overflow = refused clients despite a "running" server.

Backpressure

Slowing intake when downstream can't keep up — e.g., pausing backend reads when a slow client's send buffer is full, instead of buffering unboundedly.

Circuit breaker

Per-backend state machine (closed/open/half-open) that converts slow failure into instant failure while a backend is sick.

Control plane / data plane

Data plane moves requests (your proxy); control plane decides config/routing (xDS server, K8s). Keeping them separate is modern proxy architecture in one sentence.

Consistent hashing

Hash-ring assignment where adding/removing a node remaps only ~1/N of keys, not everything.

Drain

Finishing in-flight requests while accepting no new ones; the heart of graceful shutdown and rolling deploys.

Edge-triggered vs level-triggered

epoll modes: notify on change ("became readable") vs state ("is readable"). ET is fewer wakeups but you must read until EWOULDBLOCK or lose events.

File descriptor (FD)

Small integer handle to a kernel resource; sockets are FDs. The per-process FD limit is the classic invisible ceiling on connection count.

Hop-by-hop header

Header describing one TCP connection, not the end-to-end message (Connection, Transfer-Encoding…). Proxies must strip and regenerate them.

Idempotent

Safe to repeat: same effect once or five times (GET, PUT, DELETE by contract; not POST). The property that decides retryability.

Keep-alive / persistent connection

Reusing one TCP connection for sequential HTTP requests, skipping repeated handshakes. Default in HTTP/1.1.

L4 / L7

OSI shorthand: transport-layer (TCP bytes) vs application-layer (HTTP-aware) proxying.

mTLS

TLS where both sides present certificates. Service-to-service authentication without shared secrets.

Origin (server)

The true source of content, behind all proxies/CDNs. "Origin pull" = a cache fetching from it on miss.

Request smuggling

Attack exploiting parser disagreement (proxy vs backend) about where a request ends — e.g., conflicting Content-Length and Transfer-Encoding — to sneak a hidden second request past security checks.

Reverse proxy

Server-side intermediary that terminates client connections and forwards requests to backends the client never sees. The subject of this entire page.

SNI

Server Name Indication: the hostname sent in the TLS ClientHello (cleartext), letting one IP serve certificates for many domains — and letting L4 proxies route TLS without decrypting.

Slowloris

DoS via many deliberately slow, never-finishing requests that exhaust connection slots. Beaten by header deadlines and per-IP caps.

Sticky session / affinity

Pinning a client to one backend because it holds their state. Convenient, and the enemy of clean horizontal scaling.

Thundering herd / stampede

Many waiters unleashed at once — synchronized retries, or 1,000 requests hitting a backend when one hot cache entry expires. Beaten with jitter and request coalescing.

TLS termination

The proxy holding the certs, doing the handshake, and decrypting — the boundary where HTTPS becomes inspectable HTTP.

Upstream / downstream

Nginx-speak: upstream = the backends behind you; downstream = toward the client. (Envoy uses "upstream cluster" the same way.)

Zero-copy

Moving data between sockets/files without copying through userspace buffers (splice, sendfile). L7 proxies use it selectively for bodies after headers are parsed.

Interview Questions

If you can answer these cold, you didn't just build a proxy — you understood it. Answers are collapsed; struggle first.

Explain the difference between a forward proxy and a reverse proxy.

Both intermediate between clients and servers; the difference is allegiance and visibility. A forward proxy acts for clients (configured client-side, hides/polices who is browsing; servers see the proxy's IP). A reverse proxy acts for servers (configured server-side, hides the fleet; clients think it is the site). Forward = "my exit door to the internet"; reverse = "their entry door to the application."

Why does a reverse proxy terminate the client's TCP connection instead of just forwarding packets?

To do anything at L7 it must be an HTTP endpoint: routing by path/host requires parsing the request; TLS decryption requires completing the handshake; header rewriting, caching, and WAF inspection all require message-level access. Termination also decouples the two sides — slow clients don't hold backend resources, connections pool and keep-alive independently, and each leg can use different protocol versions. A device that only forwards packets is a router/L4 balancer and can do none of the above.

How do you know where an HTTP/1.1 request ends on a TCP stream?

Headers end at the first empty line (\r\n\r\n). The body then ends per framing rules: Content-Length: N → exactly N bytes; Transfer-Encoding: chunked → hex-sized chunks until a zero-length chunk; otherwise no body (for requests). If both CL and TE are present, TE wins per RFC and a careful proxy rejects or normalizes the message — parser disagreement over exactly this is the mechanism of request smuggling.

Compare round robin, least connections, and consistent hashing. When is each wrong?

RR: O(1), even distribution of counts — wrong when request costs vary wildly (one server gets all the heavy ones by luck). Least-connections: adapts to real load — wrong when a backend fails fast (zero connections attracts all traffic: the black-hole effect) and needs accurate live counters. Consistent hashing: stable key→server affinity that survives pool changes (~1/N remap) — wrong when the key space is skewed (one hot key overloads one server regardless) or when you needed load-awareness, which pure hashing ignores.

What is a circuit breaker and why is "fail fast" better than "keep trying"?

A per-backend state machine: Closed (normal, counting failures) → Open (threshold exceeded: reject instantly, send nothing) → Half-Open (after cooldown, one trial request decides). It exists because slow failure propagates: requests to a dead backend hold sockets, buffers, and tasks for the full timeout (maybe 30 s each), so the proxy runs out of resources and healthy traffic suffers. Failing in microseconds keeps the failure contained to the broken dependency, and Half-Open probes recovery without a stampede.

A backend sees the proxy's IP for every request. How does it learn the real client IP, and what's the security catch?

X-Forwarded-For: each proxy appends the peer address it accepted from, so the chain reads client, proxy1, proxy2. The catch: the client can send a forged XFF header first, so the leftmost value is attacker-controlled. The edge proxy must strip or overwrite untrusted inbound XFF, and consumers should trust only the rightmost N hops (N = proxies you control). Never use client-supplied XFF for allowlists or rate limiting.

What actually happens, down to the syscalls, when your Rust code does stream.read(&mut buf).await?

The future attempts a non-blocking read() immediately. Data ready → returns now. Otherwise the syscall returns EWOULDBLOCK; the future registers the FD with Tokio's reactor (mio → epoll on Linux / kqueue on macOS), stores the task's Waker, and returns Poll::Pending — the task is parked, its worker thread runs other tasks. When the kernel has bytes, epoll_wait/kevent returns the FD; the reactor calls the Waker; the scheduler re-queues the task; the executor re-polls it; the state machine resumes at the await and the read succeeds. Async is not magic threads — it's readiness notification plus compiler-generated state machines.

Why is average latency a misleading metric, and what do you use instead?

Latency is a skewed distribution; the mean is dominated by the fast majority and hides the slow tail. A 40 ms average coexists with 1% of requests taking 4 s — and heavy users hit that 1% constantly. Use percentiles from histograms: p50 (typical), p95/p99 (tail). Amazon-scale operators optimize p99+ because tail latency compounds across service fan-out: a page touching 10 services experiences someone's p99 on ~10% of loads.

Design cache keys for a shared HTTP cache. What goes wrong with a naive key?

Key = method + host + path + query + the value of every request header named in the response's Vary. Naive "path only" keys fail two ways: (1) correctness — gzip responses served to clients that didn't send Accept-Encoding: gzip; (2) security — caching a response that varied on Cookie/Authorization under a shared key serves user A's private data to user B. Also honor private/no-store, and don't cache Set-Cookie responses.

How does zero-downtime config reload work without locks on the request path?

Immutable config snapshots behind an atomic pointer (ArcSwap/RCU pattern). Each request loads the current Arc<Config> once — a cheap refcount bump — and uses that consistent snapshot for its whole lifetime. Reload parses and validates the new file off to the side (rejecting it wholesale if invalid), then atomically stores a new Arc. New requests see the new config; in-flight requests finish on the old one, which frees when its last holder drops. No locks, no torn state, no restart.

Your proxy must survive a deploy at 10k RPS with zero dropped requests. Walk through it.

Per instance: catch SIGTERM → stop accepting (close/hand off the listener) → mark self unhealthy so the upstream LB/L4 tier drains new traffic away → finish in-flight requests, answering keep-alive connections with Connection: close → hard deadline (e.g. 30 s) for stragglers → exit. Fleet-wide: roll one instance at a time behind the L4 tier/DNS, health-gated, so capacity never dips below demand. For in-place binary upgrades: pass listener FDs to the new process (or overlap via SO_REUSEPORT) so the listen queue never closes.

Why can't a WAF fully protect a vulnerable application?

A WAF matches request patterns; it can't know the application's semantics. Signatures are evadable (encoding, fragmentation, novel payloads), inspection is bounded (can't fully parse every format at line rate), and some flaws (logic bugs, IDOR, auth issues) produce perfectly innocent-looking requests. Injection is truly fixed at the app layer — parameterized queries, output encoding. The WAF's honest value: blocks commodity/automated attacks, virtual-patches during 0-day windows, adds visibility and rate control. Defense in depth, not a substitute.

FAQ

Why build this in Rust instead of Go or C?

C is the incumbent (Nginx/HAProxy) but every buffer is a potential CVE; Go is productive but GC pauses and less-explicit control show at the tail. Rust gives C-class performance with compile-time memory/thread safety — and the industry agrees: Cloudflare replaced Nginx with Rust (Pingora/River), AWS and Microsoft ship Rust in networking infrastructure. Bonus: the borrow checker is a systems-programming tutor — every fight with it is a real aliasing bug you didn't ship.

Why not just use Hyper/Axum from day one?

Because the course goal is understanding, and Hyper's excellence hides exactly the parts you're here to learn (framing, keep-alive, pooling). Level 1 builds HTTP handling by hand; once you've earned the knowledge, swapping in httparse or Hyper is a legitimate engineering choice you'll make with open eyes — that's the "explain first, then use abstractions" rule from Build.md.

Reverse proxy, load balancer, API gateway, CDN — what's the actual difference?

One machine, different job titles. A load balancer is a reverse proxy emphasizing distribution (Levels 3–4). An API gateway is one emphasizing per-API policy: auth, quotas, transformation (Levels 5–6). A CDN is thousands of caching reverse proxies scattered geographically (Levels 11+14). You're building the genus; those are species.

Where do HTTP/2 and HTTP/3 fit?

Conceptually everything transfers: routing, balancing, headers, caching are unchanged. Mechanically, HTTP/2 replaces text framing with binary frames and multiplexes streams over one connection (head-of-line blocking moves to TCP); HTTP/3/QUIC moves transport to UDP with per-stream delivery and built-in TLS. Production proxies typically speak H2/H3 to clients and HTTP/1.1 to backends. This course masters H1 first because you can read it with netcat — the learning loop is 10× tighter.

How production-ready will the final result be?

Real enough to front actual apps on your infrastructure: TLS, health-checked balancing, metrics, graceful deploys, tests and benchmarks. Not Nginx: you'll lack years of protocol edge cases, exotic modules, and battle-tested H2/H3 stacks. The honest claim is "production-inspired and genuinely usable" — and, more valuably, you'll understand the tools you do deploy at a level most engineers never reach.

macOS vs Linux — does developing on the Mac change anything?

Tokio abstracts it: your code is identical. Underneath, macOS uses kqueue where Linux uses epoll (Level 9 covers both), tooling differs slightly (lsof over ss, tcpdump -i lo0), and Linux-only tricks (io_uring, some socket options) won't apply locally. Benchmark numbers differ across kernels — but every concept and all your Rust transfers 1:1.

What order should I actually study/build in?

Follow the levels in order — they're sequenced so each has exactly one new hard thing. Within a level: read its section here, sketch the design yourself, implement, test with curl/nc, run the module quiz, and only then advance. Levels 9 and 14 are theory-heavy checkpoints; everything else lands as code in rproxy.
